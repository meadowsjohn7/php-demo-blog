## 令牌签发与密钥管理

在 PHP Demo Blog 的 JSON API 中，JWT 的签发环节是安全链条的起点。我们采用 HS256 算法，密钥长度不低于 32 字节，并通过环境变量注入，避免硬编码在代码库中。载荷设计上，只放入必要的声明：`sub` 存放用户 ID，`iat` 与 `exp` 控制有效期，`jti` 作为唯一标识用于后续吊销。过期时间建议控制在 15 至 30 分钟，配合刷新令牌机制，既降低泄露风险，又避免频繁登录影响体验。签发时使用 `hash_hmac` 对头部与载荷的 Base64Url 编码结果进行签名，并严格校验 `alg` 字段，防止算法混淆攻击。

## 传输层加固与令牌存储

JWT 的安全性高度依赖传输通道。全站应强制启用 TLS 1.3，并配置 HSTS 策略，将 `Strict-Transport-Security` 响应头的 `max-age` 设置为一年以上，同时包含子域名。对于浏览器端，令牌不应存入 `localStorage`，而应使用 `HttpOnly`、`Secure`、`SameSite=Strict` 的 Cookie 承载，从而降低 XSS 窃取风险。在负载均衡环境下，若需集中管理刷新令牌的吊销状态，可采用分布式 Redis 集群存储 `jti` 黑名单，解决多节点状态一致性问题。所有涉及令牌的接口都应实施严格的 CSRF 令牌验证，并对输入进行 XSS 过滤，形成纵深防御。

## 校验流程与失效策略

服务端校验 JWT 时，需依次验证签名、`exp`、`nbf` 与 `iss` 声明，任何一项失败都返回 401。对于敏感操作，可引入短期的一次性令牌，结合数据库或 Redis 记录使用状态，防止重放。注销场景下，将 `jti` 写入黑名单并设置与令牌剩余有效期一致的 TTL，避免黑名单无限膨胀。刷新令牌应单独签发，并绑定设备指纹或 IP 段，发现异常时立即吊销整个令牌族。在 PHP 实现中，建议封装独立的 `JwtService` 类，统一处理编码、解码与异常，避免在控制器中散落校验逻辑。

## 架构层面的综合防护

JWT 并非孤立组件，其安全边界需要与整体架构协同。反向代理层可利用 Nginx 的 Lua 模块实现动态 IP 黑名单，过滤异常请求，降低无效校验带来的 CPU 负载。关键渲染路径的优化与令牌机制无关，但 API 响应应启用 Brotli 压缩并保持简洁的 JSON 结构，以降低首字节时间。日志中禁止记录完整令牌，只保留 `jti` 前缀用于追踪。定期轮换签名密钥，并保留旧密钥一个刷新周期，实现平滑过渡。这些实践共同构成可审计、可运维的身份验证架构，为后续功能迭代提供稳定基础。
