## 为什么选择 JSON-LD 作为结构化数据载体

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，结构化数据的输出应当与视图层解耦。JSON-LD 以独立的 script 标签承载数据，不侵入 HTML 结构，天然适合由控制器统一组装、由模板一次性渲染。相比微数据需要嵌套在标签属性中，JSON-LD 的维护成本更低，也便于在 API 响应中复用同一份数据。实施时优先覆盖 Article、BreadcrumbList 与 WebSite 三类实体，分别对应文章详情、导航路径与站点搜索框，这三者是搜索展现中最常被消费的标记。

## 与语义化 HTML 及 Schema.org 的协同

JSON-LD 不是孤立存在，它需要与语义化的 HTML5 标签配合。文章页应使用 article、header、time 等标签明确内容边界，JSON-LD 中的 headline、datePublished、author 等字段再与页面可见内容保持一致，避免出现标记与正文不符的情况。在 PHP 侧，建议为每类实体编写独立的构建函数，输入为数据库查询结果，输出为符合 Schema.org 规范的关联数组，最后统一 json_encode 并设置 JSON_UNESCAPED_UNICODE 与 JSON_UNESCAPED_SLASHES，减少无谓的转义开销。对于列表页，可输出 ItemList 并配合分页参数生成规范的 URL 序列。

## 性能与安全层面的加固

结构化数据脚本应内联在 head 中，避免额外请求阻塞关键渲染路径。若数据量较大，可仅输出首屏所需实体，其余通过 API 按需获取。同时，JSON-LD 内容来自数据库，必须进行转义处理，防止闭合 script 标签导致的 XSS 风险，建议使用 json_encode 的默认转义行为并配合严格的输出过滤。在传输层，启用 Brotli 压缩与 HTTP/3 可进一步降低含结构化数据的页面体积与首字节时间。对于需要登录态的场景，Session 状态应集中存储以保证多节点一致性，避免因状态漂移导致标记内容错乱。

## 验证与持续迭代

上线前使用结构化数据测试工具校验语法与必填字段，上线后通过搜索控制台的增强报告跟踪错误率。建议在 PHP Demo Blog 中增加一个调试路由，仅在开发环境输出格式化后的 JSON-LD，便于人工核对。结构化数据不是一次性工作，随着模板改版与字段调整，需要同步更新构建函数并回归验证。将标记生成逻辑纳入单元测试，对关键实体做字段断言，可以避免回归问题流入生产环境。
