## 状态共享的底层模型

Context API 的本质是一个跨组件树的发布订阅系统。React 在创建 Context 对象时，会同时生成一个 Provider 组件和一个内部订阅表。Provider 并不把值直接注入子组件，而是把当前值保存在 Fiber 节点的 memoizedState 上，并维护一份依赖该 Context 的 consumer 集合。当 Provider 的 value 发生变化时，React 会遍历这份集合，标记对应的 consumer Fiber 为需要更新，再交由调度器按优先级处理。因此，Context 的更新不是"推"到每个组件，而是"标记 + 调度"，真正的重渲染仍由 React 的协调流程完成。

## 订阅与重渲染的触发路径

在函数组件中，useContext 会在渲染阶段读取 Provider 的值，并把当前 Fiber 注册到 Context 的依赖链上。当 value 变更时，React 会计算新旧值是否相等（使用 Object.is），不相等才触发 consumer 的更新。这里有一个关键细节：Provider 的 value 若每次渲染都新建对象，即使内容相同也会导致所有 consumer 重渲染。底层原因是引用比较失败，而不是值比较。因此稳定的 value 引用是 Context 性能的第一道闸门。

## 优先级与批量更新

Context 的更新会进入 React 的调度队列，并继承触发更新的优先级。在并发渲染模式下，高优先级更新可以打断低优先级的渲染，但 Context 的 consumer 一旦被标记，就会在对应优先级的时间片内重新读取最新值。这意味着 Context 本身不提供细粒度的选择器能力，任何 value 变化都会波及全部 consumer。要缓解这一点，可以把大对象拆成多个 Context，或在上层用 memo 包裹消费组件，让重渲染在子树边界处被截断。

## 可执行的优化策略

第一，用 useMemo 或 useCallback 固定 Provider 的 value 引用，避免无意义的重渲染。第二，按更新频率拆分 Context，把高频变化的状态与低频配置分离。第三，对消费组件使用 React.memo，并在 props 层面保持稳定，使 Context 的标记不会穿透到无关子树。第四，避免在 Provider 内部直接执行副作用，把状态变更收敛到 reducer 或事件回调中，保证更新路径可预测。第五，在需要跨层级但更新极频繁的场景，考虑用外部 store 配合 useSyncExternalStore，把订阅粒度下沉到字段级。

理解这些底层机制后，Context API 就不再是"简单的全局变量"，而是一个受调度器约束的订阅系统。它的边界清晰：适合低频、跨层级、结构稳定的状态共享；不适合高频、细粒度、强选择性的数据流。把边界用对，才能在不引入额外依赖的前提下获得可预期的性能表现。
