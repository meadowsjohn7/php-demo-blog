## 上传链路的攻击面与分层思路

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，文件上传往往是最容易被低估的入口。攻击者并不需要复杂的利用链，只要服务端对扩展名、MIME、文件内容三者中任意一项判断失误，就可能把一段 PHP 代码落盘并触发执行。防护的第一原则是把上传链路拆成接入层、校验层、存储层、执行层四个面，每一面都假设前一面的判断可能被绕过。接入层负责限流与来源校验，校验层做多维度内容鉴定，存储层保证文件不可执行，执行层则彻底切断“上传目录即脚本目录”的默认假设。这种分层不是堆砌检查，而是让单点失效不会直接演变为 RCE。

## 多维度校验：扩展名、MIME 与内容指纹

校验层的关键在于不信任任何单一信号。扩展名白名单应基于最终落盘名而非用户提交名，统一转小写并剥离多点后缀，只保留最后一个扩展名做比对。MIME 检测不能只看请求头里的 Content-Type，而要用 finfo 读取临时文件的真实类型，并与白名单交叉验证。对于图片类上传，再叠加 getimagesize 与图像重编码，重编码能破坏嵌入在元数据或像素数据中的恶意载荷。文件内容层面可扫描危险标记，例如 PHP 开标签、短标签与常见编码混淆串，命中即拒绝并记录完整上下文。所有校验失败都应返回统一错误结构，避免通过差异化响应泄露判定逻辑。

## 存储隔离与执行边界

存储层的目标是让上传文件即使被写入也无法被当作脚本执行。推荐将上传目录置于 Web 根之外，通过受控的读取脚本输出内容，并在响应头中固定 Content-Type 与 Content-Disposition。若必须放在 Web 根内，则在该目录禁用 PHP 解析，Nginx 可用 location 规则直接返回 403，Apache 可用 RemoveHandler 与 php_flag engine off。文件名使用随机 UUID 加固定扩展名，路径按日期分片，避免同名覆盖与目录膨胀。权限上以最小化原则设置，目录不可执行、文件只读，并关闭该目录的目录列表。

## 运行时检测与可观测性

再严的校验也需要运行时兜底。可在应用层对上传事件做结构化日志，记录来源 IP、原始文件名、真实 MIME、大小与校验结论，配合定期扫描上传目录中新增的可疑文件。对高敏感业务，可在写入后计算文件哈希并与已知恶意样本库比对，或对文本类文件做语法特征匹配。需要说明的是，这些手段应作为纵深防御的补充，而不是替代前置校验。把校验、隔离、检测串成闭环，并定期用构造样本回归测试，才能让上传功能在迭代中保持稳定的安全基线。
