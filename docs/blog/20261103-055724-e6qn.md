## 为什么需要 GPU 加速

现代浏览器渲染管线分为布局、绘制与合成三个阶段。传统动画若频繁触发布局或绘制，主线程极易阻塞，导致掉帧。GPU 加速的核心在于将动画元素提升为独立的合成层，使变换与透明度变化仅由合成器线程处理，从而绕过主线程的布局与绘制开销。判断一个动画是否被 GPU 加速，可在开发者工具的 Layers 面板查看合成层数量，或使用 Rendering 面板的 Paint Flashing 观察重绘区域。

## 触发合成层的正确方式

最稳妥的触发手段是使用 `transform: translateZ(0)` 或 `will-change: transform`。前者强制创建层，后者提前告知浏览器即将变化的属性，让合成器提前准备。但需注意：`will-change` 不宜滥用，动画结束后应移除，否则会长期占用显存。优先使用 `transform` 与 `opacity` 制作动画，避免对 `top`、`left`、`width`、`height` 等几何属性做过渡，因为这些属性会触发重排。对于复杂路径动画，可考虑使用 Web Animations API 配合合成器友好属性。

## 性能陷阱与规避策略

合成层并非越多越好。每个层都会带来内存与合成开销，层数过多反而拖慢渲染。常见陷阱包括：对大量列表项逐个添加 `translateZ(0)`，导致层爆炸；在动画中修改 `box-shadow` 或 `filter`，引发昂贵的离屏渲染。建议通过 Chrome DevTools 的 Performance 面板录制动画过程，检查主线程与合成线程的耗时分布。若发现合成线程耗时过高，应减少层数量或降低动画复杂度。此外，使用 `requestAnimationFrame` 驱动 JavaScript 动画时，需确保每帧逻辑轻量，避免在回调中读取布局属性造成强制同步布局。

## 实战调优与监控

在真实项目中，建议建立动画性能基线：使用 `PerformanceObserver` 监听长任务与布局偏移，结合 `requestIdleCallback` 做非关键动画的降级处理。对于移动端，需关注设备像素比与显存限制，低端机可关闭部分合成层动画。持续监控 LCP 与 INP 指标，确保动画优化不损害核心 Web 指标。通过这套闭环方法，可将动画帧率稳定在 60fps，同时保持页面加载性能不受影响。
