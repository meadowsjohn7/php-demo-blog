## 为什么富文本过滤不能只靠“转义”

富文本编辑器提交的是 HTML 片段，直接对整段内容做 `htmlspecialchars` 会让排版全部失效，而完全信任用户输入又会引入存储型 XSS。正确的做法是“先解析、再清洗、后序列化”：用 DOM 解析器把输入还原成节点树，遍历节点并按白名单决定保留、删除还是降级，最后重新输出规范化的 HTML。PHP 内置的 `DOMDocument` 配合 `libxml_use_internal_errors(true)` 即可完成解析，避免因畸形标签导致解析中断。

## 白名单是过滤策略的核心

安全规范的第一条是“默认拒绝”。标签白名单建议只保留 `p`、`br`、`strong`、`em`、`ul`、`ol`、`li`、`blockquote`、`a`、`img`、`code`、`pre`，属性白名单则按标签分别定义：`a` 只允许 `href`、`title`、`rel`，`img` 只允许 `src`、`alt`、`width`、`height`。对 `href` 与 `src` 必须做协议校验，仅放行 `http`、`https`、`mailto` 以及站内相对路径，遇到 `javascript:`、`data:` 等协议一律剥离。事件属性（`on*`）和 `style` 属性默认不进入白名单，若业务确需样式，应改为受控的 CSS 类名映射。

## 服务端与输出层的双重防线

过滤应在服务端完成，前端编辑器的“净化”只能作为体验优化，不能作为安全边界。入库前统一走清洗函数，出库渲染时再根据上下文做转义：HTML 正文直接输出已清洗的片段，而写入属性、JS 变量或 JSON 响应时必须使用对应的转义函数。同时配合 CSRF 令牌验证与 `Content-Security-Policy` 响应头，把 XSS 的利用面压到最小。对于图片资源，建议在服务端做一次无损压缩并采用 Lazy-loading，既平衡视觉质量又控制页面加载速度。

## 可执行的安全检查清单

1. 关闭 `DOMDocument` 的自动补全干扰，解析前移除 `<!DOCTYPE>` 与 XML 声明；2. 遍历节点时对文本节点不重复转义，对元素节点按白名单决策；3. 统一使用 `rel="noopener noreferrer"` 处理外链；4. 对清洗后的 HTML 做长度与嵌套深度限制，防止资源耗尽；5. 建立回归用例，覆盖 `onerror`、`srcdoc`、`svg` 内嵌脚本等常见绕过手法。把这些规则沉淀为项目内的过滤组件，并在代码评审中强制检查，才能让富文本功能在安全与可用之间保持稳定。
