自动化测试 Selenium 脚本：安全规范

2026-11-04 · PHP Demo Blog #Selenium #自动化测试 #安全规范 #PHP #CI/CD
针对 PHP Demo Blog 项目，阐述 Selenium 自动化测试脚本在凭证管理、选择器策略、环境隔离与日志脱敏等方面的安全规范，避免测试代码成为攻击入口。

凭证与配置：绝不硬编码

在 PHP Demo Blog 的 Selenium 测试中，最常见的风险是把管理员账号、数据库密码直接写进脚本。规范做法是将凭证放入环境变量或 CI 的 secret 存储，脚本通过 `getenv()` 读取。本地开发使用 `.env.test` 文件并加入 `.gitignore`，CI 环境则注入临时令牌。测试账号应遵循最小权限原则，只具备测试所需的路由与 API 访问权，避免使用生产管理员账号。对于需要登录的用例，优先使用预置的 storageState 或 cookie 注入，减少重复登录带来的凭证暴露面。

选择器与等待：稳定优先于速度

选择器写法直接影响脚本的健壮性与安全性。禁止使用基于页面文本的模糊匹配来定位敏感按钮，例如用“删除”文本定位删除按钮，容易误操作。应使用稳定的 `data-testid` 属性，并与前端约定命名规范。等待策略上，禁用 `sleep()` 硬等待，统一使用显式等待 `WebDriverWait` 配合预期条件。这样既能避免因网络抖动导致的误判，也能防止脚本在页面未就绪时提交表单，造成脏数据。对于文件上传与下载，限制临时目录并在用例结束后清理，避免残留文件泄露。

环境隔离与网络边界

Selenium 脚本不应直连生产环境。规范要求测试指向独立的 staging 域名，并在脚本启动时校验 `base_url` 是否包含预期环境标识，不匹配则立即退出。对于涉及支付的用例，使用沙箱网关或 mock 服务。浏览器启动参数应禁用不必要的扩展与自动填充，并设置 `--disable-dev-shm-usage` 等稳定参数。若使用远程 Grid，需为节点配置网络白名单，仅允许访问测试域名与依赖服务，防止脚本被利用作为内网探测跳板。

日志与报告：脱敏后再落盘

测试失败时的截图与页面源码是排查利器，但也可能包含用户信息。规范要求对截图中的输入框区域进行遮罩，或在保存前对 HTML 中的 `value` 属性与 token 字段做正则替换。日志中禁止打印完整请求头与 cookie，只记录状态码与耗时。报告上传至 CI 制品库时设置保留周期，避免长期堆积。结合 PHP Demo Blog 的 JSON API 特性，可单独编写 API 层冒烟测试，减少 UI 脚本对敏感页面的依赖，从而降低整体暴露面。

结语

安全规范不是一次性的检查项，而是随用例增长持续演进的约束。把凭证管理、选择器约定、环境校验与日志脱敏写成团队检查清单，并在代码评审中强制执行，才能让自动化测试真正成为质量保障而非风险来源。
