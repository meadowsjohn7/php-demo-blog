## 为什么选择 WebP

WebP 在同等视觉质量下通常比 JPEG 和 PNG 更小，尤其适合博客配图与列表缩略图。在 PHP Demo Blog 这类轻量项目中，图片往往是首屏最大的资源，直接拖慢 LCP。转换 WebP 不是简单换个扩展名，而是要在服务端生成兼容格式，并保留原图作为回退。

## 服务端转换与缓存策略

推荐在图片上传或首次请求时用 GD 或 Imagick 生成 WebP 副本。以 GD 为例，`imagewebp()` 可直接输出，质量参数建议 75–85。转换结果按原图路径加哈希存入独立目录，避免重复计算。若使用 Nginx，可配置 `try_files` 优先返回 WebP，减少 PHP 层开销。对于已有大量图片的站点，可写一个 CLI 脚本批量转换，并记录处理状态。

缓存方面，转换后的 WebP 应设置长缓存头，同时保留原图用于社交分享等场景。结合 Lazy-loading，在 `<img>` 上使用 `loading="lazy"` 或 IntersectionObserver，能进一步平衡视觉质量与加载速度。

## 安全与兼容性要点

转换前必须校验 MIME 类型与文件尺寸，防止恶意文件消耗内存。PHP 中可用 `getimagesize()` 做初步检查，并限制最大像素数。输出时通过 `Content-Type: image/webp` 明确类型。对于不支持 WebP 的旧客户端，用 `<picture>` 元素提供 JPEG 回退。

此外，图片路径应避免直接暴露服务器目录结构，转换脚本需做权限隔离。在 Web 层配合严格的输入过滤，可降低图片处理环节被利用的风险。

## 与整体性能优化的协同

WebP 只是图片链路的一环。将转换后的图片纳入关键渲染路径优化，例如为首屏图片设置 `fetchpriority="high"`，非首屏延迟加载。结合 HTTP/3 与 Brotli 压缩，可进一步降低 TTFB。对于 PHP Demo Blog 的 JSON API，返回图片元数据时只给必要字段，避免序列化开销。

持续监控转换成功率与缓存命中率，定期清理过期副本，是维持长期效果的必要运维动作。
