跨域资源共享 CORS 配置：底层原理

2026-11-02 · PHP Demo Blog #CORS #PHP #HTTP #安全 #API
从同源策略出发，解析 CORS 预检请求与响应头的底层机制，并结合 PHP 路由与 JSON API 场景给出可落地的配置要点。

同源策略与 CORS 的触发条件

浏览器的同源策略以协议、域名、端口三元组作为隔离边界。当页面脚本向不同源的接口发起请求时，响应必须携带 `Access-Control-Allow-Origin` 等头部，否则响应体不会交给调用方。在 PHP Demo Blog 这类路由与 JSON API 项目中，前端往往部署在独立域名或开发端口上，因此 CORS 是绕不开的一环。需要明确的是，CORS 是浏览器侧的访问控制机制，服务端只需正确声明策略，并不存在“绕过”一说。

简单请求与预检请求的分野

CORS 将请求分为两类。简单请求只允许 GET、HEAD、POST 方法，且 Content-Type 限于 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`，此时浏览器直接发送请求，仅校验响应头。一旦使用 PUT、DELETE、PATCH，或携带自定义头、JSON 请求体，浏览器会先发送 OPTIONS 预检请求，携带 `Access-Control-Request-Method` 与 `Access-Control-Request-Headers`，服务端需在响应中回显允许的方法与头部。预检结果由 `Access-Control-Max-Age` 缓存，合理设置可减少往返开销。

PHP 路由层的响应头构造

在路由分发之前统一注入 CORS 头是稳妥做法。核心头包括：`Access-Control-Allow-Origin` 应精确匹配来源而非通配符，尤其是需要携带凭证时；`Access-Control-Allow-Credentials: true` 必须与具体来源配合；`Access-Control-Allow-Headers` 需覆盖前端实际使用的自定义头；`Access-Control-Expose-Headers` 用于暴露非简单响应头。对于 OPTIONS 请求，应在路由匹配前直接返回 204，避免进入业务逻辑。注意 `Vary: Origin` 的声明，防止缓存层把某个来源的响应错误复用给其他来源。

凭证、安全与常见陷阱

当请求需要携带 Cookie 时，`Access-Control-Allow-Origin` 不能为 `*`，且前端需设置 `withCredentials`。若项目采用分布式 Redis 集群存储 Session，跨域凭证的一致性更依赖严格的来源白名单。常见陷阱还包括：在 Nginx 或 CDN 层重复添加 CORS 头导致浏览器报“多个值”错误；错误地允许所有方法却遗漏 `Access-Control-Allow-Headers`；以及在错误响应中未携带 CORS 头，使前端只能看到网络错误而拿不到状态码。建议将 CORS 逻辑集中到中间件，并配合日志记录被拒绝的来源，便于排查。

与整体架构的协同

CORS 配置不是孤立环节。启用 HSTS 与 TLS 1.3 后，混合内容问题会直接导致跨域请求失败；对关键渲染路径的优化、图片懒加载等前端手段，也都建立在接口可正常跨域访问的前提上。把 CORS 视为 API 契约的一部分，在路由层与网关层保持策略一致，才能让 JSON API 在安全与可用之间取得平衡。
