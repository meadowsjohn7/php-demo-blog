## 一、Hreflang 输出的转义与白名单校验

在多语言站点中，Hreflang 标签通常由后端动态渲染。若直接拼接语言代码或 URL 参数，极易引入 XSS 风险。建议在 PHP 中建立语言代码白名单（如 `en`、`zh-CN`、`ja`），使用 `in_array()` 校验后再输出；对 `href` 属性统一调用 `htmlspecialchars($url, ENT_QUOTES, 'UTF-8')` 转义。对于 JSON API 返回的 hreflang 映射，同样应使用 `json_encode()` 并设置 `JSON_HEX_TAG | JSON_HEX_AMP` 标志，防止前端渲染时被注入。

## 二、协议一致性与重定向安全

Hreflang 要求所有语言版本使用绝对 URL，且协议、域名与 canonical 保持一致。实践中常见问题是 HTTP 与 HTTPS 混用，导致搜索引擎无法正确归组。建议在 Web 层强制 HSTS 并配合 TLS 1.3，同时在应用入口统一检测 `$_SERVER['HTTPS']`，将非安全请求 301 重定向到 HTTPS 版本。重定向目标必须来自预定义的语言域名映射表，避免开放重定向漏洞。对于过期语言路径，使用 301 迁移权重时需校验目标 URL 属于本站白名单。

## 三、动态路由与参数过滤

多语言路由常携带 `lang`、`region` 等参数。若直接用于拼接 hreflang 链接，攻击者可通过构造恶意参数诱导生成外部链接。建议在路由层对参数做严格过滤：语言代码仅允许字母与连字符，区域代码仅允许两位大写字母；对不合法参数返回 400 而非静默回退。若使用 JSON API 输出多语言配置，应在响应头设置 `Content-Type: application/json; charset=utf-8`，并禁止浏览器 MIME 嗅探。

## 四、监控、审计与性能兼顾

Hreflang 配置错误往往难以人工发现，建议在日志中记录每次生成的 hreflang 集合，定期比对 canonical 与 sitemap 中的语言版本是否一致。可结合 Nginx 的 Lua 模块对异常爬虫请求做限速，降低恶意扫描对 CPU 的消耗。对于离线预取场景，Service Worker 缓存的 hreflang 映射需带版本号，避免旧配置长期驻留 IndexedDB。性能方面，将 hreflang 映射表缓存在 Redis 中，可减少数据库查询，同时保证多节点部署下的一致性。

安全规范不是一次性配置，而是持续校验的过程。只有在输出、路由、重定向和监控各环节都建立约束，Hreflang 才能真正服务于多语言 SEO，而不是成为新的攻击面。
