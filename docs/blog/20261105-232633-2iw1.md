## 从单机 Cron 到可观测的调度层

在 PHP Demo Blog 这类轻量项目中，Cron 往往承担着清理临时文件、生成站点地图、同步缓存等后台工作。初期直接写一条 `* * * * * php /path/to/task.php` 看似简单，但随着任务增多，问题会集中暴露：任务之间互相争抢 CPU、日志散落各处、失败后无人知晓。优化的第一步不是引入复杂调度系统，而是把 Cron 当作一个需要观测的服务来对待。建议统一入口脚本，例如 `cron/runner.php`，由它根据参数分发到具体任务类，这样所有任务共享同一套初始化逻辑、日志句柄与异常处理，避免每个脚本重复造轮子。

## 用文件锁与超时控制避免任务堆叠

Cron 最典型的故障是上一次任务尚未结束，下一次已被触发，导致进程堆积。对 PHP 脚本而言，最轻量的方案是 `flock()`：在任务开始时对固定锁文件加非阻塞排他锁，获取失败即记录一条跳过日志并退出。锁文件建议放在 `/var/lock/` 或项目 `runtime/` 目录下，命名带上任务标识。同时为每个任务设置软超时，例如在脚本内记录开始时间，循环处理数据时定期检查是否超过阈值，超限则主动退出并标记为未完成，交由下一轮继续。对于必须串行执行的任务，还可以在 crontab 中使用 `flock -n /tmp/task.lock -c 'php ...'`，把互斥逻辑前移到调度层，脚本本身保持纯粹。

## 日志分级与静默失败的兜底

默认情况下 Cron 会把任务输出通过邮件发送，但多数服务器未配置 MTA，结果就是失败被静默吞掉。优化做法是显式重定向：`>> /var/log/cron/blog.log 2>&1`，并按天切割，避免单文件无限增长。日志内容应包含时间戳、任务名、退出码与关键计数，便于用 `grep` 或简单脚本做聚合。更进一步，可以在 runner 中捕获未处理异常，写入独立的错误日志，并在连续失败达到阈值时触发告警。告警不必复杂，调用一个内部 webhook 或写入告警表即可。对于 PHP Demo Blog 的 JSON API 场景，还可以让任务在结束时把执行结果写入一张 `cron_status` 表，后台页面直接读取展示，形成最简可用的可观测性。

## 分片调度与资源错峰

当任务数量上升，集中在整点触发会造成明显的负载尖峰。可以利用 Cron 的时间字段做错峰，例如把非实时任务分散到 `5,20,35,50` 等分钟位，避免 `0 * * * *` 扎堆。对于数据量较大的任务，按主键区间或哈希取模拆成多个分片，每个分片由独立 Cron 条目驱动，既缩短单次执行时间，也降低单点失败的影响面。同时留意系统层面的限制：检查 `/etc/cron.d/` 与用户 crontab 的加载顺序，确认环境变量（如 `PATH`、`PHP_BINARY`）在 Cron 上下文中可用，必要时在脚本内显式设置绝对路径。最后，定期用 `crontab -l` 与版本库中的调度清单做比对，防止手工修改导致配置漂移。

以上方案不依赖额外组件，全部基于 Linux 自带能力与 PHP 原生函数，适合在轻量项目中逐步落地。
