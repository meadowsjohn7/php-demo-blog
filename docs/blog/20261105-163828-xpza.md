## 为什么 CORS 配置容易出安全问题

CORS 本质是浏览器的一种放宽同源策略的机制，服务端通过响应头声明哪些源可以跨域读取资源。很多项目为了快速联调，直接返回 `Access-Control-Allow-Origin: *`，这在公开只读 API 中尚可接受，但一旦接口涉及用户数据或写操作，通配符就会把跨域能力无条件开放给任意站点。更危险的是同时设置 `Access-Control-Allow-Credentials: true` 与通配符源，浏览器会直接拒绝这种组合，而开发者往往转而动态回显请求的 Origin，若未做白名单校验，等于把凭据接口暴露给所有来源。

在 PHP Demo Blog 这类轻量路由项目中，API 入口通常集中在一个前端控制器里，正好适合统一处理 CORS。安全规范的第一条是：默认不发送任何 CORS 头，只有命中显式白名单的源才追加允许头。白名单应写成配置数组，而不是从请求头直接取值。

## 精确白名单与预检请求处理

实现上，先读取 `$_SERVER['HTTP_ORIGIN']`，与配置中的源列表做严格字符串比较（区分协议、域名、端口），命中后才输出 `Access-Control-Allow-Origin` 为该源，并追加 `Vary: Origin`，避免缓存层把某个源的响应复用给其他源。对于非简单请求，浏览器会先发 `OPTIONS` 预检，服务端需返回允许的方法与请求头，并用 `Access-Control-Max-Age` 控制预检缓存时间，建议设为 600 秒左右，既减少预检往返，又能在策略调整后较快生效。

允许的方法应显式列出，例如 `GET, POST, PUT, DELETE`，不要回显 `Access-Control-Request-Method`。允许的请求头同样应白名单化，常见为 `Content-Type, Authorization, X-Requested-With`。若接口需要携带 Cookie 或 Authorization 凭据，则必须设置 `Access-Control-Allow-Credentials: true`，并且此时 `Allow-Origin` 绝不能是通配符，前端也需要设置 `credentials: 'include'`。

## 与认证、缓存和日志的配合

CORS 不是认证机制，它只控制浏览器是否把响应交给脚本。因此白名单之外，接口仍需独立的会话或令牌校验。在负载均衡环境下，若使用分布式 Redis 集群存储 Session 状态，可以保证跨节点请求的用户状态一致，但这与 CORS 是两件事，不能互相替代。对于预检响应，应避免携带业务 Cookie，并设置较短的缓存头；对于实际响应，若包含用户相关数据，应加上 `Cache-Control: private` 或 `no-store`，防止中间缓存串源。

日志方面，建议记录被拒绝的 Origin，便于发现配置遗漏或恶意探测。若项目同时启用了 HSTS 与 TLS 1.3，跨域请求的传输层安全已有保障，但 CORS 策略仍须逐条审查。一个可执行的检查清单是：是否存在通配符源、是否动态回显未校验的 Origin、是否缺少 Vary 头、凭据模式是否与源白名单匹配、预检缓存是否过长。把这些检查纳入代码评审，CORS 配置才能真正成为安全边界而非漏洞入口。
