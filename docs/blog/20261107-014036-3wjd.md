## 签名算法与密钥管理

JWT 的安全根基在于签名验证。PHP 项目应显式指定算法（如 HS256 或 RS256），禁止接受客户端传入的 `alg` 头，避免算法混淆攻击。使用 `firebase/php-jwt` 等成熟库时，在 `decode` 调用中传入允许的算法数组，而不是依赖默认值。密钥必须足够长且随机，HS256 密钥建议不少于 32 字节，RS256 则使用 2048 位以上 RSA 密钥对，私钥仅存于服务端环境变量或密钥管理服务中，绝不写入代码仓库。

密钥轮换需要平滑过渡：可在 JWT 头部增加 `kid` 字段，服务端维护多版本密钥映射，验证时按 `kid` 选择对应公钥或共享密钥。旧密钥在令牌最大有效期过后再下线，避免已签发令牌批量失效。

## 令牌生命周期与声明校验

JWT 一旦签发便无法主动撤销，因此必须控制有效期。访问令牌建议 15 至 30 分钟，配合刷新令牌实现续期。刷新令牌应存储于服务端（如 Redis），并绑定用户代理指纹或 IP 段，支持单次使用后轮换。验证时除签名外，必须校验 `exp`、`nbf`、`iat` 三个时间声明，并检查 `iss` 与 `aud` 是否与预期一致，防止令牌被跨服务重放。

自定义声明中不要放入敏感信息，JWT 载荷仅做 Base64URL 编码，任何持有者均可解码。用户角色、权限范围可放入 `scope` 声明，但服务端仍需根据业务状态做二次鉴权，不能仅凭令牌内容授权。

## 传输层与客户端存储加固

令牌在传输中必须走 TLS 1.3 并启用 HSTS，防止降级与中间人窃取。Web 场景下，访问令牌推荐存入 `HttpOnly`、`Secure`、`SameSite=Strict` 的 Cookie，避免 XSS 直接读取；若使用 Authorization 头，则需配合严格的 CSP 与输入过滤降低 XSS 风险。刷新令牌应设置更严格的路径限制，仅发送至刷新端点。

对于跨域 API，明确配置 CORS 白名单，禁止 `Access-Control-Allow-Origin: *` 与凭证模式共存。服务端可结合 CSRF 令牌对使用 Cookie 的刷新接口做双重校验，形成纵深防御。

## 常见攻击面与监控

算法混淆、弱密钥爆破、令牌重放是 JWT 的三大典型风险。除算法白名单外，应对登录与刷新接口做速率限制，记录失败次数并触发告警。对已签发令牌建立黑名单机制，在用户登出或密码变更时，将令牌 `jti` 写入 Redis 并设置与剩余有效期一致的 TTL，验证时快速比对。

日志中不要完整打印 JWT，可记录 `jti` 与用户标识用于审计。定期轮换密钥、审查依赖库版本、监控异常签发频率，才能让 JWT 认证在长期运行中保持可控。
