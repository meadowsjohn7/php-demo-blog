## 为什么内联 Critical CSS 需要安全规范

内联关键 CSS 是优化 LCP 的常用手段：将首屏渲染所需的样式直接写入 `<style>` 标签，避免额外请求阻塞渲染。但在 PHP 项目中，如果内联内容来自动态拼接或第三方提取工具，就可能引入样式注入、选择器污染甚至 XSS 风险。安全规范的核心是：内联的 CSS 必须是可信的、可审计的、与 CSP 兼容的。

## 提取与内联的边界控制

首先，Critical CSS 的提取应在构建阶段完成，而非运行时。使用 Penthouse 或 Critical 等工具时，应针对固定模板生成静态 CSS 文件，再由 PHP 读取并内联。内联前需做白名单校验：只允许 `style` 标签内出现合法的 CSS 语法，禁止 `</style>`、`<script>` 等闭合标签片段。PHP 侧可用正则或 CSS 解析器过滤，但更稳妥的做法是只内联构建产物，不接受用户输入。

其次，内联范围要克制。只内联首屏可见区域的选择器，非核心样式通过 `<link rel="preload">` 异步加载。内联体积建议控制在 14KB 以内，避免 HTML 膨胀影响 TTFB。对于多主题或多语言站点，可按路由生成不同的 Critical CSS 文件，通过配置映射加载，而不是在模板中动态计算。

## CSP 兼容与样式隔离

内联 `<style>` 会与 Content-Security-Policy 的 `style-src` 冲突。若使用 `style-src 'self'`，内联样式会被拦截。解决方案是使用 nonce：在 PHP 响应头中生成随机 nonce，并写入 CSP 头与 `<style nonce="...">` 属性。nonce 必须每次请求随机生成，且不能出现在缓存页面中。若使用静态缓存，可将 nonce 替换为 hash：在构建时计算内联 CSS 的 SHA-256，并写入 `style-src 'sha256-...'`。

此外，内联样式应避免使用 `!important` 和全局选择器，防止与后续加载的样式表冲突。建议为内联样式添加作用域前缀，如 `.critical-`，并在非核心 CSS 加载后移除或覆盖。

## 自动化校验与回退

在 CI 流程中加入校验步骤：检查内联 CSS 是否包含非法标签、是否超过体积阈值、nonce 或 hash 是否与 CSP 头匹配。PHP 项目可在单元测试中模拟响应，断言 `<style>` 标签存在且 nonce 有效。同时保留回退策略：当内联 CSS 加载失败或 CSP 校验不通过时，回退到外部样式表链接，确保页面仍可渲染。

最后，定期审计内联内容。将 Critical CSS 文件纳入版本控制，每次变更都经过代码评审，避免因模板改动引入不可控样式。安全规范不是一次性配置，而是持续集成的组成部分。
