## 从 TCP 到 QUIC：HTTP/3 的传输层重构

HTTP/3 的核心变化在于将传输层从 TCP 迁移到基于 UDP 的 QUIC 协议。QUIC 在用户态实现了可靠传输、拥塞控制与加密握手，将 TLS 1.3 集成到连接建立过程中。这意味着首次连接只需 1-RTT，会话恢复时可实现 0-RTT，显著降低首字节响应时间（TTFB）。对于 PHP Demo Blog 这类以 JSON API 为主的轻量项目，TTFB 的改善直接体现在接口响应速度上。

在架构上，QUIC 使用连接 ID 而非四元组标识连接，因此支持连接迁移。当移动端用户从 Wi-Fi 切换到蜂窝网络时，连接无需重建，正在传输的请求不会中断。这一特性对需要保持长连接或频繁轮询的 API 场景尤为友好。

## 多路复用与队头阻塞的消除

HTTP/2 虽然引入了多路复用，但底层仍依赖 TCP，一旦发生丢包，所有流都会因 TCP 的队头阻塞而等待重传。HTTP/3 在 QUIC 层面为每个流独立处理丢失与重传，单个流的问题不会波及其他流。对于博客页面中并行加载的 CSS、JS 与图片资源，这种独立性意味着更稳定的加载曲线。

在 PHP 项目中，服务端通常由 Nginx 或 Caddy 终止 HTTP/3 连接，再将请求以 HTTP/1.1 或 FastCGI 形式转发给 PHP-FPM。因此 PHP 代码本身无需感知 HTTP/3，但需要关注响应头与压缩策略。例如启用 Brotli 压缩可进一步缩小 JSON 与 HTML 体积，与 HTTP/3 的低延迟特性形成互补。

## 与 TLS 1.3、HSTS 的协同配置

HTTP/3 强制使用 TLS 1.3，这要求服务端证书与加密套件配置同步升级。建议同时启用 HSTS 策略，强制客户端使用 HTTPS，并配合 `includeSubDomains` 与合理的 `max-age`。在 Nginx 中，可通过 `add_header Strict-Transport-Security` 指令下发。需要注意的是，HSTS 一旦生效便难以回退，应先在测试环境验证。

对于 API 响应，建议设置 `Alt-Svc` 头告知客户端 HTTP/3 端点，例如 `Alt-Svc: h3=":443"; ma=86400`。这样客户端在首次通过 HTTP/2 访问后，后续请求可升级到 HTTP/3。PHP 端可通过框架的响应头中间件统一注入，避免在每个控制器中重复设置。

## 落地建议与监控

在 PHP Demo Blog 中落地 HTTP/3，可按以下步骤推进：首先确认服务端软件支持 QUIC（如 Nginx 1.25+ 配合相应模块，或 Caddy 默认支持）；其次配置 TLS 1.3 与 Brotli；然后通过 `Alt-Svc` 头引导客户端升级；最后使用浏览器开发者工具或 `curl --http3` 验证协议协商结果。

监控方面，应关注 QUIC 连接的握手失败率、0-RTT 重放攻击防护以及 UDP 端口的防火墙策略。部分网络环境会限制 UDP 443 端口，此时客户端应能自动回退到 HTTP/2，因此保留 HTTP/2 监听是必要的过渡措施。通过持续观测与灰度发布，可以在保证稳定性的前提下享受 HTTP/3 带来的性能收益。
