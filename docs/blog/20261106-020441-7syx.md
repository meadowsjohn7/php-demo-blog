## 缓存穿透的成因与影响

缓存穿透指客户端请求的数据在缓存和数据库中均不存在，导致每次请求都穿透缓存直接落到数据库。在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，若对文章 ID 的查询未做防护，恶意请求不存在的 ID 会持续冲击 MySQL，造成连接数飙升甚至拖垮服务。其核心特征是「无效查询」而非「热点失效」，因此与缓存击穿、雪崩的应对思路不同。

常见诱因包括：攻击者构造随机 ID 扫描、爬虫抓取失效链接、业务逻辑误传空参数。若 API 对参数缺少类型与范围校验，例如 `/api/post?id=abc` 直接进入查询，穿透风险会进一步放大。

## 基础防护：空值缓存与参数校验

最直接的手段是空值缓存：当数据库查询结果为空时，仍向 Redis 写入一个短 TTL 的占位值（如 `__NULL__`），后续相同键的请求直接命中缓存返回。在 PHP 中可封装统一查询方法：先校验 ID 为正整数，再读缓存，未命中则查库，空结果写入 `post:null:{id}` 并设置 60 秒过期。

需注意两点：一是空值 TTL 不宜过长，避免数据后续被创建时出现不一致；二是写入空值前应确认查询本身无异常，防止把数据库故障误判为「不存在」。配合路由层对参数做白名单过滤，可拦截大部分随机扫描。

## 进阶方案：布隆过滤器与互斥锁

当无效键数量巨大时，空值缓存会占用大量内存。此时可在 Redis 之上引入布隆过滤器（如 RedisBloom 模块或 PHP 的 bloom filter 扩展），将所有合法文章 ID 预加载其中。请求到达时先判断 ID 是否可能存在，不存在则直接返回 404，避免查库。布隆过滤器有假阳性但无假阴性，适合作为前置拦截层。

对于合法但并发的热点键，可结合互斥锁：缓存未命中时用 `SET key value NX EX` 获取锁，仅允许一个请求回源，其余请求短暂等待后重试缓存。这能防止缓存失效瞬间的数据库冲击，与空值缓存形成互补。

## 与分布式架构的协同实践

在负载均衡环境下，若项目采用分布式 Redis 集群存储 Session 状态，缓存穿透防护也应纳入同一套治理体系：统一键命名规范、监控空值键比例、对异常高频 IP 在 Nginx 层做限流。同时，API 响应应保持 JSON 结构一致，空结果返回明确的 `code` 与 `message`，便于前端与爬虫正确解析。

防护策略需持续迭代：定期分析慢查询日志，识别穿透来源；对新增接口默认加入参数校验与空值缓存模板。将这些细节固化为开发规范，才能在流量波动时保持服务稳定。
