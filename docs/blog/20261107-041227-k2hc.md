## 反爬虫的本质：识别非人类请求

反爬虫对抗的核心不是封 IP，而是判断一个请求是否由自动化程序发出。底层原理可以拆成三个维度：请求指纹、行为特征与资源消耗。请求指纹包括 User-Agent、Accept-Language、TLS 握手特征（JA3）、HTTP/2 帧顺序等；行为特征包括访问频率、路径遍历顺序、页面停留时间与鼠标轨迹；资源消耗则体现在单位时间内对 CPU、数据库连接和带宽的占用。PHP 应用层能拿到的信息有限，因此真正的第一道防线应放在 Web 服务器层。

## 在 Nginx 层做动态拦截

利用 Nginx 的 Lua 模块（如 OpenResty）可以在请求进入 PHP-FPM 之前完成判定。典型做法是用 `ngx.shared.DICT` 维护一个滑动窗口计数器，按 IP 与 UA 组合统计最近 10 秒的请求数，超过阈值就写入动态黑名单并直接返回 403。相比静态 `deny` 列表，这种方式能随流量变化自动调整，且 Lua 运行在 Nginx worker 内，几乎不增加额外进程开销。配合 `limit_req_zone` 做漏桶限速，可以对突发爬取形成平滑压制。

## 应用层的信号采集与校验

PHP 侧适合做轻量补充：检查 `Referer` 是否来自站内、Cookie 中是否携带由服务端签发的会话令牌、表单是否带 CSRF token。对于 JSON API，可以要求请求头携带自定义字段并校验其签名，避免被简单脚本直接复用。需要注意的是，这些手段只能提高门槛，不能替代传输层防护。配置 HSTS 并启用 TLS 1.3，能减少中间人篡改请求头的空间，也让基于明文协议的简单抓取更难伪装。

## 对抗的边界与成本权衡

反爬虫不是越严越好。过度拦截会误伤正常用户与搜索引擎爬虫，因此需要为已知爬虫提供白名单，并保留可观测的日志用于回溯。实践中，把拦截规则、限速阈值和黑名单过期时间做成可配置项，比写死在代码里更利于迭代。持续观察拦截命中率与误杀率，才能让防护策略在安全与可用之间保持平衡。
