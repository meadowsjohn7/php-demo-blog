## 分层防御的核心思想

SQL 注入防御不能依赖单一手段，而应构建从代码层到基础设施层的纵深体系。在 PHP Demo Blog 这类轻量项目中，常见误区是仅靠 addslashes 或简单过滤，这无法应对编码绕过与二次注入。深度防御要求每一层都假设上一层可能失效，从而形成互补。

## 代码层：参数化查询与输入验证

首要防线是彻底使用预处理语句。PDO 的 prepare/execute 将 SQL 结构与数据分离，从根本上消除拼接风险。例如：$stmt = $pdo->prepare('SELECT * FROM posts WHERE id = ?'); $stmt->execute([$id]); 避免任何字符串拼接。同时，对输入进行类型约束：整数用 filter_var 验证，字符串限制长度与字符集。白名单校验排序字段与表名，因为参数化无法覆盖标识符。ORM 如 ThinkPHP 的 Db::name() 配合绑定参数也能安全操作，但需注意 where 条件中不使用原生表达式拼接用户输入。

## 架构层：最小权限与错误处理

数据库账户应遵循最小权限原则：Web 应用仅授予 SELECT、INSERT、UPDATE、DELETE，禁用 FILE、DROP 等高风险权限。生产环境关闭详细错误回显，统一捕获异常并记录到日志，避免攻击者通过报错信息探测结构。使用独立数据库用户，不同模块隔离权限。连接层强制使用 TLS，防止中间人窃听。

## 运行时防护：WAF 与监控告警

在 Web 服务器前部署 WAF（如 ModSecurity 配合 OWASP CRS），可拦截常见注入模式。但 WAF 规则需定期更新，避免误杀。应用层记录所有 SQL 执行耗时与异常查询，设置阈值告警。对高频失败登录与异常参数进行限流。结合 Redis 存储会话时，确保会话 ID 不可预测，防止会话固定攻击。

## 持续验证与代码审计

将安全测试纳入 CI 流程，使用静态分析工具扫描拼接 SQL 的代码模式。定期进行渗透测试，模拟注入攻击验证防御有效性。代码评审时重点检查动态 SQL 构建点。通过日志分析发现潜在探测行为，及时调整规则。深度防御是持续过程，而非一次性配置。
