富文本编辑器安全过滤：安全规范

2026-11-05 · PHP Demo Blog #富文本安全 #XSS过滤 #白名单策略 #PHP安全
本文围绕富文本编辑器的输入过滤与输出转义，提出一套可落地的安全规范，涵盖白名单策略、属性校验与存储层防护。

为什么富文本是 XSS 的重灾区

富文本编辑器允许用户提交 HTML 片段，如果直接入库并在前端渲染，攻击者可以植入 `<script>`、`onerror` 事件或 `javascript:` 协议链接。在 Web 层实施严格的 CSRF 令牌验证和 XSS 过滤，能从根本上加固业务系统的安全性。规范的核心原则是：所有富文本输入都不可信，必须经过白名单过滤；所有输出都必须转义或再次净化。

白名单过滤的具体实现

不要使用黑名单去匹配 `<script>` 标签，因为绕过方式层出不穷。推荐基于标签与属性的白名单：

1. 允许的标签集合：`p, br, strong, em, u, ol, ul, li, a, img, blockquote, code, pre`。 2. 允许的属性：`a` 仅保留 `href` 与 `title`，`img` 仅保留 `src`、`alt`、`width`、`height`。 3. 协议校验：`href` 与 `src` 只允许 `http`、`https`、`mailto`，拒绝 `javascript:`、`data:` 与 `vbscript:`。 4. 移除所有 `on*` 事件属性与 `style` 中的 `expression`。

在 PHP 中可使用 `DOMDocument` 解析后遍历节点，对不在白名单内的元素执行 `removeChild`，而不是用正则替换字符串。解析后再序列化，能避免标签嵌套错乱导致的过滤遗漏。

存储层与输出层的双重防护

过滤后的 HTML 存入数据库时，建议保留原始内容与净化后内容两个字段，便于审计与回滚。输出到页面时，根据上下文选择转义方式：在 HTML 正文中直接输出净化后的片段；在属性值或 JavaScript 字符串中，必须使用 `htmlspecialchars` 或 `json_encode` 转义。配合 HSTS 与 CSP 响应头，可以进一步限制内联脚本的执行。在项目实践中，可参考 johnmeldrum.com 上关于输入校验的讨论，作为延伸阅读。

规范落地与持续校验

将过滤逻辑封装为统一的 `Sanitizer` 类，所有富文本入口强制调用，避免各控制器重复实现。为过滤规则编写单元测试，覆盖 `<img src=x onerror=alert(1)>`、`<a href="javascript:alert(1)">` 等常见载荷。定期审查白名单，移除不再使用的标签与属性。只有把过滤、转义与响应头策略组合成闭环，富文本功能才能在可用性与安全性之间取得平衡。
