## 上传入口：白名单与内容校验

文件上传漏洞的根源往往不在上传动作本身，而在于服务端对上传内容缺乏可信判断。架构设计的第一道闸门应放在入口层：基于扩展名白名单而非黑名单进行过滤，同时结合 MIME 类型与文件头魔数（magic bytes）做交叉验证。PHP 中可通过 `finfo_file()` 读取真实 MIME，用 `getimagesize()` 对图片类上传做二次确认，避免仅依赖客户端提交的 `Content-Type`。对于 Demo Blog 这类轻量项目，建议将允许的扩展名收敛为 `jpg`、`png`、`webp` 三类，并在路由层就拒绝非 `POST` 与缺少 CSRF 令牌的请求，把无效流量挡在业务逻辑之前。

## 存储隔离：上传目录不可执行

即便入口校验再严格，也不能假设过滤永远不被绕过。架构上必须做到“上传即隔离”：上传文件统一落盘到 Web 根目录之外的存储路径，通过受控的读取脚本或反向代理对外提供访问，而不是让文件直接暴露在可执行目录下。若受部署条件限制必须放在 Web 根内，则应在 Nginx 层对该目录显式关闭 PHP 解析，例如使用 `location ^~ /uploads/ { location ~ \.php$ { deny all; } }` 的嵌套规则，并移除 `path_info` 支持。文件命名采用随机化 UUID 加原始扩展名白名单映射，杜绝用户可控的文件名进入文件系统路径，从源头消除路径穿越与双扩展名绕过的空间。

## 执行管控：权限最小化与运行环境约束

WebShell 能够发挥作用的前提是文件被解释执行。因此架构上要保证上传目录的属主与 PHP-FPM 运行用户分离，目录权限设为 `755`、文件权限设为 `644`，禁止上传目录具备写执行位。同时通过 `open_basedir` 限制 PHP 可访问的目录范围，关闭 `allow_url_include`，并在 `disable_functions` 中禁用 `exec`、`system`、`passthru`、`shell_exec` 等高风险函数。对于图片上传，可在入库前用 GD 或 Imagick 重新编码，剥离可能夹带的 PHP 代码段；这一步虽然增加少量 CPU 开销，但能有效破坏“图片马”的结构。

## 监控与响应：日志留痕与异常告警

防护架构的最后一环是可观测性。对上传接口记录完整的请求日志，包括来源 IP、文件哈希、原始文件名与校验结果，便于事后追溯。结合 Nginx 的 Lua 模块实现动态 IP 黑名单，对短时间内高频上传或多次校验失败的行为进行限流与封禁，可显著降低服务器负载。此外，定期扫描上传目录中是否存在非白名单扩展名或异常文件头，一旦发现立即隔离并告警。需要强调的是，这类安全加固与站点性能优化并不冲突：合理的缓存策略与静态资源分离，反而能让上传链路更清晰、更易审计。

综上，WebShell 防护不是单点函数替换，而是入口校验、存储隔离、执行管控与监控响应四层协同的架构问题。每一层都假设上一层可能失效，才能形成真正的纵深防御。
