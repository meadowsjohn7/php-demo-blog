## TLS 握手与证书链验证

HTTPS 的本质是在 TCP 之上叠加 TLS 层，用非对称加密完成密钥协商，再用对称加密传输应用数据。客户端发起 ClientHello 后，服务器返回证书链与 ServerHello，双方基于 ECDHE 等算法协商出会话密钥。证书链的验证是信任建立的起点：浏览器从服务器证书出发，逐级向上验证中间证书与根证书的签名，同时校验证书有效期、域名匹配（SAN 扩展）以及吊销状态（OCSP 或 CRL）。在 PHP 项目中，如果使用 cURL 调用外部 API，应显式设置 CURLOPT_SSL_VERIFYPEER 与 CURLOPT_SSL_VERIFYHOST 为 true，并指定 CA 证书包路径，避免因默认配置差异导致验证被跳过。

## 证书类型与 Nginx 配置要点

证书按验证级别分为 DV、OV、EV 三类，DV 仅验证域名控制权，适合轻量 API 与博客项目；OV 与 EV 需要核验组织信息，成本更高。配置时，将完整证书链（服务器证书加中间证书）合并写入同一文件，私钥单独存放并设置 600 权限。Nginx 中通过 ssl_certificate 与 ssl_certificate_key 指定路径，协议版本建议只保留 TLSv1.2 与 TLSv1.3，密码套件优先选择 AEAD 类算法。启用 OCSP Stapling 可以减少客户端单独查询吊销状态的往返，配置 ssl_stapling on 并指定可信证书链即可。对于 PHP Demo Blog 这类项目，证书可通过 Let's Encrypt 的 ACME 客户端自动续期，配合 cron 定时任务与 Nginx reload 完成无感更新。

## HSTS 策略与安全响应头

HSTS 通过 Strict-Transport-Security 响应头告知浏览器在指定时间内强制使用 HTTPS 访问，从而阻断降级攻击与 SSL 剥离。首次部署时建议先用较短的 max-age（如 300 秒）观察，确认全站 HTTPS 无混合内容后再逐步提升到一年，并视情况加入 includeSubDomains 与 preload。需要强调的是，HSTS 一旦下发便难以回退，配置前必须确保所有子域名均已支持 HTTPS。除 HSTS 外，还应配合 Content-Security-Policy、X-Content-Type-Options 等响应头，形成纵深防御。在 PHP 层，可通过 header() 函数统一输出这些头，或在 Nginx 的 add_header 指令中集中管理，避免遗漏。

## 性能与合规的平衡

TLS 1.3 将握手往返从两次缩减为一次，并支持 0-RTT 恢复，对首字节时间有直接改善。启用会话复用（ssl_session_cache 与 ssl_session_tickets）能进一步降低重复连接的开销。在应用层，结合 HTTP/2 或 HTTP/3 的多路复用与 Brotli 压缩，可以抵消加密带来的少量 CPU 成本。证书配置不是一次性工作，应纳入监控：定期检查到期时间、协议版本分布与握手失败率，将安全策略的变更与性能指标一同观测，才能让 HTTPS 配置在安全与速度之间保持可持续的平衡。
