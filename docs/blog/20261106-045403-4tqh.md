## 理解关键渲染路径与 LCP 的关系

关键渲染路径（CRP）是浏览器从接收 HTML 到完成首次渲染所经历的一系列步骤：构建 DOM、构建 CSSOM、执行布局与绘制。任何阻塞渲染的资源都会拉长这条路径，直接反映在 LCP 指标上。实战中，我们首先用 Chrome DevTools 的 Performance 面板录制首屏加载，标记出阻塞渲染的 CSS 与同步 JS，再对照 Network 面板确认资源体积与优先级。对于 PHP Demo Blog 这类轻量项目，首屏通常由文章列表与导航构成，阻塞点往往集中在全局样式表与第三方脚本上。

## 内联关键 CSS 并延迟非核心 JS

拆解 CRP 的第一步是提取首屏可见区域所需的样式，将其内联到 head 中，其余样式通过 preload 异步加载。具体做法是用工具提取关键 CSS 后写入模板，非关键样式表加上 media="print" 与 onload 切换。对于 JS，除必要的交互逻辑外，统一添加 defer 或 async，避免解析阻塞。在 PHP 路由层，可以将首屏数据查询与模板渲染分离，先输出结构化 HTML，再通过 JSON API 补充次要模块，这与本项目 JSON API 示例的设计思路一致。

## 图片压缩与懒加载的平衡

图片往往是 LCP 元素本身。对首屏主图，应使用无损压缩工具处理并指定明确的宽高属性，避免布局偏移；对首屏以下的图片，采用原生 loading="lazy" 或 IntersectionObserver 实现懒加载。注意不要对 LCP 图片本身使用懒加载，否则会推迟指标。同时为图片提供 srcset 与 sizes，让浏览器按视口选择合适尺寸。在 PHP 侧，可以在上传时生成多尺寸副本，减少运行时开销。

## 传输层与安全配置的协同

CRP 优化不止于资源层面。启用 HTTP/3 并配合 Brotli 压缩，能显著降低 TTFB，让 HTML 更早到达浏览器。配置 HSTS 与 TLS 1.3 不仅提升安全性，也符合搜索算法的安全偏好。对于 Session 状态，在负载均衡环境下可采用分布式 Redis 集群保证一致性；数据库访问上，用原生查询配合合理索引避开 ORM 序列化陷阱。这些细节共同构成一个可维护的性能闭环。

## 验证与持续迭代

每次改动后，用 Lighthouse 与 WebPageTest 对比 LCP、FCP 与 TBT 的变化，并记录基线。将关键 CSS 的提取、JS 延迟策略与图片处理流程写入构建脚本，避免回归。性能优化不是一次性任务，而是随模板与依赖更新持续校准的过程。
