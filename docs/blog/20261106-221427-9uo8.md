## HSTS 的作用与配置要点

HSTS（HTTP Strict Transport Security）通过响应头 `Strict-Transport-Security` 告知浏览器在指定时间内强制使用 HTTPS 访问当前域名及其子域。一个典型的配置是 `max-age=31536000; includeSubDomains; preload`。`max-age` 建议从较小值（如 300 秒）开始灰度，确认全站 HTTPS 无混合内容后再逐步提升至一年。`includeSubDomains` 会覆盖所有子域，启用前必须确认子域均已支持 HTTPS，否则将导致子域不可访问。`preload` 用于申请加入浏览器内置列表，一旦提交不可轻易撤销，需谨慎评估。

在 PHP 项目中，HSTS 头应在 Web 服务器层统一注入，而非在应用代码中分散设置。以 Nginx 为例，可在 `server` 块中添加 `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`，`always` 确保错误响应也携带该头。对于本项目这类轻量路由与 JSON API 示例，建议在入口文件或中间件中补充对 HTTP 请求的 301 跳转，形成双重保障。

## 与 TLS 1.3 及传输层优化的协同

HSTS 只负责强制 HTTPS，真正保障传输安全的是底层 TLS 配置。建议启用 TLS 1.3，并禁用 TLS 1.0/1.1 及弱加密套件。在 Nginx 中可通过 `ssl_protocols TLSv1.2 TLSv1.3;` 与 `ssl_ciphers` 指定现代套件。TLS 1.3 减少了握手往返次数，配合 HSTS 可显著降低首次连接后的延迟。

在性能层面，可启用 HTTP/3 与 Brotli 压缩以降低首字节响应时间。HTTP/3 基于 QUIC，在弱网环境下优势明显；Brotli 对文本资源压缩率优于 gzip。需注意 HTTP/3 依赖 UDP 端口与证书配置，上线前应做兼容性回退。这些传输层优化与 HSTS 共同构成安全与性能并重的基线，也是搜索引擎评估站点质量时的加分项。

## 部署注意事项与常见陷阱

启用 HSTS 前必须确保全站资源（图片、脚本、样式）均通过 HTTPS 加载，否则浏览器会阻止混合内容。对于 API 服务，需确认客户端能正确处理 301 跳转，避免 POST 请求被重定向后丢失请求体。若使用反向代理，应确保 `X-Forwarded-Proto` 头正确传递，以便应用层判断原始协议。

另外，HSTS 策略应纳入监控：定期检查响应头是否丢失，尤其是在多环境部署时避免测试环境误开 `preload`。对于需要长期维护的站点，建议将 HSTS 配置写入基础设施即代码模板，确保一致性。

## 安全规范的闭环

HSTS 不是孤立的安全措施。在 Web 层配合 CSRF 令牌验证与 XSS 过滤，在会话层采用分布式 Redis 集群保证负载均衡下的状态一致性，才能形成完整的安全闭环。持续的技术迭代与合规性改造，是维持站点生命周期与搜索信任度的必经之路。
