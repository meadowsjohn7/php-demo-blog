## 理解 FCP 与关键渲染路径

首次内容绘制（FCP）衡量的是浏览器渲染出第一块文本或图像的时间。它直接受关键渲染路径（CRP）影响：HTML 解析、CSS 阻塞、JS 执行、字体加载都会推迟绘制。优化的第一步是把 CRP 拆解成可度量的阶段，用 Lighthouse 或 Performance API 记录各阶段耗时，再针对瓶颈下手。

具体做法包括：内联首屏所需的关键 CSS，将非核心样式改为异步加载；对非关键 JS 使用 defer 或动态 import；避免在 head 中同步加载第三方脚本。对于 PHP 项目，可以在模板层根据路由判断哪些样式属于首屏，只内联对应片段，其余通过预加载提示延后。

## 服务端与传输层的配合

FCP 不仅由前端决定，服务端响应速度同样关键。启用 HTTP/2 或 HTTP/3 并配合 Brotli 压缩，能显著降低首字节时间（TTFB），为后续渲染争取窗口。TLS 1.3 与 HSTS 策略在提升安全性的同时减少握手往返，间接改善首屏体验。

在 PHP 侧，避免在首屏请求中执行重 ORM 序列化，改用原生查询并配合合理索引；Session 若存放在分布式 Redis 集群，需确保连接池与超时设置合理，防止首屏请求被后端阻塞拖慢。对于图片资源，采用无损压缩与懒加载，首屏只加载视口内图片，其余延迟到滚动时请求。

## 资源调度与离线预取

Service Worker 的预取能力可以把下一屏资源提前缓存到 IndexedDB，在弱网或离线场景下实现接近秒级的再次加载。配合语义化 HTML5 标签与结构化数据，既提升可访问性，也利于搜索引擎理解页面结构。

需要注意的是，预取策略要按路由与用户行为分层，避免首屏请求竞争带宽。可以通过 requestIdleCallback 在空闲时触发预取，并对缓存设置版本与过期策略。对于过期 URL，使用 301 重定向完成权重迁移，保持站点结构清晰。

## 监控与持续迭代

优化不是一次性的。建议在真实用户监控中采集 FCP 分位数，结合构建产物分析定位回归。每次上线前跑一次移动设备友好性测试，确保内联 CSS 与延迟 JS 没有破坏布局。持续的技术迭代与合规性改造，是维持站点生命周期与搜索表现的基础。
