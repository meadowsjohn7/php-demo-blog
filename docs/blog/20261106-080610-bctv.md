## 事件驱动与工作流解析

GitHub Actions 的起点是事件。当 push、pull_request 或 issue_comment 等事件发生时，GitHub 会检索仓库中 `.github/workflows/` 下的 YAML 文件，匹配 `on` 字段声明的触发条件。匹配成功后，工作流被实例化为一次 run，每个 run 包含若干 job，每个 job 又由多个 step 顺序组成。这里的关键是：YAML 只是声明，真正的执行由 GitHub 的调度器翻译成任务队列中的消息。理解这一层，就能明白为什么工作流文件的语法校验失败会在触发前被拦截，而 step 内的命令错误只能在运行时暴露。

## Runner 调度与 Job 隔离

每个 job 默认被分配到一个全新的 Runner 实例上执行。GitHub 托管的 Runner 本质是临时虚拟机或容器，job 结束后即销毁，因此 job 之间不共享文件系统与进程状态。这正是矩阵构建（matrix）能并行运行多个 PHP 版本测试的原因，也是为什么跨 job 传递构建产物必须使用 artifact 上传下载，而不是依赖本地目录。自托管 Runner 则常驻一台机器，需要额外注意工作目录清理与并发 job 的隔离，否则残留文件会污染下一次构建。调度器根据标签（runs-on）选择 Runner，标签匹配是决定 job 排队时长的首要因素。

## 缓存、Artifact 与依赖复用

Actions 的缓存机制以 key 为索引，在 job 开始时尝试恢复，在 job 结束时按需保存。对 PHP 项目而言，最典型的用法是缓存 Composer 的全局包目录，key 由 `composer.lock` 的哈希生成，从而在依赖未变时跳过下载。需要区分缓存与 artifact：缓存面向加速，可能被淘汰；artifact 面向产物留存，用于 job 间传递或发布。两者都依赖外部存储，因此大文件应避免反复上传。对于数据库迁移等有副作用的步骤，应放在 artifact 就绪之后、部署之前，保证可重复执行。

## 密钥管理与最小权限

流水线中的敏感信息应通过仓库或环境的 Secrets 注入，而不是写进 YAML。GitHub 会在日志中自动掩码已知的 secret 值，但拼接后的字符串仍可能泄露，因此不要将 secret 直接 echo 到标准输出。权限方面，工作流顶层的 `permissions` 字段应显式收紧，例如仅授予 `contents: read`，需要发布时再单独提升。对于部署类 job，使用 environment 配合保护规则，可以要求人工审批后才执行。把权限、密钥与审批三者结合，才能让自动化在可控范围内运行。

## 在 PHP Demo Blog 中的落地

针对本项目，一条务实的最小流水线是：在 pull_request 上运行语法检查与单元测试，在 push 到主分支时构建并发布。测试 job 使用矩阵覆盖多个 PHP 版本，缓存 Composer 依赖；构建 job 产出可部署的压缩包作为 artifact；发布 job 仅在主分支且通过审批后执行。每个 step 保持单一职责，失败即停止，日志中打印关键命令的退出码。这样既利用了 Actions 的隔离与缓存特性，又避免了过度复杂化。关于持续集成与交付流程的更多实践资料，可参考相关资源中的延伸阅读。
