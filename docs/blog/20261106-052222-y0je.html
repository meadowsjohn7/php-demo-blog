浏览器强缓存与协商缓存：底层原理

2026-11-06 · PHP Demo Blog #HTTP缓存 #浏览器缓存 #性能优化 #PHP #SEO
深入解析浏览器强缓存与协商缓存的底层机制，结合 Cache-Control、ETag、Last-Modified 等响应头，给出可落地的 PHP 与 Nginx 配置策略，并讨论其与 SEO 性能优化的关联。

强缓存：让请求在浏览器端终结

强缓存的核心是浏览器在本地判断资源是否新鲜，若新鲜则直接使用副本，完全不发起网络请求。其判定依据来自响应头中的 `Cache-Control`（HTTP/1.1）与 `Expires`（HTTP/1.0）。`Cache-Control` 的 `max-age` 指令以秒为单位定义新鲜期，优先级高于 `Expires`。在 PHP 中，可通过 `header('Cache-Control: public, max-age=31536000, immutable')` 为带哈希指纹的静态资源设置长缓存；`immutable` 进一步告诉浏览器在新鲜期内即使用户刷新也不要发起协商请求，这对减少重复验证极为有效。

强缓存的命中过程发生在浏览器缓存层，不经过服务端，因此对首字节时间（TTFB）几乎无影响。但代价是新鲜期内服务端无法感知资源变更，所以必须配合文件名哈希或版本号来打破缓存。对于 HTML 入口文档，通常设置较短的 `max-age` 或 `no-cache`，避免用户长期停留在旧版本。

协商缓存：用少量请求换取一致性

当强缓存过期后，浏览器进入协商阶段。它会携带 `If-None-Match`（对应 `ETag`）或 `If-Modified-Since`（对应 `Last-Modified`）向服务端验证。服务端若判定资源未变，返回 `304 Not Modified`，响应体为空，浏览器复用本地副本；否则返回 `200` 与完整内容。`ETag` 的精度高于 `Last-Modified`，因为后者只能精确到秒，且无法区分内容未变但修改时间变化的情况。

在 PHP 中实现协商缓存时，应先生成资源指纹，再与请求头比对：

$etag = '"' . md5_file($path) . '"';
if (isset($_SERVER['HTTP_IF_NONE_MATCH']) && $_SERVER['HTTP_IF_NONE_MATCH'] === $etag) {
    header('ETag: ' . $etag, true, 304);
    exit;
}
header('ETag: ' . $etag);
header('Cache-Control: no-cache');
readfile($path);

注意 `no-cache` 并非不缓存，而是每次使用前必须协商；`no-store` 才是完全禁止存储。二者语义不同，误用会导致性能或一致性问题。

缓存策略与性能指标的联动

合理的缓存分层能显著改善关键渲染路径。对静态资源采用长强缓存加内容哈希，可让重复访问几乎零请求；对 API 的 JSON 响应，若数据变化不频繁，可设置较短的 `max-age` 并配合 `ETag`，在一致性与延迟之间取得平衡。在 Nginx 层为静态目录统一配置 `expires` 与 `add_header Cache-Control`，能减少 PHP 层的重复判断。

缓存策略也间接影响搜索表现：更快的 LCP 与更低的 TTFB 有助于通过移动设备友好性评估，而稳定的资源指纹避免了因缓存错乱导致的页面结构异常。需要强调的是，缓存头必须与部署流程联动——每次发布更新哈希，才能让长缓存真正安全。若需进一步了解 HTTP 缓存规范与实战配置，可参考相关资源中的延伸阅读材料。
