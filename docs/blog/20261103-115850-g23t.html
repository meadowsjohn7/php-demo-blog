Redis 缓存穿透防护：安全规范

2026-11-03 · PHP Demo Blog #Redis #缓存穿透 #安全规范 #PHP #高并发
本文围绕 Redis 缓存穿透防护，从空值缓存、布隆过滤器、互斥锁与限流监控四个层面给出可落地的 PHP 实现规范，强调安全边界与一致性。

缓存穿透的成因与风险

缓存穿透指查询一个必然不存在的数据，请求绕过 Redis 直接落到数据库。常见于恶意构造的 ID 或非法参数，若接口未做校验，数据库将承受持续压力。在 PHP Demo Blog 这类轻量项目中，路由层与数据层解耦清晰，反而更容易在参数入口处遗漏校验。规范要求：所有对外查询接口必须对主键类型、长度、格式做白名单校验，非法请求在进入缓存逻辑前即被拒绝，从源头减少穿透流量。

空值缓存与布隆过滤器

对确认不存在的数据，写入短 TTL 的空值标记，例如 `SETEX cache:post:9999 60 "__NULL__"`，读取时识别该标记直接返回。TTL 建议 30 到 120 秒，避免脏数据长期占用内存。对于集合型查询，可在写入数据库前用布隆过滤器预判键是否存在，PHP 侧可借助 Redis 的 `BF.ADD` 与 `BF.EXISTS` 命令实现，误判率控制在百分之一以内。注意布隆过滤器不支持删除，需配合定期重建或使用可扩展布隆过滤器。

互斥锁与降级策略

当缓存未命中且空值标记也不存在时，使用 `SET lock:post:9999 1 NX EX 3` 获取互斥锁，仅允许一个请求回源数据库，其余请求短暂等待后重试缓存。锁的过期时间必须短于业务超时，防止死锁。回源成功后立即写回缓存并释放锁。若数据库压力已接近阈值，应触发降级：直接返回默认值或错误码，并记录告警。降级开关建议放在配置中心，便于运维快速调整。

监控与安全边界

穿透防护不是一次性配置。需对缓存命中率、空值写入量、锁等待时长建立监控指标，命中率骤降或空值激增往往意味着攻击开始。同时，Redis 实例应启用 ACL 与 TLS，禁止公网暴露，避免缓存数据被篡改后反向污染业务。结合请求频率限制与 IP 黑名单，可进一步压缩恶意流量。规范落地后，应在预发环境用压测工具模拟随机 ID 洪水，验证空值缓存与锁机制的实际效果，再灰度上线。
