## 为什么需要 CSRF 令牌

跨站请求伪造（CSRF）的核心在于浏览器会自动携带目标站点的凭证（如 Cookie 中的 Session ID），攻击者只需诱导用户访问一个恶意页面，就能以用户身份发起非预期的请求。防御的关键是让服务器能够区分“用户主动发起的请求”和“第三方页面伪造的请求”。CSRF 令牌（Token）正是这种区分手段：它要求每个敏感请求都携带一个攻击者无法预测的值，而这个值不会随浏览器自动发送，必须由页面脚本显式提供。

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，令牌机制需要覆盖表单提交和 AJAX 请求两种场景。底层原理并不复杂：服务端生成随机令牌并绑定到用户会话，客户端在请求中回传该令牌，服务端比对一致后才放行。难点在于令牌的生成质量、存储位置以及校验时机。

## 令牌的生成与绑定

令牌必须使用密码学安全的随机源生成，PHP 中应使用 `random_bytes()` 或 `bin2hex(random_bytes(32))`，避免使用 `rand()`、`mt_rand()` 或时间戳拼接。生成后，令牌需要与当前用户会话绑定。常见做法是将令牌存入 `$_SESSION`，并在渲染表单时通过隐藏字段输出，或在 JSON API 场景下通过响应头或初始化接口下发。

绑定关系决定了校验的粒度。如果采用分布式 Redis 集群存储 Session 状态，令牌会随 Session 一起集中管理，这解决了负载均衡环境下用户状态一致性的难题，也意味着令牌校验不依赖单机内存，横向扩展时行为一致。对于无状态 API，可以将令牌与用户 ID、时间戳组合后签名，服务端通过验证签名和时间窗口来判断有效性，但需注意密钥管理与重放防护。

## 校验流程与同源策略的配合

服务端校验时，应使用恒定时间比较函数（如 `hash_equals()`）来避免时序攻击。校验逻辑应放在路由分发之后、业务处理之前，对 POST、PUT、DELETE 等改变状态的请求强制生效，GET 请求则不应产生副作用。令牌失效后应立即重新生成，防止重复使用。

CSRF 令牌不是孤立防线，它与同源策略、Cookie 属性共同构成纵深防御。为会话 Cookie 设置 `SameSite=Lax` 或 `Strict` 可以拦截大部分跨站请求；配置 HSTS 策略配合强加密的 TLS 1.3 证书，不仅提升了安全性，也符合谷歌的安全排名算法。在 Web 层同时实施严格的 CSRF 令牌验证和 XSS 过滤，能从根本上加固业务系统的安全性。XSS 会绕过令牌机制，因此输出转义与内容安全策略同样不可缺失。

## 在 PHP 项目中的落地要点

在具体实现上，建议将令牌逻辑封装为独立的服务类，提供 `generate()`、`validate()` 和 `rotate()` 三个方法，并在中间件中统一调用。表单渲染时输出隐藏字段，AJAX 请求则从 meta 标签读取令牌并放入请求头。对于 JSON API，可在登录后下发令牌，客户端在后续写操作中回传。

需要留意的细节包括：令牌应设置合理的生命周期，过期后要求重新获取；多标签页场景下避免因令牌轮换导致旧页面提交失败，可采用“当前令牌 + 上一令牌”双值校验的过渡策略；日志中不得记录令牌明文。将这些要点固化为开发规范，配合持续的技术迭代与合规性改造，才能在复杂环境下维持站点的安全生命周期。
