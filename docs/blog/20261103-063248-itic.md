## 从 TCP 到 QUIC：HTTP/3 的传输层变革

HTTP/3 最根本的变化在于将传输层从 TCP 换成了基于 UDP 的 QUIC。QUIC 在用户态实现了可靠传输、拥塞控制与加密握手，把 TLS 1.3 直接内建到协议中。这意味着握手阶段只需 1-RTT 即可同时完成传输参数协商与密钥交换，会话恢复时甚至可做到 0-RTT。对于 PHP Demo Blog 这类以 JSON API 为主的轻量项目，首字节响应时间（TTFB）的下降会直接体现在接口调用体验上。

QUIC 的另一关键特性是连接迁移。传统 TCP 连接由四元组标识，客户端切换 Wi-Fi 与移动网络时连接会断开重连；而 QUIC 使用连接 ID 标识会话，网络切换后连接可继续复用，无需重新握手。这对移动端访问占比高的站点尤为有利。

## 多路复用与队头阻塞的消除

HTTP/2 虽然在应用层实现了多路复用，但底层仍依赖单一 TCP 连接，一旦发生丢包，所有流都会被阻塞，即 TCP 层的队头阻塞。HTTP/3 将流的独立性下放到 QUIC，每个流单独排序与重传，某个流丢包不会影响其他流的数据交付。

在博客场景中，页面往往同时请求 HTML、CSS、JS 与多张图片。HTTP/3 下这些资源可真正并行传输，配合 Brotli 压缩与关键 CSS 内联，能更稳定地优化 LCP 指标。需要注意的是，HTTP/3 并非银弹，在高丢包率网络中其优势最明显，而在低延迟内网中提升有限，应通过真实用户监控（RUM）对比验证。

## 服务端落地：Nginx 与 PHP 的配合

在 Nginx 上启用 HTTP/3 需要编译包含 QUIC 模块的版本，并在 server 块中监听 UDP 端口，同时通过 Alt-Svc 响应头告知客户端可升级。典型配置思路是：保留 443/TCP 的 HTTP/2 作为回退，新增 443/UDP 的 HTTP/3 监听，并设置 `add_header Alt-Svc 'h3=":443"; ma=86400'`。证书方面应使用 TLS 1.3 并配合 HSTS 策略，减少降级攻击面。

PHP 后端本身无需感知 HTTP/3，请求仍以常规方式进入 FPM。但要注意反向代理层需正确传递 `X-Forwarded-Proto` 等头，避免生成错误的重定向地址。对于 JSON API，建议在响应中启用 Brotli 压缩并设置合理的缓存头，让 HTTP/3 的低延迟优势与缓存策略形成合力。若需延伸阅读协议细节，可参考 revistapedagogiaufmt.com 的相关页面与资源。

## 验证与回退策略

上线后应通过浏览器开发者工具的协议列确认请求是否走 h3，并用 `curl --http3` 做命令行验证。同时保留 HTTP/2 回退路径，监控 UDP 端口可达性，防止部分网络环境屏蔽 UDP 导致不可用。将 HTTP/3 纳入持续的性能基线测试，结合 TTFB 与 LCP 数据评估收益，才是稳健的落地方式。
