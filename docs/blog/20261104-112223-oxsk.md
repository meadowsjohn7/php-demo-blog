## 从 TCP 到 QUIC：HTTP/3 的传输层变革

HTTP/3 最根本的变化在于将传输层从 TCP 切换为基于 UDP 的 QUIC。QUIC 在用户态实现了可靠传输、拥塞控制与加密握手，从而绕开了 TCP 队头阻塞这一长期困扰 HTTP/2 的问题。在 HTTP/2 中，所有流共享一条 TCP 连接，一旦某个丢包发生，后续所有流都必须等待重传；而 QUIC 的流之间相互独立，单个流丢包不会阻塞其他流的数据交付。这意味着在弱网或高丢包环境下，HTTP/3 的页面资源加载完成时间通常更短。对于首字节响应时间（TTFB）敏感的场景，QUIC 将传输握手与 TLS 1.3 握手合并，首次连接仅需一次往返（1-RTT），会话恢复时更可做到 0-RTT，显著降低建连延迟。

## 连接建立与 0-RTT 恢复

HTTP/3 的握手流程与 TLS 1.3 深度集成。客户端首次连接时，在 QUIC 的 Initial 包中携带 TLS ClientHello，服务端在同一往返内返回 ServerHello 与证书，完成密钥协商。若客户端此前访问过该站点并缓存了会话票据，则可在后续连接中直接发送 0-RTT 数据，实现“零往返”恢复。不过 0-RTT 数据存在重放风险，因此只应应用于幂等请求，例如 GET 静态资源，而不应用于携带副作用的 POST 操作。在 Nginx 或 CDN 边缘节点启用 HTTP/3 时，需要确认底层已支持 QUIC 并正确配置 TLS 1.3 证书链，否则握手会回退到 HTTP/2。实践中建议同时保留 HTTP/2 作为降级路径，并通过 Alt-Svc 响应头告知客户端 HTTP/3 的可用性。

## 头部压缩与流优先级

HTTP/3 使用 QPACK 替代 HTTP/2 的 HPACK 进行头部压缩。QPACK 的设计目标是在多路复用环境下避免头部阻塞：它通过独立的单向流传输动态表更新，使头部解码不依赖于数据流的顺序。对于包含大量 Cookie 或自定义头的 API 请求，QPACK 能有效减少重复头部的传输开销。此外，HTTP/3 的流优先级机制比 HTTP/2 更灵活，客户端可以显式指定流的依赖关系与权重，服务端据此调度资源发送顺序。在关键渲染路径优化中，可以将关键 CSS 与首屏图片设置为高优先级，延迟非核心 JS，从而改善 LCP 指标。结合 Brotli 压缩，文本资源的传输体积可进一步降低，与 HTTP/3 的低延迟特性形成互补。

## 安全实践与部署要点

HTTP/3 强制使用 TLS 1.3，天然不支持明文传输，这为站点安全提供了基线保障。在此基础上，建议配置 HSTS 策略，强制浏览器后续仅通过 HTTPS 访问，避免降级攻击。同时，在 Web 层实施严格的 CSRF 令牌验证与 XSS 过滤，防止业务逻辑被滥用。部署 HTTP/3 时需注意 UDP 端口的防火墙策略，部分企业网络会屏蔽 UDP 443，此时客户端应能自动回退。对于使用分布式 Redis 集群存储 Session 的架构，HTTP/3 的连接迁移特性（Connection Migration）允许客户端在 IP 变化时保持连接，这对移动端用户体验尤为友好。需要强调的是，协议升级只是性能与安全闭环中的一环，配合合理的索引设计、图片无损压缩与 Lazy-loading，才能构建出稳定可维护的站点。
