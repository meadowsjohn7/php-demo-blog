Brotli 压缩算法应用：底层原理

2026-11-07 · PHP Demo Blog #Brotli #HTTP 压缩 #PHP 性能 #TTFB #Web 优化
本文从底层原理出发，解析 Brotli 压缩算法的工作机制，并说明如何在 PHP 项目中启用与调优，以降低传输体积和 TTFB。

静态字典与上下文建模

Brotli 的核心创新之一在于内置了一个约 120KB 的静态字典，其中收录了大量常见的 HTML、CSS、JavaScript 片段以及自然语言词汇。当压缩器扫描输入流时，会优先尝试用字典中的短码替换匹配的长字符串，从而在极小的窗口下也能获得可观的压缩率。与 gzip 单纯依赖 LZ77 滑动窗口不同，Brotli 将字典匹配、上下文建模和熵编码分层处理：第一层负责找出重复串，第二层根据字符上下文选择不同的概率模型，第三层再用前缀码输出。这种分层设计让 Brotli 在文本类资源上通常比 gzip 再小 15% 到 25%。

质量参数与窗口大小的取舍

Brotli 提供 0 到 11 共十二档质量参数。0 到 3 档速度极快，适合动态内容实时压缩；4 到 9 档是平衡区间；10 和 11 档会启用更激进的块拆分和回溯搜索，压缩率最高但 CPU 开销显著上升，通常只用于构建阶段预压缩静态文件。窗口大小以 2 的幂表示，范围从 16 到 24 位，窗口越大能捕获的重复距离越远，但解码端内存占用也越高。对于常规网页资源，窗口设为 22 位（4MB）已能覆盖绝大多数重复模式。在 PHP 侧，可通过 `brotli_compress()` 函数指定质量与窗口参数，但更推荐在 Web 服务器层对静态资源做预压缩，避免每次请求都消耗 PHP 进程的 CPU。

与 HTTP 协议栈的协同

Brotli 的收益不仅取决于算法本身，还依赖协议层的配合。在 HTTP/1.1 下，压缩后的响应需要完整传输；而在 HTTP/2 或 HTTP/3 的多路复用环境中，Brotli 压缩后的较小体积能更快填满拥塞窗口，间接降低首字节响应时间。服务端需正确设置 `Content-Encoding: br` 并配合 `Vary: Accept-Encoding`，让缓存层区分不同编码的副本。若同时启用 HSTS 与 TLS 1.3，握手阶段的节省与传输阶段的压缩叠加，才能形成完整的性能闭环。对于动态 JSON API，可依据 `Accept-Encoding` 请求头判断客户端是否支持 br，再决定是否压缩，避免对不支持的老旧客户端输出乱码。

在 PHP 项目中的落地建议

在轻量路由与 JSON API 场景中，建议将 Brotli 压缩放在 Nginx 或 Apache 层处理：对静态文件启用 `brotli_static` 并预生成 `.br` 文件，对动态响应启用 `brotli` 指令并设置合理的 `brotli_comp_level 5`。PHP 代码中只需保证输出内容不重复压缩，并检查 `$_SERVER['HTTP_ACCEPT_ENCODING']` 中是否包含 `br`。若无法修改服务器配置，再退回 `ob_start('brotli_compress')` 的方案，但需注意该函数依赖 brotli 扩展，且质量参数不宜超过 6。压缩不是孤立优化，它与关键渲染路径拆解、图片懒加载、缓存策略共同构成页面性能的基础设施，持续度量 TTFB 与传输体积的变化，才能确认每一档参数的真实收益。
