MySQL 慢查询排查：底层原理

2026-11-05 · PHP Demo Blog #MySQL #慢查询 #索引优化 #执行计划 #性能调优
从索引结构、执行计划到锁与临时表，剖析 MySQL 慢查询的底层成因，并给出可落地的排查与优化步骤。

慢查询的判定与采集

MySQL 慢查询日志的判定依据是 `long_query_time`，默认 10 秒，实际生产中通常调到 1 秒以下。开启 `slow_query_log` 并配合 `log_queries_not_using_indexes` 后，日志会记录执行时间超阈值的语句。但要注意，`long_query_time` 只统计执行时间，不包含锁等待时间，因此锁冲突导致的阻塞需要借助 `performance_schema` 的 `events_statements_history_long` 表或 `SHOW PROCESSLIST` 观察。采集阶段的核心是拿到 `Query_time`、`Lock_time`、`Rows_examined`、`Rows_sent` 四个指标，其中 `Rows_examined` 与 `Rows_sent` 的比值是判断索引效率的第一手线索。

执行计划揭示的访问路径

拿到慢 SQL 后，第一步是 `EXPLAIN`，重点看 `type`、`key`、`rows`、`Extra` 四列。`type` 为 `ALL` 表示全表扫描，`index` 表示全索引扫描，两者都意味着大量行被读入。`rows` 是优化器基于统计信息估算的扫描行数，若与实际 `Rows_examined` 偏差过大，说明统计信息过期，可执行 `ANALYZE TABLE` 更新。`Extra` 中出现 `Using filesort` 或 `Using temporary` 时，排序或分组无法利用索引顺序，MySQL 需要创建临时表并在磁盘上归并，这是慢查询最常见的底层原因之一。

索引失效与回表代价

InnoDB 的二级索引叶子节点存储的是主键值，通过二级索引查询非索引列时需要回表。当回表行数过多时，优化器可能放弃索引直接全表扫描。常见的索引失效场景包括：对索引列使用函数或表达式、隐式类型转换、`LIKE` 以通配符开头、以及联合索引未遵循最左前缀。排查时可用 `EXPLAIN FORMAT=JSON` 查看 `used_key_parts` 与 `attached_condition`，确认优化器实际使用了索引的哪几列。对于回表代价高的查询，可考虑覆盖索引，把查询列全部放入索引，避免回表。

锁等待与临时表

慢查询不一定是扫描行数多，也可能是等锁。InnoDB 行锁在索引失效时会退化为全表扫描加锁，导致并发写互相阻塞。通过 `information_schema.innodb_trx` 与 `performance_schema.data_locks` 可以定位持有锁的事务及其 SQL。另一类隐性开销来自临时表：`GROUP BY`、`DISTINCT`、`UNION` 在无法利用索引时会产生内部临时表，超过 `tmp_table_size` 后落盘，I/O 成本陡增。排查时关注 `Created_tmp_disk_tables` 状态变量，并结合 `SHOW STATUS LIKE 'Handler_read%'` 判断扫描放大倍数。优化方向是让排序与分组走索引顺序，或拆分查询减少中间结果集。
