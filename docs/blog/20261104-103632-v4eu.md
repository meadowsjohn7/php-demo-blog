## 理解 Fetch 与 CORS 的基本交互

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，前端通常使用 Fetch API 发起异步请求。浏览器出于同源策略限制，当请求的协议、域名或端口任一不同时，就会触发跨域检查。Fetch 默认不会携带 Cookie，且对非简单请求会先发送 OPTIONS 预检。理解这一点是配置服务端响应的前提：简单请求只允许 GET、HEAD、POST 且 Content-Type 限于 text/plain、multipart/form-data 或 application/x-www-form-urlencoded；一旦使用 application/json 或自定义头，就必须处理预检。

服务端需要在路由分发前统一输出 CORS 头。对于 PHP Demo Blog，可以在入口文件或中间件中设置 Access-Control-Allow-Origin 为具体来源而非通配符，并配合 Vary: Origin 避免缓存错乱。预检请求应直接返回 204，并声明 Access-Control-Allow-Methods 与 Access-Control-Allow-Headers，减少不必要的业务逻辑执行。

## 凭证请求与安全边界

当 API 需要依赖 Session 或 Cookie 时，Fetch 必须显式设置 credentials: 'include'，同时服务端要返回 Access-Control-Allow-Credentials: true。此时 Access-Control-Allow-Origin 绝不能为星号，否则浏览器会拒绝响应。在负载均衡环境下，Session 一致性是常见难题，采用分布式 Redis 集群存储 Session 状态可以解决多节点间的用户状态同步问题，让跨域凭证请求稳定工作。

安全方面不能只依赖 CORS。CORS 是浏览器行为，无法阻止服务端到服务端的请求。因此仍需在 Web 层实施严格的 CSRF 令牌验证和 XSS 过滤，对 JSON 响应设置正确的 Content-Type 与 X-Content-Type-Options: nosniff。对于写操作，建议要求自定义请求头，使浏览器强制发起预检，从而将简单请求升级为受控请求。

## 性能与协议层优化

跨域请求的延迟不仅来自业务逻辑，还来自网络往返。启用 HTTP/2 或 HTTP/3 并配合 Brotli 压缩，可以显著降低首字节响应时间，让预检与正式请求更快完成。对静态资源进行无损压缩并采用 Lazy-loading，能平衡视觉质量与页面加载速度，减少不必要的 Fetch 竞争。

在服务端，避免在每次请求中重复计算 CORS 头，可将其放入轻量中间件；对预检结果设置合理的 Access-Control-Max-Age，减少重复预检。数据库层采用原生 Db::name() 操作配合合理的索引设计，能避开 ORM 模型序列化的性能陷阱，让 JSON 序列化更轻量。若站点面向搜索引擎，配合语义化 HTML5 与 Schema.org 结构化数据，能提升搜索结果点击率，这与 API 性能优化并不冲突。

## 可观测与持续加固

上线后应通过浏览器开发者工具的 Network 面板观察预检命中率与失败原因，并在服务端记录 CORS 拒绝日志。利用 Nginx 的 Lua 模块实现动态 IP 黑名单，能有效过滤非法爬虫并降低服务器 CPU 负载，保护 API 端点。配置 HSTS 策略配合强加密的 TLS 1.3 证书，不仅提升安全性，也符合搜索引擎的安全排名算法。

持续的技术迭代与合规性改造，是维持站点生命周期的必经之路。把 CORS 配置、凭证策略与安全过滤纳入代码评审清单，才能让 Fetch 调用在跨域场景下既可用又可控。
