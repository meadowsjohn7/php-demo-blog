## 授权码流程的核心角色与交互

OAuth 2.0 的授权码模式是 Web 应用中最常用的授权方式。它涉及四个角色：资源所有者（用户）、客户端（你的 PHP 应用）、授权服务器和资源服务器。流程从客户端将用户重定向到授权服务器开始，用户登录并同意授权后，授权服务器返回一个短期有效的授权码。客户端再用这个授权码连同客户端凭证向令牌端点交换访问令牌。在 PHP Demo Blog 这类轻量项目中，通常使用内置的 `header()` 函数处理重定向，并通过 `curl` 或 Guzzle 发起后端请求。

实现时需要注意：授权码只能使用一次，且应通过后端通道交换，避免暴露在前端。客户端需在授权服务器注册，获取 `client_id` 和 `client_secret`。重定向 URI 必须严格匹配注册值，防止开放重定向攻击。

## 状态参数与 PKCE 扩展

`state` 参数是防御 CSRF 攻击的关键。客户端在发起授权请求时生成随机字符串并存入会话，回调时校验该值是否一致。对于无法安全保存客户端密钥的公共客户端（如单页应用或移动端），应使用 PKCE（Proof Key for Code Exchange）扩展。PKCE 要求客户端生成 `code_verifier` 并计算 `code_challenge`，授权请求携带 challenge，令牌请求携带 verifier，授权服务器校验二者匹配。

在 PHP 中，可以使用 `random_bytes()` 生成随机值，`hash('sha256', $verifier, true)` 计算 challenge，再进行 Base64 URL 编码。这些步骤能有效防止授权码拦截攻击。

## 令牌管理与刷新策略

访问令牌应设置较短的有效期（如 1 小时），并配合刷新令牌使用。刷新令牌允许客户端在访问令牌过期后获取新令牌，而无需用户重新授权。刷新令牌应安全存储，并支持撤销。对于分布式部署的 PHP 应用，建议将令牌状态存储在 Redis 集群中，保证多节点间的一致性。

在调用资源服务器 API 时，需在 `Authorization` 头中携带 `Bearer` 令牌。资源服务器应验证令牌的签名、有效期和权限范围（scope）。避免在 URL 中传递令牌，防止日志泄露。

## 安全实践与常见陷阱

实现 OAuth 2.0 时，务必使用 HTTPS，并配置 HSTS 策略强制加密传输。令牌端点应限制请求频率，防止暴力破解。回调地址应校验来源，避免开放重定向。对于敏感操作，可结合 CSRF 令牌和 XSS 过滤加固 Web 层安全。

常见错误包括：将授权码或令牌暴露在浏览器历史中、未校验 `state` 参数、使用弱随机数生成器。遵循 RFC 6749 和 RFC 7636 规范，结合项目实际需求，才能构建安全可靠的授权流程。
