## 为什么轻量路由项目也要认真对待 CORS

PHP Demo Blog 这类项目通常以 JSON API 对外提供数据，前端可能部署在独立域名或端口上。浏览器基于同源策略限制跨域读取，CORS 就是服务端声明「允许谁读」的机制。配置过宽会带来安全风险，配置过窄则导致前端请求被拦截。实战中应先明确允许的源、方法与请求头，再落到代码，而不是简单返回一个星号。

## 预检请求与关键响应头

对于非简单请求（如带自定义头或 PUT、DELETE 方法），浏览器会先发 OPTIONS 预检。服务端需要正确响应 Access-Control-Allow-Origin、Access-Control-Allow-Methods、Access-Control-Allow-Headers，以及可选的 Access-Control-Max-Age 来缓存预检结果。若涉及 Cookie 或 Authorization，必须设置 Access-Control-Allow-Credentials 为 true，且 Allow-Origin 不能为通配符，需要回显具体来源。同时建议返回 Vary: Origin，避免缓存层把某个来源的响应错误复用给其他来源。

## 在路由层实现可复用的 CORS 中间件

在轻量路由中，建议把 CORS 逻辑抽成中间件，在分发前统一处理。示例思路：读取请求的 Origin，与白名单数组比对；命中则设置 Allow-Origin 为该 Origin，未命中则不设置跨域头。对 OPTIONS 请求直接返回 204 并结束，不再进入业务控制器。对于普通请求，在响应头中补齐 Allow-Credentials 与 Vary。白名单建议从配置读取，避免硬编码；同时注意不要对错误响应遗漏 CORS 头，否则前端拿不到具体错误信息。

## 常见坑点与验证方法

第一，重复设置 Allow-Origin 会导致浏览器报错，需确保只有一处写入。第二，带凭证时使用通配符会被拒绝，必须精确回显来源。第三，预检失败往往是因为 Allow-Headers 未包含前端实际发送的头。第四，反向代理或 CDN 缓存可能干扰 Vary 行为，需要确认缓存键包含 Origin。验证时可用 curl 模拟 OPTIONS 请求，检查状态码与响应头；再在浏览器开发者工具中观察实际请求是否被拦截。把这些细节处理到位，JSON API 的跨域调用才能稳定可靠。
