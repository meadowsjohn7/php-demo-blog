## 审计的起点：把页面拆成可度量的阶段

性能审计不是跑一遍评分工具就结束，而是把一次请求拆成可度量的阶段：DNS 与连接建立、TLS 握手、TTFB、内容下载、关键渲染路径执行。底层原理决定了每个阶段的上限。例如 TLS 1.3 将握手压缩到一次往返，配合 HSTS 可省去协议降级判断；HTTP/3 基于 QUIC 在弱网下避免队头阻塞，Brotli 则在文本资源上提供比 gzip 更高的压缩比。审计时应先确认这些协议能力是否真正生效，再谈上层优化。

## 关键渲染路径与 LCP 的因果关系

LCP 慢通常不是图片本身大，而是它被非关键资源阻塞。审计时要拆解 CRP：找出首屏必需的 CSS，内联为关键样式，把非核心 JS 标记为延迟加载；对图片做无损压缩并启用 Lazy-loading，但首屏主图必须排除在懒加载之外。DOM 深度、字体加载策略、渲染阻塞脚本都会影响 LCP。用 Performance 面板记录主线程长任务，确认解析与执行时间占比，才能判断是网络问题还是 CPU 问题。

## 服务端与缓存层的底层约束

TTFB 的瓶颈常在服务端。审计应关注数据库查询是否走索引、是否因 ORM 序列化产生额外开销；在可控场景下采用原生查询配合合理索引，能减少无谓的对象映射。Session 若落在单机，负载均衡下会出现状态漂移，分布式 Redis 集群可保证一致性，但要注意序列化成本与网络往返。静态资源应设置长缓存与内容哈希，动态接口则用短缓存加校验头。Nginx 层可用 Lua 做动态 IP 黑名单，过滤非法爬虫以降低 CPU 负载。

## 安全头与离线能力也是性能变量

HSTS、CSP、CSRF 令牌与 XSS 过滤看似安全议题，实则影响性能审计结论：严格的安全头减少重定向与混合内容回退，稳定的会话减少重复鉴权。Service Worker 预取配合 IndexedDB 可让二次访问接近秒级，但缓存策略必须版本化，否则会放大旧资源问题。审计的终点是形成可回归的基线：记录各阶段指标，每次迭代对比，而不是一次性调优。
