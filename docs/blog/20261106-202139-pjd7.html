HSTS 强制安全传输：完整手册

2026-11-06 · PHP Demo Blog #HSTS #TLS 1.3 #安全响应头 #HTTPS #Web 安全
HSTS 通过强制 HTTPS 消除降级攻击，本文从响应头配置、max-age 与 preload 策略、到与 TLS 1.3 及现代前端栈的协同，给出可落地的完整实施路径。

为什么需要 HSTS

HTTP 明文传输的每一次请求都可能被中间人劫持，即便站点已经部署了 HTTPS，用户首次访问或手动输入域名时仍可能走 HTTP。HSTS（HTTP Strict Transport Security）的作用是让浏览器在收到一次合法响应后，记住"此域名只走 HTTPS"，后续所有请求在发出前就被浏览器改写为 HTTPS，从根本上消除 301 跳转窗口期的降级风险。对于需要处理登录态、支付回调和 Session 同步的业务，这一层强制策略是安全基线而非可选项。

响应头配置与参数取舍

HSTS 通过 `Strict-Transport-Security` 响应头下发，核心参数是 `max-age`（秒）、`includeSubDomains` 与 `preload`。起步阶段建议 `max-age=300` 做灰度验证，确认全站资源、API 与子域均已支持 HTTPS 后再逐步提升到 31536000（一年）。`includeSubDomains` 会影响所有子域，务必先排查是否存在仅支持 HTTP 的内部服务。`preload` 用于申请加入浏览器内置列表，一旦提交回滚周期很长，应在 `max-age` 稳定运行数月后再考虑。配置示例：`Strict-Transport-Security: max-age=31536000; includeSubDomains`。

在 Nginx 中可直接在 server 块添加 `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`，`always` 确保错误响应也携带该头。注意 HSTS 头只能通过 HTTPS 响应下发，浏览器会忽略 HTTP 响应中的该头。

与 TLS 1.3 及现代栈的协同

HSTS 只负责"强制走 HTTPS"，传输层强度仍需 TLS 配置兜底。建议启用 TLS 1.3 并禁用 TLS 1.0/1.1，配合 ECDSA 证书与 OCSP Stapling 降低握手开销。在负载均衡环境下，Cookie 应设置 `Secure` 与 `HttpOnly`，Session 状态可用分布式 Redis 集群集中存储，避免多节点间状态不一致。对于 Web 层，严格的 CSRF 令牌校验与输出转义 XSS 过滤与 HSTS 形成互补：前者防业务逻辑攻击，后者防传输层降级。

上线检查清单与常见坑

上线前逐项核对：全站资源（图片、字体、API）是否均为 HTTPS；是否存在硬编码的 HTTP 外链；CDN 回源是否支持 HTTPS；301 跳转是否保留路径与查询串。常见问题包括：子域未覆盖导致 `includeSubDomains` 后部分服务不可达；`max-age` 设置过大且未验证便提交 preload；反向代理层未透传原始协议导致应用层生成 HTTP 链接。建议先用小 `max-age` 观察日志中的混合内容告警，再逐步收紧。HSTS 不是一次性配置，而是需要与证书轮换、域名变更流程绑定的长期运维项。
