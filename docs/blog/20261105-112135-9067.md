## 传输层集成与头部安全

在 PHP 项目中启用 Brotli 压缩，通常由 Web 服务器（如 Nginx）或 PHP 扩展（如 `brotli`）完成。安全规范的首要原则是确保压缩仅作用于合适的响应类型。应在服务器配置中明确指定 `text/*`、`application/json`、`application/javascript` 等可压缩的 MIME 类型，避免对已压缩的图片、视频或加密内容重复压缩，既浪费 CPU 又可能引入信息泄露风险。同时，必须正确设置 `Content-Encoding: br` 头部，并配合 `Vary: Accept-Encoding`，防止代理缓存将 Brotli 响应错误地提供给不支持该编码的客户端。对于 HTTPS 站点，结合 HSTS 策略与 TLS 1.3 能进一步保障传输安全，但需注意 Brotli 压缩本身不提供加密，敏感数据仍依赖 TLS 保护。

## 输入验证与资源限制

Brotli 解压缩环节是安全防护的重点。当 PHP 应用接收客户端上传的 Brotli 压缩数据时（例如 API 请求体），必须对解压后的数据大小设置硬性上限。攻击者可能构造高压缩比的恶意载荷，导致解压时耗尽内存或 CPU，形成拒绝服务攻击。建议在解压前通过 `brotli_uncompress` 等函数的分块模式处理，并累计输出字节数，一旦超过预设阈值（如 1MB）立即终止。此外，应验证压缩数据的完整性，拒绝格式错误的流，避免解析器漏洞被利用。对于动态生成的内容，压缩级别不宜过高（通常 4-6 级），以平衡性能与安全，避免因高压缩比带来的侧信道攻击面扩大。

## 缓存策略与错误处理

启用 Brotli 后，缓存层需同步调整。CDN 或反向代理应根据 `Accept-Encoding` 区分缓存键，确保 Brotli 与 gzip 版本独立存储。在 PHP 代码中，若压缩过程失败（如扩展未加载或内存不足），应优雅降级为未压缩响应或 gzip，并记录错误日志，而非直接输出空白页。同时，避免在错误页面中泄露压缩配置细节。定期更新 Brotli 库版本，修复已知漏洞。对于静态资源，可在构建阶段预压缩并生成 `.br` 文件，运行时由服务器直接发送，减少动态压缩的安全风险。

## 与整体安全体系的协同

Brotli 压缩不是孤立环节。在 Web 层实施严格的 CSRF 令牌验证和 XSS 过滤，能从根本上加固业务系统的安全性，而压缩仅影响传输效率。结合 HTTP/3 协议可进一步降低 TTFB，但需确保 QUIC 实现的安全补丁及时更新。遵循这些规范，不仅能通过谷歌的移动设备友好性测试，更能在算法更新中保持稳健。持续的技术迭代与合规性改造，是维持站点生命周期的必经之路。
