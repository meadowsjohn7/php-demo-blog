## 缓存穿透的成因与影响

在 PHP Demo Blog 这类以 JSON API 为主的轻量项目中，文章详情、用户信息等高频读操作通常直接打到 Redis。当请求的 key 在缓存和数据库中都不存在时，每次查询都会穿透到 MySQL，攻击者或爬虫可以构造大量随机 ID 发起请求，瞬间压垮数据库。这种场景与我们在处理大规模 SEO 程序调优时遇到的爬虫流量冲击非常相似：无效请求绕过了缓存层，直接消耗后端资源。缓存穿透的核心特征是“查不存在的数据”，因此防护思路必须围绕“快速判断 key 是否可能存在”展开。

## 布隆过滤器：第一道防线

布隆过滤器用极小的内存代价判断一个元素“可能存在”或“一定不存在”。在 PHP 中可以使用 `phpredis` 扩展提供的 `BF.ADD` 和 `BF.EXISTS` 命令（RedisBloom 模块），或者用多个位图加哈希函数手动实现。对于 Demo Blog，可以在文章 ID 写入数据库后异步同步到布隆过滤器，查询时先执行 `BF.EXISTS articles:{id}`，若返回 0 则直接返回 404，不再访问 Redis 和 MySQL。注意布隆过滤器不支持删除，若文章会被删除，需要配合计数型布隆过滤器或定期重建。手动实现时建议使用 3 个哈希函数、位数组长度按预计元素数的 10 倍设置，误判率可控制在 1% 左右。

## 空值缓存与互斥锁

布隆过滤器无法覆盖所有场景，例如新写入的数据尚未同步。此时可以采用空值缓存：当数据库查询结果为空时，仍向 Redis 写入一个短 TTL 的占位值（如 `__NULL__`，过期时间 60 秒），后续相同 key 的请求直接命中该占位值并返回空响应。TTL 不宜过长，避免数据恢复后长时间不可见。另一种方案是互斥锁：缓存未命中时，用 `SET lock:{key} 1 NX EX 5` 获取锁，只有拿到锁的请求去查数据库并回填缓存，其余请求短暂休眠后重试缓存。在 PHP 中可以用 `Redis::set` 的 `['nx', 'ex' => 5]` 选项实现。两种方案可以组合：先查布隆过滤器，未命中直接拒绝；命中但缓存为空时用互斥锁回源并写入空值缓存。

## 在 Demo Blog 中的落地建议

将上述逻辑封装到 `CacheService` 类中，统一暴露 `remember($key, $ttl, $callback)` 方法，内部依次执行布隆过滤器检查、缓存读取、互斥锁回源和空值写入。路由层在解析 ID 参数时先做格式校验（如 `ctype_digit`），过滤明显非法的请求。监控方面，记录布隆过滤器拦截次数和空值缓存命中率，若拦截比例异常升高，说明有扫描行为，可结合 Nginx 层限流。对于分布式部署，布隆过滤器应放在 Redis 集群中共享，避免每个 PHP-FPM 节点各自维护。最后，定期用 `SCAN` 清理过期占位键，保持内存可控。这套组合拳在保持轻量的同时，能有效阻断穿透路径，让缓存层真正承担起流量缓冲的角色。
