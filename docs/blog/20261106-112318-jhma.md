## 一、防抖与节流的核心差异与安全边界

防抖（debounce）与节流（throttle）常被混用，但在安全规范下必须明确边界。防抖关注“最后一次触发”，适合搜索联想、表单校验等场景；节流关注“固定频率执行”，适合滚动监听、按钮防连点。二者的共同风险在于：如果实现不当，会绕过业务层的请求频率限制。例如，在 PHP Demo Blog 的 JSON API 中，若前端仅靠防抖控制评论提交，攻击者仍可绕过前端直接调用接口。因此，安全规范要求前端防抖/节流只作为体验优化，服务端必须保留独立的频率校验与 CSRF 令牌验证。

## 二、可执行的实现规范

实现上建议统一封装一个工具函数，避免散落在各组件中。防抖需支持 `immediate` 选项以区分首次触发与末次触发；节流推荐使用时间戳与定时器结合的方式，保证首次立即执行且末次不丢失。关键规范包括：1）所有定时器必须在组件卸载时清理，防止内存泄漏与回调乱序；2）回调中抛出的异常必须被捕获，避免阻塞后续事件；3）涉及网络请求时，应结合 `AbortController` 取消过期请求，防止旧响应覆盖新状态。在 PHP Demo Blog 的评论与搜索接口中，可将防抖延迟设为 300ms，并在请求头携带 CSRF 令牌，服务端再以 Session 维度做二次限流。

## 三、与后端安全策略的协同

前端防抖/节流不能替代后端防护。规范要求：API 层对同一 Session 的写操作设置最小间隔，并对异常高频请求返回 429；同时启用 HSTS 与强加密传输，防止中间人篡改请求频率。对于 JSON API，还应校验 `Content-Type` 与来源，避免跨站请求伪造。前端工具函数应暴露统一的错误上报接口，将节流触发的异常与取消的请求记录到日志，便于排查是体验问题还是攻击行为。

## 四、测试与回归要点

上线前需覆盖三类测试：快速连续点击、慢速长按、以及网络延迟下的乱序响应。验证点包括：按钮在节流窗口内是否只提交一次、防抖回调是否在组件销毁后仍被触发、取消的请求是否真正中止。建议在 CI 中加入针对工具函数的单元测试，并在预发环境用弱网模拟验证。只有把前端节流/防抖纳入安全规范，才能让 PHP Demo Blog 这类轻量项目在体验与安全之间取得平衡。
