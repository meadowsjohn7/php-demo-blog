## HSTS 的作用与部署前提

HSTS（HTTP Strict Transport Security）通过响应头 `Strict-Transport-Security` 告知浏览器在指定时间内强制使用 HTTPS 访问当前域名，从而避免 SSL 剥离攻击与混合内容风险。在 PHP Demo Blog 这类轻量项目中，部署 HSTS 的前提是站点已全面启用 HTTPS，且所有子资源（CSS、JS、图片）均通过 HTTPS 加载。若仍存在 HTTP 资源，浏览器会直接阻断，导致页面功能异常。因此，建议先在测试环境验证资源完整性，再逐步在生产环境启用。

## 响应头配置与参数选择

HSTS 的核心参数包括 `max-age`、`includeSubDomains` 与 `preload`。`max-age` 建议从较小值（如 300 秒）开始，确认无问题后逐步提升至一年（31536000 秒）。`includeSubDomains` 需谨慎启用，确保所有子域名均已支持 HTTPS，否则会导致子域名无法访问。`preload` 用于申请加入浏览器预加载列表，要求 `max-age` 至少一年且包含 `includeSubDomains`。在 PHP 中，可通过 `header()` 函数在入口文件统一输出：

```php
header('Strict-Transport-Security: max-age=31536000; includeSubDomains');
```

若使用 Nginx，可在 `server` 块中添加 `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`。注意避免重复设置导致冲突。

## 与 TLS 1.3 及性能优化的协同

HSTS 仅强制使用 HTTPS，传输层安全仍依赖 TLS 配置。建议启用 TLS 1.3，其握手过程更简洁，可降低延迟。在 Nginx 中配置 `ssl_protocols TLSv1.2 TLSv1.3;` 并选用强加密套件。同时，结合 HTTP/2 或 HTTP/3 与 Brotli 压缩，可进一步降低首字节时间。对于使用分布式 Redis 集群存储 Session 的架构，HSTS 不会影响会话机制，但需确保 Cookie 设置 `Secure` 与 `HttpOnly` 属性，避免在 HTTPS 下泄露。

## 测试、回滚与长期维护

启用 HSTS 前，应使用 `curl -I` 检查响应头是否正确输出，并通过浏览器开发者工具确认无混合内容警告。由于 HSTS 策略会被浏览器缓存，回滚较为困难，建议在预发布环境充分测试。对于需要长期维护的站点，可将 HSTS 配置纳入基础设施即代码（IaC）模板，确保每次部署一致性。定期审查 `max-age` 与子域名覆盖范围，结合安全扫描工具验证配置有效性，是维持安全传输规范的必要环节。
