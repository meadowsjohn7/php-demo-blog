Redis 缓存穿透防护：技术架构

2026-11-05 · PHP Demo Blog #Redis #缓存穿透 #PHP #架构设计 #布隆过滤器
本文讨论在 PHP Demo Blog 中基于 Redis 实现缓存穿透防护的架构设计，涵盖空值缓存、布隆过滤器与互斥锁等可落地方案。

缓存穿透的成因与影响

在 PHP Demo Blog 的 JSON API 场景中，缓存穿透通常表现为大量请求查询根本不存在的键，导致请求直接落到数据库。与缓存击穿（热点键失效）和雪崩（大批键同时失效）不同，穿透的根源是查询目标在数据源中本就不存在，缓存层无法形成有效拦截。若不加防护，攻击者只需构造随机 ID 持续请求，就能让数据库承受与请求量等价的压力。因此防护架构的核心目标是在缓存层之前或之内，尽早识别并拒绝这类无效查询。

空值缓存与短 TTL 策略

最直接的防护手段是空值缓存：当数据库查询结果为空时，仍向 Redis 写入一个占位值（如空字符串或特定标记），并设置较短的过期时间（例如 60 秒）。这样后续相同键的请求会命中缓存并直接返回空结果，不再触达数据库。实现时需注意两点：一是占位值要与真实数据可区分，避免业务逻辑误判；二是 TTL 不宜过长，防止数据后续被创建时出现长时间不一致。在 PHP 中可封装统一的缓存读取函数，将“查缓存—查库—回填”三步收敛到一处，减少遗漏。

布隆过滤器前置拦截

空值缓存只能拦截已出现过的无效键，对随机生成的键无能为力。此时可在缓存之前增加布隆过滤器：将所有合法键的哈希映射到位数组中，请求到达时先判断键是否可能存在，若判定不存在则直接返回。布隆过滤器存在误判率（可能把不存在的键判为存在），但不会漏判，因此适合做前置过滤。在 Redis 中可使用位图命令手动实现，或采用支持布隆过滤器的模块。关键设计是过滤器与数据库的同步策略：新增数据时写入过滤器，删除数据时通常不直接移除（布隆过滤器不支持删除），可通过定期重建或结合计数型变体来缓解。

互斥锁与降级兜底

对于穿透与击穿交织的场景，可在缓存未命中时使用 Redis 的 SET NX 命令获取短时互斥锁，仅允许一个请求回源查询，其余请求短暂等待或返回降级结果。锁的过期时间要略大于一次数据库查询的耗时，避免死锁。同时应在 API 层设置统一的降级响应，例如返回空列表或默认值，并记录命中日志，便于观察穿透比例。配合请求参数校验（如 ID 格式与范围检查），可在进入缓存逻辑前过滤掉明显非法的请求，进一步降低无效流量。

架构落地要点

在 PHP Demo Blog 这类轻量项目中，建议将上述策略组合为分层防护：参数校验在最外层，布隆过滤器做前置判断，空值缓存处理已出现的无效键，互斥锁控制回源并发。所有 Redis 操作应设置合理的连接与读取超时，避免缓存层自身故障拖垮整个 API。监控方面，可统计缓存命中率、空值缓存命中数与回源 QPS，用数据验证防护效果并指导 TTL 与过滤器容量的调整。
