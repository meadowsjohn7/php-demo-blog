跨域资源共享 CORS 配置：安全规范

2026-11-05 · PHP Demo Blog #CORS #PHP #安全 #HTTP #API
本文探讨 PHP 项目中 CORS 配置的安全规范，包括避免通配符、限制来源、处理凭证请求及预检缓存，并结合 Demo Blog 给出可执行建议。

为什么 CORS 配置容易出错

跨域资源共享（CORS）是浏览器同源策略的补充机制，但许多开发者为了快速联调，直接使用 `Access-Control-Allow-Origin: *` 并允许所有方法。这种配置在公开 API 中尚可接受，一旦涉及用户凭证或敏感数据，就会引入 CSRF 与数据泄露风险。在 PHP Demo Blog 中，JSON API 需要被前端页面跨域调用，因此必须明确区分公开接口与需认证接口的 CORS 策略。

核心安全原则：最小化授权

首先，禁止在生产环境使用通配符来源。应根据请求的 `Origin` 头动态校验白名单，仅当来源匹配时返回该来源，否则不返回 CORS 头。其次，`Access-Control-Allow-Credentials: true` 必须与具体来源配对，不能与 `*` 同时使用。对于预检请求，`Access-Control-Allow-Methods` 只列出实际使用的方法，例如 `GET, POST`，而非全部。`Access-Control-Allow-Headers` 同样应限制为必要的自定义头，如 `Content-Type, X-CSRF-Token`。

预检缓存与 Vary 头

预检请求会增加延迟，可通过 `Access-Control-Max-Age` 设置合理缓存时间，例如 600 秒。但需注意，当响应依赖 `Origin` 头时，必须添加 `Vary: Origin`，避免代理或 CDN 缓存错误响应。在 PHP 中，可在路由分发前统一处理 CORS 逻辑，根据请求方法返回 204 或继续执行。对于简单请求，直接附加 CORS 头即可；对于预检请求，提前终止并返回相应头信息。

结合认证与 CSRF 防护

CORS 不是认证机制。对于携带 Cookie 的请求，应同时实施 CSRF 令牌验证，并在服务端校验 `Origin` 或 `Referer` 头。在 PHP Demo Blog 中，建议将 CORS 配置封装为独立中间件，与 Session 认证解耦，便于审计和测试。此外，避免在错误响应中泄露内部头信息，统一错误格式。定期审查白名单，移除不再使用的域名，是维持安全基线的必要步骤。
