## 为什么富文本编辑器是 XSS 的高发区

富文本编辑器允许用户提交带格式的 HTML，这天然与 XSS 防护相冲突。很多项目只在前端做简单替换，后端直接入库并原样输出，攻击者只需构造 `<img src=x onerror=...>` 或 `javascript:` 伪协议链接即可执行脚本。安全规范的第一条原则是：**永远不信任客户端提交的 HTML**。服务端必须对富文本内容做白名单净化，只保留业务允许的标签和属性，例如 `p`、`strong`、`em`、`ul`、`li`、`a`、`img`，并强制 `a` 标签的 `href` 只允许 `http`、`https`、`mailto` 协议，`img` 的 `src` 只允许 `http`、`https`。净化应在入库前完成，同时保留一份原始内容用于审计。

## 白名单净化的实现要点

在 PHP 侧可以基于 DOMDocument 遍历节点，删除不在白名单中的标签及其子节点（或转义为文本），并移除所有 `on*` 事件属性、`style` 中的 `expression` 与 `url()` 外链。对于 `a` 标签，额外添加 `rel="noopener noreferrer"` 与 `target="_blank"` 的受控策略。净化函数应幂等，重复执行不改变结果。注意不要用正则去解析 HTML，标签嵌套与属性顺序的边界情况会让正则失效。净化后的内容在输出时仍需按上下文转义：在 HTML 正文中直接输出净化结果，在属性、JS 字符串、JSON 中则使用对应的转义函数，避免二次注入。

## 与 CSRF、安全头的协同防护

富文本提交接口同样需要 CSRF 令牌验证，令牌应绑定会话并在服务端校验，防止攻击者借用已登录用户的身份提交恶意内容。会话状态建议集中存储，避免多节点下令牌不一致。在 Web 层统一设置安全响应头：`Content-Security-Policy` 限制脚本来源，`X-Content-Type-Options: nosniff` 阻止 MIME 嗅探，配合 HSTS 与 TLS 1.3 降低传输层风险。这些措施与净化逻辑形成纵深防御，即使净化出现遗漏，CSP 也能拦截大部分内联脚本执行。

## 可执行的检查清单

上线前逐项核对：净化白名单是否覆盖所有允许标签；`href` 与 `src` 协议是否受限；是否移除全部事件属性；输出是否按上下文转义；接口是否校验 CSRF 令牌；是否设置 CSP 与 nosniff 响应头；是否记录净化前后的内容差异用于审计。把这份清单固化为代码评审项，才能让富文本功能在安全与可用之间保持稳定。
