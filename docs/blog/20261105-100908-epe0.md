## 参数化查询：从根源切断注入路径

SQL 注入的本质是用户输入被当作 SQL 语法解析。防御的第一原则是让数据永远以数据身份进入数据库，而不是拼接进语句。在 PHP 中，PDO 的预处理语句提供了最直接的实现方式：使用命名占位符或问号占位符，并在 execute 时传入绑定参数，同时显式指定 PDO::ATTR_EMULATE_PREPARES 为 false，确保预处理在数据库端真正执行，而非在驱动层做字符串替换。对于 MySQL，还应将 charset 设置为 utf8mb4，避免宽字节注入。需要强调的是，表名、列名、排序方向等无法用占位符绑定的部分，必须使用白名单映射，绝不能直接拼接用户输入。

## ORM 与查询构造器的安全边界

许多团队使用 ORM 或查询构造器来降低手写 SQL 的风险，但这并不意味着自动免疫。以常见的 Db::name() 风格查询为例，where 方法在传入数组或字符串时行为差异很大：字符串条件若包含用户输入，同样会形成注入点。优化方案是统一约定：所有动态值一律通过绑定参数传入，禁止在 where 中拼接原始字符串；对 like 查询要显式转义百分号和下划线；对 in 查询使用数组绑定而非 implode 拼接。此外，应关闭生产环境的调试模式，避免异常信息泄露表结构。对于批量写入，使用事务配合参数绑定，既保证一致性，也避免逐条拼接 SQL。

## 输入校验与最小权限的双重兜底

参数化查询解决的是语法层注入，但业务层仍需校验。对整数型参数使用 filter_var 配合 FILTER_VALIDATE_INT，对枚举型参数建立白名单，对长度和字符集做约束。数据库账号应遵循最小权限原则：Web 应用账号只授予必要的 SELECT、INSERT、UPDATE、DELETE 权限，禁止 DROP、FILE 等高风险权限，并限制其只能访问业务库。这样即使出现漏网之鱼，攻击者也无法通过堆叠查询或文件读写扩大战果。同时，关闭数据库的 multi statements 支持，可进一步阻断堆叠注入。

## 代码审计与持续防护

防御不是一次性配置，而是持续过程。建议在 CI 流程中引入静态分析工具，对拼接 SQL 的代码模式进行告警；定期使用 sqlmap 等工具对测试环境做回归验证，但严禁对生产环境扫描。日志层面，记录所有执行失败或参数异常的查询，并设置阈值告警。对于历史遗留代码，优先改造直接拼接的入口函数，再逐步收敛到统一的查询层。把这些措施固化为开发规范，才能让 SQL 注入防御从被动修补转为主动免疫。
