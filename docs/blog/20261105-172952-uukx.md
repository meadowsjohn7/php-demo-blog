## 同源策略与 CORS 的出发点

浏览器执行同源策略，是为了限制一个源（协议、主机、端口三者组合）的脚本读取另一个源的资源。CORS 并非“关闭同源策略”，而是在服务端显式声明“允许哪些外部源读取本资源”。对于 PHP Demo Blog 这类提供 JSON API 的项目，前端可能部署在独立域名或本地开发端口上，跨域请求不可避免。理解 CORS 的底层原理，关键是区分“简单请求”与“预检请求”：前者直接发出，后者先以 OPTIONS 方法探测服务端是否放行。

服务端在响应中返回 Access-Control-Allow-Origin 等头部，浏览器据此决定是否把响应体交给发起请求的脚本。注意，请求本身往往已经到达服务器并被执行，CORS 控制的是“响应能否被读取”，这一点常被误解为“请求被拦截”。

## 预检请求与响应头语义

当请求方法不是 GET、HEAD、POST，或携带了非安全列表内的请求头（如自定义的 X-Requested-With、Content-Type 为 application/json），浏览器会先发送 OPTIONS 预检。服务端必须正确响应 Access-Control-Allow-Methods、Access-Control-Allow-Headers，并用 Access-Control-Max-Age 缓存预检结果，减少往返。

在 PHP 中，可在路由分发前统一处理 OPTIONS：识别请求方法后直接返回 204，并输出允许的方法与头部。对于 JSON API，Content-Type 常为 application/json，这会触发预检，因此不能只设置 Allow-Origin 就以为万事大吉。若响应缺少 Allow-Headers 中声明的自定义头，浏览器会拒绝后续实际请求。

## 凭证模式与安全边界

当请求需要携带 Cookie 或 Authorization 时，前端需设置 credentials，服务端则必须返回 Access-Control-Allow-Credentials: true，且 Access-Control-Allow-Origin 不能为通配符 *，必须是具体源。实践中应维护一份允许源白名单，根据请求的 Origin 头动态回显，而不是无条件反射任意来源。

此外，Vary: Origin 响应头必不可少，否则中间缓存可能把针对某个源的 CORS 响应错误地复用给其他源。对于需要跨域写入的接口，还应结合 CSRF 令牌与 SameSite Cookie 策略，避免 CORS 放开后引入新的攻击面。PHP Demo Blog 的 JSON API 可在入口处集中校验 Origin 是否在白名单内，再决定是否输出 CORS 头。

## 在 PHP Demo Blog 中的落地建议

建议把 CORS 逻辑封装为独立的中间件或前置函数：先判断 Origin 是否合法，再按请求方法区分预检与实际请求，统一输出 Allow-Origin、Allow-Methods、Allow-Headers、Max-Age 与 Vary。对于公开只读接口，可放宽为具体源列表；对于涉及用户状态的接口，坚持凭证模式并收紧白名单。调试时可用浏览器开发者工具的 Network 面板观察预检请求与响应头是否匹配，避免“看似配置了却仍被拦截”的循环排查。
