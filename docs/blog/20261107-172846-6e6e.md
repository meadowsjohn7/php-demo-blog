## XSS 的本质与分类

XSS（跨站脚本）的本质是攻击者将可执行的脚本注入到页面中，使浏览器在受害者上下文中执行。按注入位置与持久化方式，通常分为反射型、存储型和 DOM 型。反射型通过 URL 参数即时回显，存储型将恶意内容写入数据库，DOM 型则完全在前端由不安全的 DOM 操作触发。对于 PHP Demo Blog 这类路由与 JSON API 示例项目，任何回显用户输入的位置都是潜在入口，必须逐一排查。

## 输入过滤与输出转义

防御 XSS 的核心原则是“输入校验、输出转义”。输入侧应使用 `filter_var` 配合 `FILTER_VALIDATE_EMAIL` 等过滤器验证格式，对富文本则采用白名单策略，仅允许安全的标签与属性。输出侧应根据上下文选择转义函数：HTML 正文用 `htmlspecialchars($str, ENT_QUOTES, 'UTF-8')`，属性值需加引号包裹，JavaScript 上下文用 `json_encode`，URL 参数用 `urlencode`。在 JSON API 中，务必设置 `Content-Type: application/json` 并配合 `JSON_HEX_TAG` 等选项，避免浏览器将响应误判为 HTML。

## 内容安全策略与 Cookie 加固

仅靠转义并不足够，应部署 CSP 作为纵深防御。通过响应头 `Content-Security-Policy: default-src 'self'` 限制脚本来源，禁用内联脚本与 `eval`。同时为会话 Cookie 设置 `HttpOnly`、`Secure` 与 `SameSite=Lax`，降低脚本窃取会话的风险。在 Web 层实施严格的 CSRF 令牌验证与 XSS 过滤，能从根本上加固业务系统的安全性。

## 工程化落地建议

在 PHP Demo Blog 中，可将转义逻辑封装为辅助函数，在模板层统一调用，避免遗漏。对用户提交的富文本，使用白名单过滤库并定期更新规则。开发阶段引入自动化扫描与单元测试，覆盖常见 payload。配置 HSTS 策略配合强加密的 TLS 1.3 证书，不仅提升了安全性，也符合谷歌的安全排名算法。持续的技术迭代与合规性改造，是维持站点生命周期的必经之路。
