## 日志采集与脱敏：从源头控制风险

蜘蛛日志分析的第一步不是分析，而是安全地采集。在 Nginx 层，建议单独定义 `log_format`，只记录必要字段：`$remote_addr`、`$time_local`、`$request`、`$status`、`$http_user_agent`、`$http_referer` 与 `$request_time`。避免将 `$http_cookie`、`$args` 中的完整查询串直接落盘，防止令牌或用户标识泄露。若确需保留 URL 参数，应在采集端用 Lua 或日志切割脚本对 `token`、`session` 等键值做掩码替换后再写入文件。日志文件权限应设为 640，属主为运行 Nginx 的专用账户，禁止 Web 根目录可访问。对于多机部署，通过 `rsyslog` 或 `filebeat` 集中转发时启用 TLS 加密，避免日志在传输链路中被嗅探。

## 访问控制与完整性校验

日志目录不应挂载在可公开访问的路径下，建议放在 `/var/log/nginx/spider/` 并配合 `chattr +a` 追加写属性，防止进程被入侵后篡改历史记录。分析任务使用的账户应遵循最小权限原则：只读日志、只写分析结果，不授予数据库写权限。若使用 PHP 脚本做定时汇总，务必在脚本入口校验 `php_sapi_name() === 'cli'`，拒绝 Web 直接调用，避免通过 URL 触发日志解析接口。对原始日志按天做 SHA-256 摘要并单独存储，当出现异常流量争议时可用于比对完整性。

## 爬虫识别与异常告警

识别合法爬虫不能只看 `User-Agent`。规范做法是结合反向 DNS 解析与 IP 段白名单：对声称是 Googlebot 的请求，先做 PTR 查询，再正向解析确认归属，二者一致才放行。在 Nginx 层可用 Lua 模块维护动态黑名单，对短时间内高频请求 404 或携带可疑 UA 的 IP 自动封禁，降低 CPU 负载。分析侧应设置基线告警：当某 IP 的请求量在 5 分钟内超过阈值、或对同一路径的重复访问比例异常时，写入告警队列并通知运维。所有封禁与放行操作记录操作人、时间与原因，形成可审计的安全闭环。

## 数据留存与合规边界

日志中的 IP 在多数司法辖区属于个人数据，留存周期应明确：原始访问日志建议保留 30 至 90 天，聚合后的统计结果可保留更久，但需去除可识别字段。分析报表中展示 IP 时做末段掩码，例如 `203.0.113.x`。删除策略应写成脚本并纳入定时任务，避免人工遗漏。整套规范的目标不是增加复杂度，而是让日志分析在可追溯、可审计的前提下持续运行，为站点安全与爬虫治理提供可靠依据。
