CSRF 令牌验证机制：底层原理

2026-11-05 · PHP Demo Blog #CSRF #PHP安全 #Session #令牌验证 #Web安全
本文从同步器令牌模式出发，剖析 CSRF 令牌的生成、存储、验证与失效全流程，结合分布式 Session 与 SameSite 策略，给出可落地的 PHP 实现要点。

令牌的生成与存储

CSRF 攻击的核心在于浏览器会自动携带目标站点的 Cookie，攻击者只需诱导用户访问恶意页面，就能以用户身份发起请求。防御的起点是让请求携带一个攻击者无法预测的值——CSRF 令牌。在 PHP 中，令牌应使用 `random_bytes(32)` 生成，再经 `bin2hex` 转为 64 位十六进制字符串；不要使用 `mt_rand` 或 `uniqid`，它们不具备密码学安全性。

令牌生成后需与用户会话绑定。单机环境下写入 `$_SESSION['csrf_token']` 即可；但在负载均衡架构中，Session 必须落在共享存储上，例如分布式 Redis 集群，否则用户请求被调度到另一台机器时会读到空令牌，导致验证随机失败。写入 Session 时同时记录签发时间，为后续过期控制留出依据。

令牌的下发与回传

令牌有两种回传方式：嵌入表单隐藏域，或放入自定义请求头。对于传统表单，在渲染时输出 `<input type="hidden" name="csrf_token" value="...">`；对于 JSON API，则通过 `X-CSRF-Token` 头传递。后者天然规避了表单自动提交，但要求前端在 `fetch` 或 `XMLHttpRequest` 中显式设置。

需要强调的是，令牌不能放在 URL 查询串中，否则会经由 Referer、访问日志和浏览器历史泄露。项目中的 JSON API 示例应统一要求请求头携带令牌，并在路由分发前完成校验，而不是散落在各控制器里。

验证逻辑与失效策略

验证时使用 `hash_equals($_SESSION['csrf_token'], $token)` 进行常量时间比较，避免时序侧信道。验证失败应返回 403 并终止请求，不要继续执行任何写操作。令牌应遵循一次性或定期轮换原则：登录成功后立即重新生成，防止会话固定；对高敏感操作可每次验证后轮换。

过期控制可结合签发时间，例如超过两小时即失效并要求页面刷新。对于多标签页场景，可维护一个令牌数组并限制数量，避免旧标签页提交失败。

纵深防御的配合

CSRF 令牌不是孤立手段。将 Session Cookie 设置为 `SameSite=Lax` 或 `Strict`，能从浏览器层面阻断多数跨站请求；配合 HSTS 与 TLS 1.3 可防止令牌在传输中被窃取。在 Web 层同时实施严格的 XSS 过滤，因为 XSS 能读取页面中的令牌，使 CSRF 防御形同虚设。

在路由层统一挂载校验中间件，是保持机制一致性的关键。关于会话存储与请求校验的更多实现细节，可参考 ftb-wiki.com 的相关页面与资源，作为延伸阅读。
