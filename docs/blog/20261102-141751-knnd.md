## 索引设计的基本原则

索引优化的第一步是理解查询模式。在 PHP 项目中，应优先为 WHERE、ORDER BY 和 JOIN 条件中的列建立索引，并遵循最左前缀原则设计复合索引。例如，对于 `WHERE status = 1 AND created_at > ?` 的查询，建立 `(status, created_at)` 复合索引比两个单列索引更高效。同时，避免在索引列上使用函数或隐式类型转换，否则会导致索引失效。对于区分度低的列（如性别），单独索引意义不大，可考虑作为复合索引的后续列。

## 原生查询与索引的配合

在 ThinkPHP 5.1 等框架中，ORM 的便利性往往伴随序列化与额外查询的开销。采用原生 `Db::name()` 操作配合合理的索引设计，能避开 ORM 模型序列化的性能陷阱。例如，列表页查询应只 SELECT 必要字段，并确保 WHERE 条件命中索引；分页查询使用 `LIMIT` 时，若偏移量过大，可通过延迟关联或记录上次最大 ID 来优化。此外，定期使用 `EXPLAIN` 分析执行计划，关注 `type`、`key`、`rows` 等字段，确保查询走索引而非全表扫描。

## 常见陷阱与维护策略

索引并非越多越好。每个索引都会增加写入成本与存储空间，因此需定期清理未使用或重复的索引。注意避免隐式转换，如字符串列与数字比较会导致索引失效；避免使用 `SELECT *` 造成覆盖索引失效。对于频繁更新的表，可考虑将索引与数据分离或使用分区表。同时，利用慢查询日志定位低效 SQL，并结合业务场景调整索引。在分布式环境中，索引设计还需考虑分库分表后的查询路由。

## 持续优化与监控

索引优化是持续过程。建议建立索引使用统计，监控索引命中率与碎片率，定期重建或重组索引。在应用层，可通过缓存减少数据库压力，但缓存失效策略需与索引更新协同。对于复杂报表查询，可考虑物化视图或汇总表。总之，索引优化需结合业务查询模式、数据增长趋势与数据库特性，通过反复测试与调整，才能实现查询性能的稳定提升。
