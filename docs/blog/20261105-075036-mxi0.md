## 流水线设计原则与项目适配

为 PHP Demo Blog 设计 CI/CD 流水线时，首要原则是让每次推送都经过可重复的验证。GitHub Actions 的 workflow 文件放在 `.github/workflows` 目录下，建议按职责拆分为 `ci.yml` 与 `deploy.yml`。CI 阶段至少包含依赖安装、静态分析、单元测试与安全扫描。对于轻量路由与 JSON API 项目，可使用 `shivammathur/setup-php` 动作固定 PHP 版本，并启用 Composer 缓存以缩短构建时间。测试环节应覆盖路由解析与 JSON 响应结构，避免仅运行语法检查。

## 关键步骤：测试、安全与性能门禁

在 CI 中引入 PHPStan 或 Psalm 做静态分析，配合 PHPUnit 执行单元测试。安全方面，使用 `composer audit` 检查依赖漏洞，并借助 `gitleaks` 扫描提交中是否泄露密钥。性能门禁可运行轻量基准脚本，记录 API 响应时间，超过阈值则失败。部署前，通过 `actions/upload-artifact` 保存构建产物，确保部署环境与测试环境一致。若项目涉及前端资源，可在流水线中执行关键 CSS 内联与 JS 延迟加载的构建步骤，以优化 LCP 指标。

## 部署策略与环境隔离

部署作业应仅在主分支通过 CI 后触发，使用 GitHub Environments 管理生产与预发环境，并配置审批规则。通过 SSH 或容器镜像将产物推送到目标服务器，部署后执行健康检查，验证路由与 JSON 端点返回 200。回滚机制可依赖版本化产物或镜像标签，确保故障时快速恢复。对于 Session 状态，若采用分布式 Redis 集群，需在部署脚本中检查连接可用性，避免负载均衡下状态不一致。

## 安全加固与持续迭代

流水线中可加入 TLS 与 HSTS 配置检查，确保部署的 Nginx 配置符合安全基线。同时，通过自动化脚本验证 CSRF 令牌与 XSS 过滤规则是否生效。持续迭代时，定期更新 Actions 版本与依赖，利用 Dependabot 自动创建升级 PR。将性能与安全指标纳入流水线门禁，能形成技术闭环，支撑站点长期稳定运行。
