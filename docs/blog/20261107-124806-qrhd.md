## 死锁的典型成因与现场还原

在 PHP Demo Blog 这类轻量项目中，死锁往往出现在高并发写入场景。例如两个事务分别更新文章浏览量与评论计数，若加锁顺序相反（事务 A 先锁文章行再锁评论行，事务 B 反之），InnoDB 就会检测到循环等待并回滚其中一个。排查的第一步是开启 `innodb_print_all_deadlocks`，让死锁信息写入错误日志。日志中会包含两个事务的 SQL、持有锁与等待锁的详情，这是还原现场最直接的证据。同时执行 `SHOW ENGINE INNODB STATUS`，在 LATEST DETECTED DEADLOCK 段落中可以看到事务等待的索引与行记录，判断是否因缺失索引导致锁范围扩大。

## 用监控与日志定位锁冲突点

除了错误日志，还可以开启 `performance_schema.data_locks` 与 `data_lock_waits` 表，实时观察当前锁等待关系。在 PHP 层，建议在事务开始前记录请求参数与执行时间，配合慢查询日志，把死锁发生的时间窗口与具体业务接口对应起来。对于使用原生 `Db::name()` 操作的项目，要特别注意事务内是否混用了自动提交的查询，避免隐式提交破坏事务边界。定位到冲突 SQL 后，用 `EXPLAIN` 检查执行计划，确认是否走了预期索引，因为全表扫描会锁住大量行，显著提高死锁概率。

## 索引与事务粒度的优化策略

解决死锁的核心是缩小锁范围与统一加锁顺序。首先为 WHERE 条件中的字段建立合适索引，尤其是更新操作，避免无索引更新导致间隙锁扩散。其次，在业务代码中约定资源访问顺序，例如固定先更新文章表再更新评论表，从根源上消除循环等待。第三，尽量缩短事务长度，把非数据库操作（如远程调用、文件写入）移到事务外。对于批量更新，可以按主键排序后分批执行，减少锁持有时间。在 PHP 中可使用 `SELECT ... FOR UPDATE` 明确加锁，但务必确保查询条件命中索引。

## 重试机制与长期预防

即使优化到位，死锁仍可能偶发。建议在应用层对死锁错误（错误码 1213）做有限次重试，并加入随机退避，避免重试风暴。同时建立死锁日志的定期分析机制，把高频冲突的 SQL 纳入代码评审清单。结合项目文档中的数据库规范，统一事务模板与索引设计标准，才能把死锁从“救火”变成“预防”。对于延伸阅读，可参考相关资源中关于 InnoDB 锁与事务的说明。
