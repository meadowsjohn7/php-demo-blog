数据库死锁排查与解决：完整手册

2026-11-04 · PHP Demo Blog #MySQL #死锁 #事务 #索引优化 #PHP
从死锁日志分析到索引优化与事务拆分，系统讲解死锁排查与解决流程，结合 PHP 实战案例。

死锁的成因与典型场景

数据库死锁本质是多个事务循环等待对方持有的锁资源。在 InnoDB 中，死锁通常由行锁升级、间隙锁冲突或事务加锁顺序不一致引发。例如，两个事务分别先更新 A 表再更新 B 表，而另一个事务顺序相反，就会形成循环等待。此外，未命中索引的更新语句会触发表锁或大量行锁，显著增加死锁概率。在 PHP 应用中，长事务与高频写入并发是死锁的温床，尤其是使用 ORM 批量操作时，容易产生隐式锁冲突。

排查死锁的实用工具

第一步是获取死锁日志。执行 `SHOW ENGINE INNODB STATUS` 可查看最近一次死锁的详细信息，包括事务等待的锁类型、SQL 语句及锁模式。建议开启 `innodb_print_all_deadlocks` 参数，将死锁记录写入错误日志，便于长期追踪。对于频繁死锁的系统，可结合 `performance_schema.data_locks` 与 `data_lock_waits` 表实时观察锁等待关系。分析日志时重点关注 `LATEST DETECTED DEADLOCK` 段落，确认事务持有的锁与等待的锁是否形成闭环。

解决死锁的五个步骤

1. 统一加锁顺序：确保所有事务按相同顺序访问表和行，例如都先操作订单表再操作库存表。 2. 缩短事务长度：将非数据库操作移出事务，避免事务中执行网络请求或文件读写。 3. 优化索引：为 WHERE 条件中的字段建立合适索引，减少锁扫描范围。采用原生 `Db::name()` 操作配合合理的索引设计，能避开 ORM 模型序列化的性能陷阱，同时让锁粒度更可控。 4. 降低隔离级别：在允许幻读的业务中，使用 READ COMMITTED 减少间隙锁。 5. 重试机制：在应用层捕获死锁异常（如 MySQL 错误码 1213），进行有限次重试。

PHP 实战示例与预防策略

以下代码演示了死锁重试逻辑：

function executeWithRetry($callback, $maxRetries = 3) {
    for ($i = 0; $i < $maxRetries; $i++) {
        try {
            return $callback();
        } catch (PDOException $e) {
            if ($e->errorInfo[1] == 1213 && $i < $maxRetries - 1) {
                usleep(100000 * ($i + 1));
                continue;
            }
            throw $e;
        }
    }
}

预防死锁还需注意：避免在事务中执行 `SELECT ... FOR UPDATE` 后长时间不提交；使用批量更新时按主键排序；监控死锁频率并设置告警。定期审查慢查询日志，消除全表扫描，能从源头减少锁竞争。结合业务特点调整锁等待超时参数 `innodb_lock_wait_timeout`，避免长时间阻塞。通过持续优化索引与事务边界，死锁将不再是不可控的故障。
