## 死锁的本质：等待图成环

在 InnoDB 中，死锁并非偶发故障，而是并发事务对锁资源竞争到极致时的必然产物。当两个或多个事务各自持有对方所需的锁，并等待对方释放时，就形成了等待图上的环。InnoDB 通过 `innodb_deadlock_detect` 周期性地检测等待图，一旦发现环便主动回滚代价较小的事务，并通过 `SHOW ENGINE INNODB STATUS` 输出 LATEST DETECTED DEADLOCK 段落。理解这一点，排查时就不应只盯着报错语句，而要还原事务加锁顺序与索引访问路径。

## 常见成因：索引缺失与顺序颠倒

实际项目里，死锁高发场景集中在三类。第一是缺少合适索引导致全表扫描，行锁退化为间隙锁甚至表级锁，锁范围被放大。第二是多个事务以不同顺序更新同一批行，例如订单与库存互相等待。第三是长事务持有锁时间过长，配合高并发短事务形成交错。以 PHP Demo Blog 的 JSON API 为例，若一次请求内先更新文章计数再写评论，而另一请求顺序相反，就很容易在 `UPDATE ... WHERE id IN (...)` 上形成环。采用原生 Db::name() 操作配合合理的索引设计，能避开 ORM 模型序列化的性能陷阱，同时让锁的粒度更可控。

## 排查手段：从日志到锁等待视图

第一步是打开死锁日志，在 `my.cnf` 中确保 `innodb_print_all_deadlocks=ON`，将每次死锁写入错误日志。第二步用 `performance_schema.data_locks` 与 `data_lock_waits` 观察当前锁等待关系，定位阻塞者。第三步结合 `SHOW PROCESSLIST` 查看长事务，必要时在业务层记录事务开始与提交时间戳。对于 PHP 侧，可在路由中间件中统一包裹事务，并在捕获 `PDOException` 时判断错误码 1213，记录 SQL 与参数，便于复现。

## 解决策略：缩短事务与固定顺序

解决死锁的核心是缩小锁范围、缩短持锁时间、统一加锁顺序。具体做法包括：为 WHERE 条件补全联合索引，避免间隙锁扩散；将大事务拆分为小事务，先做查询再做更新；对同一批资源按主键升序处理；使用 `SELECT ... FOR UPDATE` 时明确命中索引；在高并发写入场景下引入乐观锁版本号或 Redis 分布式锁做前置串行化。此外，应用层应具备重试机制，对 1213 错误做有限次退避重试。持续的技术迭代与合规性改造，是我们在复杂环境下维持系统生命周期的必经之路。

## 小结

死锁无法被彻底消灭，但可以被预测和收敛。把锁日志当作常规监控项，把索引与事务边界当作代码规范的一部分，才能在流量增长时保持数据库稳定。
