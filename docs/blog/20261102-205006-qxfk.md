## 防抖与节流的核心差异

防抖（debounce）和节流（throttle）是前端控制函数执行频率的两种基础手段，但适用场景截然不同。防抖在事件被触发后延迟执行，若在延迟期内再次触发则重新计时，适合输入框搜索联想、窗口 resize 结束后的布局计算等「只关心最终状态」的场景。节流则保证函数在指定时间间隔内最多执行一次，适合滚动加载、拖拽跟随、按钮防重复点击等「需要持续反馈但频率可控」的场景。理解这一差异是选对方案的前提。

## 防抖的实战实现与边界处理

一个可直接落地的防抖函数需要处理三个细节：立即执行选项、取消能力、以及 this 与参数的透传。例如在搜索框场景中，用户停止输入 300ms 后才发起请求，可避免每个字符都触发一次 API 调用。实现时用闭包保存定时器句柄，返回的函数上挂载 cancel 方法以便组件卸载时清理。需注意：若回调内部依赖事件对象，应在事件处理函数中先提取所需字段再传入防抖函数，避免异步访问已被回收的事件对象。对于需要首次立即执行的场景（如按钮提交），增加 immediate 参数，在定时器为空时先执行一次。

## 节流的两种实现路径

节流常用时间戳与定时器两种写法。时间戳版本在首次触发时立即执行，适合滚动位置上报；定时器版本保证最后一次触发后仍有一次执行，适合拖拽结束时的状态同步。更稳妥的做法是结合两者：用时间戳控制执行节奏，用定时器兜底最后一次调用。在滚动加载场景中，将节流间隔设为 100ms 至 200ms，并在回调中通过 getBoundingClientRect 判断元素是否进入视口，可显著降低滚动事件的处理次数。若项目已使用 requestAnimationFrame，也可用其替代定时器实现节流，使执行节奏与浏览器渲染帧对齐。

## 与整体性能策略的配合

防抖与节流并非孤立手段。在关键渲染路径优化中，延迟非核心脚本的执行时机，再配合事件层面的频率控制，能更稳定地改善交互响应指标。对于图片懒加载，滚动监听应使用节流而非防抖，否则用户持续滚动时回调可能长时间不触发。同时，所有事件监听都应在组件销毁时移除，防抖函数的定时器也要显式取消，避免内存泄漏。将这些细节纳入代码规范，才能让优化方案在长期迭代中保持有效。
