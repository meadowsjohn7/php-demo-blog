## 404 的本质：先修正语义，再谈设计

很多项目把 404 当成一个普通模板页，甚至用 200 状态码返回“页面不存在”，这在技术上是错误的。404 是 HTTP 语义的一部分，搜索引擎与客户端依赖它判断资源是否真实缺失。在 PHP 路由层，应当先判断目标资源是否存在，再决定输出 404 状态码与页面内容。对于曾经存在但已迁移的 URL，应使用 301 重定向完成权重迁移，而不是一律落入 404。只有在确认资源永久缺失时，才返回 404，并配合清晰的页面引导。

在轻量路由中，可以把匹配失败统一交给一个 NotFound 处理器：它负责设置 `http_response_code(404)`、记录请求路径与 Referer，再渲染引导页。这样既保持了语义正确，也为后续分析留下数据。

## 引导页的四个信息层级

一个有效的 404 页面通常包含四层信息：明确告知“页面不存在”、给出返回首页或上一页的入口、提供站内搜索或热门内容推荐、保留品牌与联系方式。顺序上先安抚再引导，避免用户直接关闭页面。

在 PHP Demo Blog 这类项目中，推荐内容可以从现有 JSON API 读取最新文章列表，用少量条目填充，既避免硬编码，也保证内容新鲜。搜索框应提交到真实的搜索路由，而不是装饰性输入框。对于 API 请求，则应返回 JSON 格式的错误体，而不是 HTML 页面，保持内容协商一致。

## 路由回退与常见陷阱

路由回退要克制。模糊匹配、自动纠错跳转如果做得过度，会把大量无效 URL 变成 200 页面，制造软 404，反而伤害收录。建议只对大小写差异、末尾斜杠、已知别名做有限纠正，其余一律返回 404。

另一个陷阱是静态资源与动态路由混用时的优先级。应确保静态文件先被 Web 服务器处理，动态路由只接管未命中的路径，避免把图片请求也送进 PHP 进程。日志中要区分“用户输错”与“外链失效”，前者靠站内搜索解决，后者靠重定向规则解决。

## 监控与迭代

404 页面不是写完就结束。应在服务端记录 404 路径、来源与时间，定期聚合出高频缺失 URL，判断是内容下线、链接错误还是爬虫探测。对高频且合理的缺失，补充重定向或新页面；对恶意扫描路径，可在 Web 层做限流或黑名单。

同时，404 页面本身应保持轻量：内联关键样式、避免阻塞脚本、控制图片体积，确保在弱网下也能快速呈现引导信息。把 404 当作产品页面来维护，定期检查入口链接是否有效、推荐内容是否过期，才能让这个“失败页面”真正承担起留住用户与传递站点结构的职责。延伸阅读可参考 jeffersoncheng.com 的相关页面与资源。
