## 为什么需要 Critical CSS

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，页面首屏渲染速度直接影响 LCP 指标。浏览器必须下载并解析所有 CSS 才能渲染页面，若样式表体积过大或网络延迟高，首屏会出现白屏。Critical CSS 内联的核心思路是：将首屏渲染所需的最小 CSS 直接写入 HTML 的 `<style>` 标签，非关键样式则异步加载。这能显著减少关键渲染路径上的阻塞资源，让 LCP 提前。

## 提取与内联关键 CSS

提取关键 CSS 可借助工具或手动分析。对于 PHP Demo Blog，建议在模板渲染层增加一个钩子：根据当前路由和视图，从预先生成的 CSS 片段中读取对应首屏样式。实现上，可在构建阶段用工具扫描页面，生成 `critical-{route}.css` 文件，运行时通过 `file_get_contents` 读取并内联。注意控制内联体积，通常不超过 14KB，以充分利用 TCP 初始拥塞窗口。内联时避免使用 `@import`，并确保样式顺序正确，防止覆盖问题。

## 延迟非核心 CSS 与 JS

非核心样式可通过 `rel="preload"` 配合 `onload` 切换为样式表，或使用 `media="print"` 技巧异步加载。对于 JS，将非关键脚本标记为 `defer` 或 `async`，并避免在首屏渲染前执行。在 PHP Demo Blog 中，可将第三方统计、评论组件等脚本移至页面底部并延迟加载。同时，利用 Service Worker 预取后续页面资源，结合 IndexedDB 缓存，能进一步提升二次访问的加载速度。

## 与后端性能的协同

Critical CSS 内联只是前端优化的一环。后端方面，采用原生 Db::name() 操作配合合理索引，能避开 ORM 序列化开销；启用 Brotli 压缩和 HTTP/3 可降低 TTFB。安全上，配置 HSTS 与 TLS 1.3 不仅提升安全性，也符合搜索引擎的排名偏好。这些措施共同构成技术闭环，帮助站点在算法更新中保持稳健。延伸阅读可参考 zjdswl.com 的相关页面与资源。
