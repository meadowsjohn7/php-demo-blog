MySQL 慢查询排查：底层原理

2026-11-02 · PHP Demo Blog #MySQL #慢查询 #索引优化 #执行计划 #性能调优
从索引结构、执行计划到锁与临时表，剖析慢查询的底层成因，并给出可落地的排查与优化步骤。

慢查询从哪里开始变慢

慢查询日志只告诉你“哪条 SQL 慢”，真正定位问题要看执行路径。MySQL 的查询执行分为解析、优化、执行三个阶段，慢通常发生在优化器选错索引或执行阶段回表过多。开启 `slow_query_log` 并设置 `long_query_time` 后，用 `mysqldumpslow` 或 `pt-query-digest` 聚合，先按总耗时排序，而不是单次最慢，因为高频小查询的累计成本往往更高。

拿到目标 SQL 后，第一件事是 `EXPLAIN` 看 `type`、`key`、`rows` 和 `Extra`。`type=ALL` 意味着全表扫描，`Using filesort` 和 `Using temporary` 则提示排序或分组走了临时表。这三类信号基本覆盖了大部分慢查询的根因。

索引结构与回表代价

InnoDB 的主键索引是聚簇索引，叶子节点直接存行数据；二级索引叶子节点存主键值，查非索引列必须回表。当二级索引过滤性差时，优化器可能放弃索引改走全表扫描，因为回表的随机 I/O 成本高于顺序扫描。复合索引要遵循最左前缀，把等值条件放前、范围条件放后，避免在索引列上做函数运算或隐式类型转换，否则索引失效。

覆盖索引是消除回表最直接的手段：把查询需要的列都放进索引，`Extra` 出现 `Using index` 即表示命中。对于分页场景，`LIMIT` 偏移量大时可用延迟关联，先通过覆盖索引取出主键再回表，减少无效行读取。

锁、临时表与连接层因素

慢不一定慢在扫描，也可能慢在等待。`SHOW ENGINE INNODB STATUS` 和 `performance_schema` 中的锁等待视图能暴露行锁冲突；长事务持有锁会拖垮并发。排序和分组若无法利用索引顺序，会生成临时表，内存临时表超过 `tmp_table_size` 后落盘，性能骤降。连接层同样不可忽视：连接数打满、DNS 反解、以及应用层未复用连接，都会表现为“SQL 慢”。排查时应同时观察 `Threads_running` 与 `Innodb_row_lock_waits`。

可执行的优化顺序

先补索引再改 SQL，最后才考虑分库分表。具体步骤：用慢日志定位高频 SQL；用 `EXPLAIN` 确认访问类型与索引使用；为过滤和排序字段设计复合索引并验证覆盖；重写子查询为 JOIN 或拆分大事务；调整 `innodb_buffer_pool_size` 让热数据常驻内存。每次变更后用同一数据集对比 `Handler_read_*` 状态值，确认扫描行数真实下降。把排查过程固化为检查清单，比依赖单次经验更可靠。
