## 权限隔离与最小化原则

Cron 的安全隐患往往始于权限过宽。建议为每个定时任务分配独立的系统用户，避免使用 root 直接运行脚本。通过 `/etc/cron.d/` 下的文件显式指定执行用户，并确保文件权限为 `644`、属主为 root，防止普通用户篡改。对于仅需读取数据的任务，使用 `nobody` 或专用低权限账户，并在脚本内通过 `set -euo pipefail` 强化错误处理。同时，利用 `cron.allow` 与 `cron.deny` 限制可创建任务的用户范围，从入口处收敛攻击面。

## 脚本加固与路径安全

Cron 执行环境与登录 Shell 差异明显，PATH 通常极简，这既是兼容性问题也是安全风险。务必在 crontab 顶部显式声明 `PATH` 与 `SHELL`，并避免在脚本中直接调用相对路径命令。所有外部输入（如从数据库或 API 获取的参数）必须经过白名单校验，禁止拼接进 `eval` 或 `curl | bash` 管道。涉及文件操作时，使用 `mktemp` 创建临时文件并设置 `umask 077`，防止敏感数据落盘后被其他用户读取。若任务需调用网络接口，优先使用带证书校验的客户端，并避免在命令行参数中明文传递令牌。

## 日志审计与异常监控

Cron 默认将输出邮寄给用户，但在生产环境中应重定向到集中日志。建议在 crontab 中将标准输出与错误输出追加到带时间戳的日志文件，例如 `>> /var/log/cron/task.log 2>&1`，并配合 logrotate 控制体积。对于关键任务，可在脚本末尾写入执行状态码到独立文件，再由监控系统采集。定期审计 `/var/spool/cron/` 与 `/etc/cron.*` 的变更，结合 `auditd` 监控 crontab 文件的写入事件，能及时发现未授权的任务注入。

## 密钥与敏感信息管理

绝对避免在 crontab 或脚本中硬编码数据库密码、API Key。推荐使用系统级密钥管理方案，如通过 `systemd` 的 `EnvironmentFile` 加载权限为 `600` 的环境变量文件，或在脚本运行时从受控的配置中心拉取短期凭证。对于必须落地的凭据，使用 `gpg` 加密后由任务解密到内存文件系统（tmpfs），任务结束立即清除。此外，定期轮换密钥并回收离职人员相关的任务账户，是维持长期安全基线的重要环节。

遵循上述规范，Cron 不再是运维盲区，而成为可审计、可隔离的可靠调度组件。
