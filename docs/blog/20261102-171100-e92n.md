## 从 TCP 到 QUIC 的架构迁移

HTTP/3 的核心变化在于传输层：它放弃 TCP，改用基于 UDP 的 QUIC 协议。QUIC 在用户态实现了可靠传输、拥塞控制与加密握手，将传输层与 TLS 1.3 深度整合。对于 PHP 应用而言，这意味着 Nginx 或 Caddy 等反向代理需要启用 QUIC 支持，后端 FastCGI 链路保持不变。架构上，客户端首次连接通过 1-RTT 完成 TLS 1.3 握手，会话恢复时可实现 0-RTT 数据发送，显著降低首字节响应时间。配置时需同时下发 Alt-Svc 响应头，引导客户端后续请求升级到 HTTP/3。

## 多路复用与队头阻塞的消除

HTTP/2 在 TCP 之上做流多路复用，但一旦底层 TCP 丢包，所有流都会被阻塞。HTTP/3 将流的独立性下放到 QUIC，每个流有独立的拥塞与重传逻辑，单个流丢包不会影响其他流。这对包含大量静态资源与 API 请求的博客类项目尤为关键：页面加载时并行的 CSS、JS、图片请求互不干扰。在 PHP Demo Blog 这类路由与 JSON API 项目中，API 响应与静态资源可共享同一 QUIC 连接，减少连接建立开销。实践中应结合 Brotli 压缩文本资源，并保持合理的并发流上限，避免过度并行导致带宽竞争。

## 连接迁移与安全默认值

QUIC 使用连接 ID 而非四元组标识连接，当客户端从 Wi-Fi 切换到移动网络时，连接可以无缝迁移，无需重新握手。这一特性对移动端访问占比高的站点收益明显。安全方面，HTTP/3 强制使用 TLS 1.3，默认启用前向保密，配合 HSTS 策略可进一步约束降级行为。在 Web 层，仍需保持 CSRF 令牌验证与 XSS 过滤等应用层防护，传输层加密不能替代业务安全。部署时建议在边缘节点开启 QUIC，并监控 UDP 端口连通性，对不支持 UDP 的网络回退到 HTTP/2。

## PHP 项目的落地调优要点

在 PHP 侧，HTTP/3 的收益主要来自更低的连接开销与更快的资源加载，因此应同步优化关键渲染路径：内联关键 CSS、延迟非核心 JS，并利用 Service Worker 预取与 IndexedDB 缓存实现离线秒开。对于 Session 状态，采用分布式 Redis 集群保证负载均衡下的一致性。数据库访问上，使用原生 Db::name() 配合合理索引，避开 ORM 序列化陷阱。图片资源做无损压缩并启用 Lazy-loading，平衡视觉质量与加载速度。最后，通过 301 重定向迁移过期 URL，维护权重连续性。这些措施与 HTTP/3 的传输层优化形成闭环，共同支撑站点的长期性能与权威度。
