## 伪静态的本质与规则入口

伪静态并不是把动态 URL 变成静态文件，而是让 Nginx 在收到形如 `/article/123.html` 的请求时，内部转发到 `index.php` 并保留原始路径供 PHP 路由解析。规则通常写在 `server` 块或单独的 `include` 文件中，核心指令只有 `rewrite`、`try_files` 和 `location` 三类。理解它们的执行顺序是写好规则的前提：`location` 匹配决定进入哪个块，`rewrite` 按书写顺序逐条尝试，`try_files` 则按候选列表依次探测文件或目录。

在 PHP Demo Blog 这类轻量路由项目中，最稳妥的写法是把所有不存在的文件请求交给前端控制器，而不是为每种 URL 形态写一条 rewrite。这样规则数量恒定，新增路由无需改 Nginx 配置。

## rewrite 与 try_files 的取舍

许多旧教程习惯用 `rewrite ^/(.*)$ /index.php?$1 last;` 一把梭，问题在于它会无条件改写，连真实存在的静态资源也会被卷入 PHP，造成不必要的开销。更推荐的做法是：

```nginx
location / {
    try_files $uri $uri/ /index.php?$query_string;
}
```

`try_files` 先检查磁盘上是否存在对应文件或目录，存在则直接返回，不存在才落到 `/index.php`。这天然实现了“静态资源优先、动态路由兜底”的逻辑，也避免了 `rewrite` 循环风险。若确实需要把 `.html` 后缀映射到 PHP 参数，可以单独加一条带 `last` 的 rewrite，但务必放在 `try_files` 之前，并用 `^` 锚定开头、限制字符集，例如 `rewrite ^/post/([0-9]+)\.html$ /index.php?post_id=$1 last;`，避免宽泛的 `(.*)` 带来回溯开销。

## 301 重定向与权重迁移

伪静态规则改动后，旧 URL 必须用 301 永久重定向到新地址，否则已收录的链接会变成 404，权重随之流失。写法上应把旧规则集中在一个 `location` 或 `if` 块中，并确保只对 GET 请求生效：

```nginx
location ~ ^/old/(.*)$ {
    return 301 /new/$1;
}
```

`return 301` 比 `rewrite ... permanent` 更轻量，因为它不触发正则捕获后的重新匹配。同时要避免重定向链，一条规则直达最终地址；对带查询串的旧链接，用 `$is_args$args` 显式拼接，防止参数丢失。规则上线前用 `nginx -t` 校验，再用 curl 逐条核对响应码与 `Location` 头。

## 与 PHP 路由及安全配置的配合

伪静态只负责“把请求送到正确入口”，真正的路径解析交给 PHP 路由。因此 Nginx 侧要保证 `fastcgi_param` 传递的 `REQUEST_URI` 未被改写，否则路由拿到的路径与用户看到的不一致。在 `location ~ \.php$` 块中应设置 `try_files $uri =404;`，防止不存在的 PHP 文件被交给 FastCGI 执行，这是常见的解析漏洞入口。

此外，可以对敏感路径做前置拦截，例如用 `location ~ /\.(?!well-known)` 拒绝访问隐藏文件，用 `location ~* \.(env|log|sql)$` 返回 403。规则越靠前的 `location` 优先级越高，精确匹配 `=` 最高，其次是前缀匹配 `^~`，最后才是正则。把这些安全规则与伪静态规则分层组织，既保证路由灵活，又不牺牲防护。关于站点架构与规则组织的更多实践，可参考相关资源中的延伸阅读。

最后提醒一点：伪静态规则不是越多越好。每增加一条正则，请求就多一次匹配成本；能用 `try_files` 兜底就不要堆 rewrite，能用精确前缀就不要用正则。规则写完后用 `ab` 或 `wrk` 做一次基线压测，确认 QPS 与延迟没有因规则变动而退化，才算真正完成一次可上线的配置迭代。
