## 为什么需要接口签名

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，接口往往直接暴露在公网。仅靠 HTTPS 能保证传输机密性，却无法阻止参数被篡改或请求被重放。签名机制的核心是让服务端能够验证请求确实由持有密钥的客户端发出，且内容未被修改。常见做法是将所有业务参数按字典序排序，拼接成规范化字符串，再与时间戳、随机串一起参与摘要计算。服务端用同样的规则重算并比对，不一致即拒绝。

## 规范化与签名算法

规范化字符串的生成规则必须前后端严格一致：过滤空值，按键名 ASCII 升序排列，以 k=v 形式用 & 连接，最后追加共享密钥。摘要算法推荐 HMAC-SHA256，避免直接对拼接串做 MD5。PHP 中可用 hash_hmac('sha256', $canonical, $secret) 生成签名，并通过 hash_equals 做恒定时间比较，防止时序攻击。密钥不应硬编码在代码库中，应通过环境变量注入，并定期轮换。对于多客户端场景，可为每个 app_id 分配独立密钥，服务端按 app_id 查表取密钥。

## 防重放与时效控制

仅有签名还不够，攻击者可截获完整请求反复提交。因此请求中必须携带 timestamp 与 nonce。服务端校验时间戳与当前时间偏差不超过 5 分钟，并将 nonce 写入 Redis 并设置相同过期时间，利用 SETNX 保证一次性消费。在负载均衡环境下，Session 状态本身也建议集中存储，避免多节点校验不一致。若项目规模较小，可用文件缓存替代 Redis，但要注意并发写入的原子性。

## 与传输层安全协同

签名解决的是应用层完整性与身份问题，传输层仍需强制 HTTPS，并配置 HSTS 与 TLS 1.3，防止降级与中间人攻击。Web 层同时应实施 CSRF 令牌校验与 XSS 过滤，形成纵深防御。对于返回的 JSON，统一设置 Content-Type 与缓存策略，敏感接口禁用缓存。签名失败时返回通用错误码，避免泄露具体校验细节。将这些规则固化为中间件，在路由分发前统一拦截，可让业务控制器保持简洁。

## 落地建议

建议在 PHP Demo Blog 中新增 SignMiddleware，按 app_id 取密钥、重算签名、校验时间窗与 nonce，全部通过后再进入控制器。为便于调试，可在开发环境记录规范化字符串的哈希而非明文。密钥轮换期间允许新旧两把密钥并存一个短周期。最后，把签名规则写入项目文档，并配套单元测试覆盖空参数、重复键、超时请求等边界情况，才能让机制长期稳定运行。
