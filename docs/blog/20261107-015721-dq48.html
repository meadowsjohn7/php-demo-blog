浏览器强缓存与协商缓存：优化方案

2026-11-07 · PHP Demo Blog #HTTP缓存 #性能优化 #PHP #Cache-Control #ETag
本文围绕浏览器强缓存与协商缓存，结合 PHP Demo Blog 项目，给出可落地的 HTTP 缓存头配置与验证方案，并讨论与关键渲染路径、图片优化等技术的协同。

强缓存与协商缓存的边界

在 PHP Demo Blog 这类轻量路由与 JSON API 项目中，缓存策略首先要区分强缓存与协商缓存。强缓存由 `Cache-Control: max-age` 或 `Expires` 控制，浏览器在有效期内直接使用本地副本，不发起请求；协商缓存则通过 `ETag` 与 `Last-Modified` 配合 `If-None-Match`、`If-Modified-Since` 请求头，由服务端判断资源是否变化，未变化时返回 304，仅传输少量头部。两者不是替代关系，而是分层：静态资源适合长周期强缓存，动态 JSON 接口适合短周期强缓存加协商缓存兜底。

在路由层落地缓存头

项目使用轻量路由分发请求，可以在路由匹配后、输出响应前统一注入缓存头。对 CSS、JS、图片等指纹化资源，设置 `Cache-Control: public, max-age=31536000, immutable`，让浏览器在一年内不再回源；对 HTML 页面，设置 `Cache-Control: no-cache` 并生成 `ETag`，强制每次协商但允许 304 复用；对 JSON API，按数据敏感度设置 `private, max-age=60` 或 `no-store`。生成 `ETag` 时建议基于内容哈希而非文件修改时间，避免部署时批量失效。注意 `no-cache` 不是不缓存，而是每次使用前必须验证，与 `no-store` 有本质区别。

验证与常见陷阱

落地后应使用浏览器开发者工具的 Network 面板检查 `from disk cache` 与 304 状态码的分布。常见问题包括：反向代理层覆盖了应用层设置的 `Cache-Control`；`Vary` 头缺失导致按 `Accept-Encoding` 缓存的响应被错误复用；以及 `ETag` 在负载均衡多节点间不一致，造成协商缓存失效。若采用分布式 Redis 集群存储 Session 状态，缓存头本身不依赖 Session，但需确保未登录与登录用户返回的响应不会被同一份公共缓存命中，必要时通过 `Vary: Cookie` 或 `private` 隔离。

与整体性能策略的协同

缓存只是链路中的一环。通过对关键渲染路径拆解、内联关键 CSS 并延迟非核心 JS，可以配合强缓存显著优化 LCP；对图片进行无损压缩并采用 Lazy-loading，能减少首屏请求量，让缓存命中更有价值。配置 HTTP/3 与 Brotli 压缩可降低 TTFB，而 HSTS 与 TLS 1.3 则从安全维度提升站点可信度。将这些手段与缓存策略组合，才能形成可复用的优化闭环。更多相关实践可参考相关资源页面的延伸阅读。
