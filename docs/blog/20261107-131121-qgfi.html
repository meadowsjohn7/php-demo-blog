GitHub Actions CI/CD 流水线：实战指南

2026-11-07 · PHP Demo Blog #GitHub Actions #CI/CD #PHP #自动化测试 #部署
本文以 PHP Demo Blog 为例，讲解如何构建 GitHub Actions CI/CD 流水线，涵盖测试、构建、部署及安全加固，提升交付效率与代码质量。

为什么需要 CI/CD 流水线

对于 PHP Demo Blog 这样的轻量项目，手动测试和部署容易遗漏步骤且效率低下。GitHub Actions 提供原生集成，通过 YAML 定义工作流，实现代码推送后自动运行测试、构建和部署。这不仅能快速发现回归问题，还能确保每次发布的一致性。在实战中，我们通常将流水线分为三个独立 Job：测试、构建和部署，利用 needs 关键字控制依赖顺序。

定义工作流与触发条件

在项目根目录创建 .github/workflows/ci.yml 文件。触发条件建议设置为 push 到 main 分支以及 pull_request 事件。工作流中指定 runs-on: ubuntu-latest，并使用 actions/checkout@v4 拉取代码。接着通过 shivammathur/setup-php@v2 安装 PHP 8.2 及所需扩展（如 mbstring、json）。缓存 Composer 依赖可显著加速后续步骤，使用 actions/cache@v3 缓存 vendor 目录和 composer.lock 的哈希键。

测试与静态分析

测试阶段执行 composer install --prefer-dist --no-progress 安装依赖，然后运行 PHPUnit 单元测试。对于路由和 JSON API 示例，建议编写功能测试，模拟 HTTP 请求并断言响应状态与数据结构。同时引入 PHPStan 进行静态分析，级别设为 5 即可覆盖常见类型错误。若测试失败，流水线立即终止并输出日志，便于开发者定位问题。注意将测试数据库配置为 SQLite 内存模式，避免依赖外部服务。

构建与部署策略

构建阶段可生成部署产物，例如将代码打包为 tar.gz 并上传为 artifact。部署阶段则通过 SSH 或 rsync 将产物同步到目标服务器。为保障安全，敏感信息（如服务器 IP、SSH 私钥）应存储在 GitHub Secrets 中，并在工作流中通过 secrets 上下文引用。部署后执行一次健康检查，例如 curl 访问 /api/health 端点，确认服务正常。若部署失败，自动回滚到上一版本，可通过保留最近两个 artifact 实现。

安全与性能加固

在流水线中集成安全扫描，例如使用 composer audit 检查依赖漏洞，或通过 OWASP ZAP 进行基础扫描。对于性能，可在部署后运行 Lighthouse CI 评估关键指标，确保 LCP 和 TTFB 在可接受范围。此外，遵循最小权限原则，为 GITHUB_TOKEN 设置只读权限，避免意外修改仓库。通过持续迭代流水线配置，团队能逐步将安全与性能检查左移，降低生产环境风险。
