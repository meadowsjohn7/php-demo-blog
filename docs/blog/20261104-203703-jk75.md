## 连接建立：控制连接与工作连接的分工

frp 的底层模型可以概括为“一条控制连接 + 多条工作连接”。客户端启动后先依据配置向服务端的 bind_port 发起一条长连接，这条控制连接只承载登录认证、心跳与指令，不传输业务数据。认证通过后，客户端把本地要暴露的服务（例如 PHP Demo Blog 的 8080 端口）注册到服务端，服务端据此在 remote_port 上监听公网请求。当外部用户访问服务端端口时，服务端通过控制连接下发一条“新建工作连接”的指令，客户端再主动向服务端建立一条新的 TCP 连接，由服务端把这条连接与用户连接做双向管道对接。理解这一点很关键：业务流量走的是工作连接，控制连接只负责调度，两者分离使得心跳与业务互不阻塞。

## 多路复用：一条隧道承载多个请求

早期实现中每个用户请求都要新建一条工作连接，连接数随并发线性增长。现代 frp 引入多路复用（mux）后，客户端与服务端之间只需维持少量底层连接，在其上按流 ID 划分逻辑流，HTTP 请求、TCP 会话都被封装成独立的流。对 PHP Demo Blog 这类以短连接为主的 JSON API 尤其友好：大量小请求共享同一条加密隧道，避免了频繁三次握手与 TLS 协商的开销，首字节响应时间明显下降。需要注意 mux 与部分老旧中间件存在兼容问题，若出现连接被重置，可先关闭多路复用做对照排查。

## 心跳保活与超时控制

内网穿透最怕的是 NAT 设备静默回收映射表项，导致连接看似存在实则已断。frp 通过 heartbeat_interval 与 heartbeat_timeout 两个参数维持链路：客户端按间隔发送心跳，服务端在超时时间内未收到即判定连接失效并清理资源。实战中建议心跳间隔不要大于 30 秒，同时把服务端的 tcp_keepalive 打开作为兜底。对于 PHP 侧的长轮询或 SSE 接口，还要在 Web 服务器上适当调大读超时，避免 frp 已保活而应用层先断开。

## 加密隧道与访问控制

frp 支持在控制连接与工作连接上启用 TLS，配合 token 认证可防止隧道被未授权复用。若服务端部署在公网，建议同时开启 tls_only 并只信任指定证书，避免明文握手被中间人利用。访问控制层面，可用 allow_ports 限制可映射的远程端口范围，用 subdomain 配合 HTTP 类型做基于域名的路由，再在 Nginx 层叠加限流与来源校验。把 frp 当作传输层，把认证、限流、日志留给反向代理与应用本身，职责清晰，排障也更容易。
