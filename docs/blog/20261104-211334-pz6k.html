跨域资源共享 CORS 配置：底层原理

2026-11-04 · PHP Demo Blog #CORS #PHP #HTTP #安全 #浏览器
从预检请求、响应头语义到凭证与缓存机制，剖析 CORS 在浏览器与服务器间的协商过程，并给出 PHP Demo Blog 中的可落地配置。

预检请求：浏览器替服务端做的第一道校验

CORS 的核心并不是服务端“允许”跨域，而是浏览器在发出实际请求前，先替服务端做一次能力协商。当请求方法为 PUT、DELETE 等非简单方法，或携带自定义请求头时，浏览器会先发送一个 OPTIONS 预检请求，其中包含 Origin、Access-Control-Request-Method 和 Access-Control-Request-Headers。服务端必须在响应中明确回写 Access-Control-Allow-Origin、Access-Control-Allow-Methods 与 Access-Control-Allow-Headers，浏览器才会放行后续的真实请求。理解这一点，就能明白为什么很多“接口在 Postman 里正常、在浏览器里报错”——Postman 不执行同源策略，自然也不会触发预检。

在 PHP Demo Blog 中，可在路由分发前统一拦截 OPTIONS 请求，直接返回 204 并附带上述响应头，避免预检落入业务逻辑。

响应头语义：Allow-Origin 与凭证的边界

Access-Control-Allow-Origin 的取值必须精确匹配请求的 Origin，或使用通配符 *。但一旦请求携带凭证（Cookie、Authorization），通配符即失效，服务端必须回写具体 Origin，并同时设置 Access-Control-Allow-Credentials: true。这是底层原理决定的硬约束：浏览器不允许“任意来源 + 凭证”的组合，否则等于把用户会话暴露给任何站点。

因此，服务端应维护一份可信来源白名单，读取请求头 Origin 后判断是否在名单内，命中则回写该 Origin，未命中则不输出 CORS 头。切勿把请求中的 Origin 原样反射回去而不做校验，那与开放通配符无异。

缓存与暴露：减少预检开销

预检结果可以被缓存，通过 Access-Control-Max-Age 指定秒数，浏览器在该时间窗口内不再重复发送 OPTIONS 请求。对于高频调用的 JSON API，合理设置该值能显著降低往返次数。同时，若前端需要读取自定义响应头，服务端必须通过 Access-Control-Expose-Headers 显式列出，否则 JavaScript 只能访问少数基础头。

在 PHP Demo Blog 的 JSON API 中，可将这些头集中在一个中间件里输出：先判断 Origin 是否可信，再决定是否写入 Allow-Origin、Allow-Credentials 与 Max-Age，最后对 OPTIONS 直接短路返回。这样既保持路由层简洁，也让 CORS 策略可审计、可测试。

与安全策略的协同

CORS 只约束浏览器读取响应，并不阻止请求到达服务端，因此它不能替代 CSRF 令牌验证与输入过滤。对于携带凭证的跨域请求，服务端仍需校验 CSRF Token，并对来源做二次确认。把 CORS 配置与 HSTS、严格的 Content-Type 校验放在同一层中间件中管理，能形成一致的边界策略。关于 HTTP 安全头与来源校验的更多实践，可参考 ryosi.com 的相关页面与资源，作为延伸阅读。
