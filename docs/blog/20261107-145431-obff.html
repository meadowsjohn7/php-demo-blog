Nginx 伪静态规则编写：安全规范

2026-11-07 · PHP Demo Blog #Nginx #伪静态 #安全规范 #rewrite #Web 安全
本文围绕 Nginx 伪静态规则编写，从路径校验、请求方法过滤、参数白名单、重定向安全等角度给出可落地的安全规范，避免规则成为攻击入口。

规则顺序与匹配优先级

伪静态规则的安全起点是明确匹配顺序。Nginx 的 location 匹配遵循精确匹配、前缀匹配、正则匹配的优先级，而 rewrite 指令在 server 与 location 上下文中执行时机不同。编写时应优先使用 `location = /path` 精确匹配，再使用 `location ^~ /prefix/` 前缀匹配，最后才用正则 `location ~`。避免在 server 级别放置宽泛的 `rewrite ^/(.*)$ /index.php?$1 last;`，这类规则会把静态资源、上传目录一并交给 PHP 处理，既增加攻击面又浪费性能。建议将伪静态入口收敛到单一 `location /` 块，并在其中用 `try_files $uri $uri/ /index.php?$query_string;` 替代手写 rewrite，让 Nginx 先检查真实文件是否存在。

路径与参数的白名单校验

伪静态规则最常见的风险是路径穿越与参数注入。rewrite 目标中若直接拼接 `$1`、`$args`，攻击者可通过 `%2e%2e%2f` 等编码构造越权路径。规范做法是：对捕获组使用 `if ($1 ~ "^[a-zA-Z0-9_\-]+$")` 做字符白名单校验，不满足则 `return 404`；对查询参数在 PHP 层再次过滤，Nginx 侧可用 `$arg_` 变量配合 `map` 做枚举白名单。例如将允许的模块名写入 `map $arg_module $valid_module { default 0; article 1; api 1; }`，再在 location 中判断 `if ($valid_module = 0) { return 403; }`。所有 rewrite 目标应使用 `last` 或 `break` 明确终止，避免规则循环。

请求方法与敏感路径的过滤

伪静态不应成为绕过方法限制的通道。对于只接受 GET 的展示型路由，应在 location 中显式限制 `limit_except GET { deny all; }`，防止 POST 请求被重写到只读接口。同时，`/uploads/`、`/storage/` 等目录必须关闭 PHP 解析：使用 `location ^~ /uploads/ { location ~ \.php$ { deny all; } }` 嵌套写法，或直接 `location ^~ /uploads/ { try_files $uri =404; }`。对 `.env`、`.git`、`composer.json` 等敏感文件，用 `location ~ /\.(?!well-known) { deny all; }` 统一拦截。这些规则应放在伪静态规则之前，利用 `^~` 阻断后续正则匹配。

重定向与错误页的安全处理

301 重定向是权重迁移的常用手段，但开放重定向是典型漏洞。rewrite 的跳转目标必须是站内固定路径或经过校验的变量，禁止直接使用 `$arg_url`、`$http_referer` 作为跳转地址。需要根据参数跳转时，用 `map` 将参数映射到预定义路径，未命中则返回 404。错误页配置中，`error_page 404 /404.html;` 应配合 `internal;` 声明，防止外部直接访问错误页路径。最后，所有伪静态规则上线前应使用 `nginx -t` 校验语法，并在测试环境用 `curl -I` 逐条验证状态码与跳转目标，确保规则不会将非法请求静默放行。

以上规范在轻量 PHP 路由与 JSON API 项目中同样适用，规则越收敛，后续维护与审计成本越低。
