## 字体加载与渲染阻塞的本质

当浏览器解析到 @font-face 规则时，若字体文件尚未就绪，它必须决定：是先用后备字体渲染文本，还是等待字体下载完成。这个决策窗口由 font-display 控制，其底层依赖浏览器的字体加载状态机。状态机包含 block 期、swap 期和 failure 期，每个阶段对应不同的渲染行为。默认的 auto 等价于 block，即短时间隐藏文本（FOIT），超时后回退到后备字体。理解这些阶段的时间阈值（通常 block 期约 3 秒，swap 期无限长）是选择策略的前提。

## 五个取值的实际行为

font-display 接受 auto、block、swap、fallback、optional 五个值。block 在 block 期内隐藏文本，适合图标字体等必须准确显示的场景，但会拖慢首次内容绘制。swap 则立即用后备字体渲染，字体就绪后替换，产生 FOUT，对 LCP 最友好，但可能引起布局偏移。fallback 是折中：极短 block 期后使用后备字体，若字体在约 3 秒内到达则替换，否则本次页面生命周期不再替换。optional 更激进，浏览器可能完全放弃本次加载，仅在网络极快时使用自定义字体，适合非关键文本。auto 则交给浏览器启发式判断，通常等同于 block。

## 与关键渲染路径的联动

字体是渲染阻塞资源之一。若字体在首屏关键文本中使用，block 策略会推迟文本绘制，直接影响 LCP 指标。实践中，可将首屏字体预加载（preload）并配合 font-display: swap，让文本尽早可见；同时通过 size-adjust 和 ascent-override 等度量覆盖减少替换时的布局偏移。对于非首屏或装饰性字体，使用 optional 或 fallback 避免不必要的网络竞争。注意，font-display 只影响渲染时机，不改变下载优先级，因此仍需结合 preconnect 与合理的缓存策略。

## 策略选择与验证方法

选择策略时应先区分字体用途：品牌标题字体可接受短暂 FOIT，用 block 或 fallback；正文与 UI 字体优先 swap 保障可读性；图标字体建议内联为 SVG 或使用 block 并预加载。验证时，可在 Chrome DevTools 的 Performance 面板观察字体请求与文本绘制的时序，并利用 Lighthouse 检查 LCP 与 CLS 变化。对于多语言站点，还需考虑子集化（unicode-range）以缩小字体体积，让 swap 的替换窗口更短。最终策略应写入设计系统文档，避免不同页面随意取值导致体验不一致。
