## 缓存雪崩的成因与识别

缓存雪崩指大量缓存键在同一时间集中失效，请求瞬间穿透到数据库，导致后端负载飙升甚至宕机。常见诱因有三类：一是批量写入时统一设置了相同的 TTL；二是缓存服务重启或主从切换导致整体不可用；三是热点键过期后并发请求同时回源。在 PHP Demo Blog 这类轻量项目中，接口层往往直接使用 Redis 存储文章列表与详情，若初始化脚本对全部键统一设置 3600 秒过期，整点刷新时就会形成明显的流量尖峰。识别方法很直接：监控 Redis 的命中率曲线与数据库 QPS 是否在固定时间点同步抖动，并检查慢查询日志中是否出现大量相同的 SELECT。

## TTL 随机化与互斥锁

最基础的防护是打散过期时间。写入缓存时在基础 TTL 上叠加一个随机偏移，例如 `$ttl = 3600 + mt_rand(0, 600);`，让键的失效点均匀分布。对于无法避免的热点键，应引入互斥锁：回源前先用 `SET key value NX EX 10` 抢占锁，抢到的进程查询数据库并回填缓存，未抢到的进程短暂休眠后重试读缓存，从而把并发回源压缩为一次。PHP 中可用 `Redis::set($lockKey, 1, ['nx', 'ex' => 10])` 实现，注意在 finally 块中释放锁，避免死锁。锁的过期时间要略大于一次数据库查询的耗时上限。

## 多级缓存与逻辑过期

在应用进程内增加一层本地缓存（如 APCu 或进程内数组），可以吸收绝大部分读请求，Redis 只作为二级缓存。更进一步可采用逻辑过期方案：缓存值中携带一个过期时间戳，物理上不设置 TTL，读取时若发现逻辑过期，则异步触发一个后台刷新任务，当前请求仍返回旧值。这样既保证了响应速度，又避免了缓存击穿。对于文章详情这类读多写少的数据，该方案尤为合适；写操作发生时主动删除对应键，由下一次读请求重建。

## 降级与兜底

任何缓存方案都需要兜底。当 Redis 不可用或回源失败时，接口应返回预置的静态快照或空列表并附带重试提示，而不是让异常向上冒泡拖垮整个页面。可在 PHP 中封装一个统一的缓存读取函数，捕获连接异常后记录日志并走降级分支。同时为数据库连接池设置合理的最大连接数与超时，防止雪崩时连接耗尽。防护机制的价值不在于完全消除故障，而在于把故障的影响范围限制在可接受的区间内，并为恢复争取时间。
