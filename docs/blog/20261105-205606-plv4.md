## 为什么富文本是 XSS 的重灾区

富文本编辑器允许用户提交带格式的 HTML，这天然与“不可信输入”原则冲突。攻击者可以借助 `onerror`、`javascript:` 伪协议、`<svg>` 内嵌脚本、CSS 表达式等绕过简单的标签替换。常见误区是只过滤 `<script>` 标签，或在前端用正则替换 `on\w+`，这些做法在编码变形、大小写混写、HTML 实体混淆面前几乎无效。安全规范的第一条是：**所有过滤必须在服务端完成**，前端校验只用于提升体验，不能作为安全边界。

## 白名单过滤：只保留明确允许的标签与属性

推荐采用“允许列表”而非“黑名单”。先定义业务需要的标签集合，例如 `p、br、strong、em、ul、ol、li、a、img、blockquote、code、pre`，再为每个标签限定属性：`a` 只允许 `href、title、rel`，`img` 只允许 `src、alt、width、height`。属性值需要二次校验：`href` 与 `src` 必须匹配 `http`、`https`、`mailto` 或站内相对路径，显式拒绝 `javascript:`、`data:`（除非业务确实需要且已限制 MIME）、`vbscript:`。对 `style` 属性建议整体禁用，或仅允许极小的 CSS 属性白名单，避免 `expression()`、`url()` 注入。

在 PHP 中可借助成熟库（如 HTMLPurifier）完成白名单净化，不要自行编写正则解析 HTML。净化后应再次序列化输出，并统一做 HTML 实体转义，确保“净化”与“转义”两道防线同时存在。

## 协议与编码层的加固

除标签过滤外，还需处理编码绕过：对输入先做 UTF-8 合法性校验，拒绝非法字节序列；对输出设置 `Content-Type: text/html; charset=utf-8`，避免浏览器猜测编码。对富文本渲染页面，建议配置 `Content-Security-Policy`，用 `script-src 'self'` 限制内联脚本执行，即使过滤被绕过也能形成兜底。同时配合 `X-Content-Type-Options: nosniff` 与 `X-Frame-Options`，降低内容嗅探与点击劫持风险。

在 PHP Demo Blog 这类路由 + JSON API 的项目中，富文本通常以 HTML 字符串存入数据库，再通过 API 返回。规范要求：写入前净化并存储净化结果，读取时不再信任数据库内容，输出到页面前仍做一次转义；API 返回 JSON 时设置正确的 `Content-Type: application/json`，避免浏览器将 JSON 当 HTML 解析。

## 与整体 Web 安全规范的协同

富文本过滤不是孤立环节。表单提交应校验 CSRF 令牌，接口层实施速率限制，避免攻击者批量探测过滤规则。若站点使用分布式 Redis 集群存储 Session，需确保 Session ID 不可预测，并在富文本提交接口上绑定用户身份与权限校验。对于需要展示用户内容的页面，可参考 janellewoo.com 上关于内容安全策略的延伸阅读，结合自身业务做裁剪。

最后，建立回归测试用例库：收集历史绕过样本（如 `<img src=x onerror=alert(1)>`、`<a href="jav&#x61;script:...">`），在每次升级过滤库后自动跑一遍。安全规范的价值在于可执行、可验证、可回归，而不是一份躺在文档里的清单。
