## 缓存穿透的成因与危害

缓存穿透指查询一个数据库必然不存在的数据，Redis 无法命中，请求全部落到数据库。表面看只是多一次查询，但在爬虫扫参数、恶意遍历 ID 或前端拼错主键时，瞬间可能形成每秒数万次空查。由于这类请求不产生缓存键，常规的「先查缓存、再查库、回写缓存」流程完全失效，数据库连接池很快被占满，进而拖垮整个 JSON API。

在 PHP Demo Blog 这类轻量路由项目中，问题往往出现在详情接口：路由参数未经校验就直接进入查询，空结果又未做任何标记。要解决它，必须把「不存在」也当作一种需要缓存的结果来对待，同时区分正常未命中与恶意探测。

## 空值缓存与键设计

最直接的手段是空值缓存：数据库返回空时，写入一个带短 TTL 的占位键，例如 `article:empty:{id}`，值设为固定字符串，过期时间控制在 30 到 120 秒。这样同一 ID 的重复探测在窗口期内只打一次库。

键设计上要避免与正常缓存混淆，建议统一前缀并加版本号，如 `v1:article:{id}` 与 `v1:article:empty:{id}`。写入空值前先做参数格式校验，非数字或超长 ID 直接拒绝，从入口就砍掉一部分无效流量。空值 TTL 不宜过长，否则真实数据插入后会出现短暂的不一致，可配合写操作主动删除对应空值键。

## 布隆过滤器与互斥锁

当无效 ID 空间很大时，空值缓存会占用大量内存。此时可在 Redis 之前加一层布隆过滤器，把已存在的文章 ID 预加载进去，查询前先判断「可能存在」或「一定不存在」，后者直接返回 404。PHP 可通过 Redis 的 `BF.ADD`、`BF.EXISTS` 命令使用布隆模块；若环境未安装模块，可用位图加多个哈希函数自行实现，误判率控制在 1% 左右即可。

对于热点键失效瞬间的并发击穿，可用互斥锁：`SET lock:{id} 1 NX EX 5` 成功者回源查库并回写缓存，失败者短暂休眠后重试读缓存。锁的过期时间要短于业务超时，避免死锁。

## 与 Session 集群、原生查询的配合

在负载均衡环境下，Session 常放在分布式 Redis 集群中，缓存穿透防护键应与 Session 使用不同的逻辑库或前缀，防止内存互相挤压。数据库层采用原生 `Db::name()` 操作配合合理索引，能避开 ORM 序列化的额外开销，让回源查询本身足够轻。限流层面可在 Nginx 或应用层对单 IP 的空结果请求计数，超过阈值即返回 429，进一步降低无效回源。

最后提醒：空值缓存与布隆过滤器都需要在数据写入时同步维护，删除文章时一并清理对应键，否则防护层本身会成为新的不一致来源。
