## 问题的根源：高频事件与回调放大

在 PHP Demo Blog 这类轻量项目中，前端往往只承担少量交互，但一旦接入搜索联想、无限滚动或窗口尺寸监听，`input`、`scroll`、`resize` 等事件就会以每秒数十甚至上百次的频率触发回调。若回调内部包含 DOM 查询、数组遍历或网络请求，主线程会被持续占用，直接拖慢首屏交互与 LCP 指标。防抖（debounce）与节流（throttle）本质上是两种控制回调执行节奏的策略，前者合并连续触发，后者保证固定间隔内最多执行一次。

## 防抖：合并连续触发，只认最后一次

防抖适合“用户停止操作后才需要结果”的场景，例如搜索框联想、表单异步校验、窗口 resize 后重新计算布局。实现要点是每次触发都清除上一个定时器，并重新计时。下面是一个带立即执行选项的通用实现：

```js
function debounce(fn, wait = 300, immediate = false) {
  let timer = null;
  return function (...args) {
    const callNow = immediate && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      if (!immediate) fn.apply(this, args);
    }, wait);
    if (callNow) fn.apply(this, args);
  };
}
```

在搜索联想场景中，`wait` 建议取 250 到 400 毫秒，既能覆盖多数用户的连续输入间隔，又不会让响应显得迟滞。若回调中要发起 fetch 请求，还应在回调内部使用 `AbortController` 取消上一次未完成的请求，避免旧响应覆盖新结果。

## 节流：固定窗口内最多执行一次

节流适合“过程中需要持续反馈”的场景，例如滚动监听、鼠标移动、拖拽位置计算。常见实现有基于时间戳与基于定时器两种，前者保证首次立即执行，后者保证尾部执行。一个兼顾首尾的写法是：

```js
function throttle(fn, interval = 200) {
  let last = 0;
  let timer = null;
  return function (...args) {
    const now = Date.now();
    const remaining = interval - (now - last);
    if (remaining <= 0) {
      clearTimeout(timer);
      timer = null;
      last = now;
      fn.apply(this, args);
    } else if (!timer) {
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}
```

滚动监听中，节流间隔取 100 到 200 毫秒即可，配合 `requestAnimationFrame` 在回调内读取 `getBoundingClientRect`，可以避免布局抖动。注意不要在节流回调中直接修改样式，而应把读写操作分离，减少强制同步布局。

## 选型与落地：参数、清理与可观测性

选型判断可以归结为一句话：需要“最终态”用防抖，需要“过程态”用节流。落地时还有三个细节值得注意。其一，防抖与节流函数应返回带 `cancel` 方法的包装器，便于在组件卸载或路由切换时清除定时器，防止内存泄漏。其二，参数不要拍脑袋决定，可在开发环境用 `performance.now()` 记录回调执行次数与耗时，观察优化前后的差异。其三，对于输入框场景，可以把防抖与 `compositionstart`、`compositionend` 结合，避免中文输入法组合期间触发无效请求。将这些细节固化为项目内的工具函数，并在代码评审中统一约定，才能让优化方案长期可维护。
