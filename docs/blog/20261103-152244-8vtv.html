frp 内网穿透实战：底层原理

2026-11-03 · PHP Demo Blog #frp #内网穿透 #TCP 多路复用 #Go 网络编程
解析 frp 内网穿透的底层原理，从连接建立、多路复用到流控与安全，结合实战配置与性能调优。

连接建立与多路复用

frp 的核心在于解决无公网 IP 环境下的服务暴露问题。客户端 frpc 主动向服务端 frps 建立一条长连接，这条连接通常基于 TCP 或 KCP，并承载控制信令。控制连接建立后，双方通过自定义的二进制协议交换元数据，例如代理名称、类型、远程端口等。当外部用户访问 frps 的指定端口时，frps 并不直接转发，而是通过控制连接通知 frpc 建立一条新的工作连接。这条工作连接同样由 frpc 发起，以避免服务端主动连接内网带来的 NAT 穿透难题。

多路复用的关键在于 frp 使用了基于 smux 的流复用库，将控制信令与数据流统一承载在一条底层连接上。每个代理请求对应一个逻辑流，流内数据经过加密与压缩后传输。这种设计减少了连接建立的开销，同时让 NAT 映射保持稳定。在 frpc 侧，每个逻辑流会与本地服务端口建立独立的 TCP 连接，形成“外部请求 → frps 逻辑流 → frpc 逻辑流 → 本地服务”的完整链路。

协议栈与传输优化

frp 的协议栈分为三层：底层传输、流复用层和代理层。底层传输支持 TCP、KCP 和 WebSocket，其中 KCP 在丢包率较高的网络下能显著降低延迟，但会消耗更多带宽。流复用层基于 smux，负责流的创建、关闭和流量控制。代理层则处理 TCP、UDP、HTTP 和 HTTPS 等不同类型，HTTP 代理还会解析 Host 头以支持基于域名的路由。

在实战中，可以通过调整 frpc 的 `transport.tcpMux` 和 `transport.poolCount` 参数来平衡连接复用与并发性能。对于低延迟场景，启用 KCP 并配合 `kcp.tcp` 模式能减少握手时间。此外，frps 的 `maxPoolCount` 和 `vhostHTTPPort` 配置直接影响虚拟主机路由的效率。值得注意的是，frp 本身不提供 TLS 终止，若需加密，应在代理层配置 HTTPS 或在传输层启用 TLS。

流控、安全与可观测性

frp 在流级别实现了滑动窗口流控，防止单个代理耗尽带宽。每个逻辑流都有独立的发送与接收窗口，当窗口耗尽时，发送方会暂停写入，直到接收方确认。这种机制在共享带宽的场景下尤为重要，避免了大流量代理影响其他服务。

安全方面，frp 支持 token 认证和 TLS 加密。token 在控制连接建立时进行校验，防止未授权客户端接入。TLS 则用于加密传输层，避免数据被窃听。对于暴露到公网的服务，建议启用 `tls.force` 并配置证书。可观测性方面，frps 提供了 Dashboard 和 Prometheus 指标，可以监控连接数、流量和错误率。结合日志中的 `proxy name` 和 `error` 字段，能快速定位代理异常。

实战调优与常见陷阱

在实际部署中，常见的问题是 frpc 与 frps 版本不一致导致协议不兼容，因此应保持版本同步。另一个陷阱是 NAT 超时：如果控制连接长时间空闲，中间设备可能回收映射，导致连接断开。可以通过设置 `heartbeatInterval` 和 `heartbeatTimeout` 来维持连接活性。对于高并发场景，适当增加 `transport.poolCount` 可以复用工作连接，减少握手开销。

性能调优时，关注 frps 的 `maxPortsPerClient` 和 `userConnTimeout` 参数，避免资源耗尽。如果代理的是 HTTP 服务，启用 `vhostHTTPPort` 并配合域名解析，能实现基于 Host 的路由，减少端口暴露。最后，建议将 frps 部署在具有公网 IP 的服务器上，并限制其监听端口，仅开放必要的代理端口，以降低攻击面。
