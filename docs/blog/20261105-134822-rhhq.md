## 性能面板不是黑盒：CDP 与采样机制

打开 DevTools 的 Performance 面板录制一段交互，得到的火焰图并非浏览器“事后统计”出来的，而是通过 Chrome DevTools Protocol（CDP）实时推送的事件流。录制期间，渲染进程内的 Tracing 系统以环形缓冲区收集微秒级时间戳，主线程、合成线程、光栅线程各自上报 Begin/End 事件，前端再按 trace id 与父指针还原成调用树。理解这一点很关键：火焰图的宽度是时间区间，而不是 CPU 占用率；一个很宽但颜色很浅的块，可能只是在等待 I/O 或锁。

采样型 CPU Profile 则走另一条路。V8 以固定间隔（默认约 1ms）对执行栈采样，记录当前函数地址，最后聚合成自顶向下的调用树。因此短于采样周期的函数可能被“平滑”掉，排查微任务抖动时要结合 PerformanceObserver 与 User Timing API 打点，而不是只信火焰图。

## 从主线程任务到渲染流水线

主线程上的每个 Task 都可能触发样式计算、布局、绘制与合成。DevTools 把这些阶段拆成 Recalculate Style、Layout、Paint、Composite Layers 等条目，其底层依赖 Blink 的 Lifecycle 更新：一次事件循环结束前，若存在脏标记，浏览器会执行一次渲染更新。所谓“强制同步布局”，就是 JavaScript 在读取 offsetHeight 等属性时提前触发了 Layout，导致同一帧内布局被反复计算。

合成线程独立于主线程，负责把图层树提交给 GPU。滚动与 transform 动画若只作用于合成层，就能绕过主线程，这正是 will-change 与 transform 优化的原理。但滥用图层提升会带来显存与合成开销，DevTools 的 Layers 面板与 Rendering 中的“Layer borders”能直观暴露过度分层。

## 读懂长任务与关键指标

Performance 面板会把超过 50ms 的任务标记为 Long Task，并给出“Task”上的红色角标。底层依据是 Event Loop 的 task 时长统计，与 Long Tasks API 同源。LCP、CLS 等 Core Web Vitals 也在面板中标注，其数据来自 PerformanceObserver 的 entry 类型，与真实用户监控（RUM）采集的是同一套接口。

调试时建议先看 Main 轨道上的长任务，再逐层展开到函数级，结合 Bottom-Up 视图按自身耗时排序。对于 PHP Demo Blog 这类以 JSON API 为后端、前端渲染为主的项目，重点往往在首屏脚本解析与接口等待上，可配合 Network 面板的优先级列判断资源是否被正确调度。

## 可执行的排查路径

第一，录制时勾选“Screenshots”与“Web Vitals”，把视觉变化与指标对齐；第二，用 Performance Monitor 观察 JS 堆与 DOM 节点数，排除内存增长导致的 GC 抖动；第三，对疑似函数使用 console.profile 与 console.profileEnd 做定向采样，减少全量录制的噪声。掌握这些底层机制后，火焰图上的每一块颜色都能对应到具体的渲染阶段或 V8 行为，调优才有据可依。
