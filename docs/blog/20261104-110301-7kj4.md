## 为什么 CORS 在 JSON API 中不可回避

在 PHP Demo Blog 这类前后端分离的轻量项目中，前端页面往往部署在与 API 不同的源上。浏览器同源策略会拦截跨源的 XHR 与 Fetch 请求，而 CORS 正是服务端通过响应头声明“允许谁访问”的标准机制。理解 CORS 的关键在于分清两类请求：简单请求直接携带 `Origin` 头，服务端回以 `Access-Control-Allow-Origin` 即可；而携带自定义头、使用 `PUT`/`DELETE` 方法或 `Content-Type: application/json` 的请求会触发预检，浏览器先发 `OPTIONS` 询问许可，再发真实请求。JSON API 几乎必然触发预检，因此 `OPTIONS` 路由必须被正确响应，否则前端只会看到一个笼统的跨域错误。

## 核心响应头与凭证处理

最基础的一组头是 `Access-Control-Allow-Origin`、`Access-Control-Allow-Methods` 和 `Access-Control-Allow-Headers`。生产环境不应图省事写 `*`，而应维护一份白名单，将请求的 `Origin` 与白名单比对后原样回写，并配合 `Vary: Origin` 避免缓存串源。方法列表只声明实际用到的 `GET, POST, PUT, DELETE, OPTIONS`，头列表则要覆盖前端真正发送的 `Content-Type`、`Authorization` 等。若需要携带 Cookie 或 HTTP 认证，必须设置 `Access-Control-Allow-Credentials: true`，此时 `Allow-Origin` 绝不能是通配符，否则浏览器会直接拒绝。预检结果可以用 `Access-Control-Max-Age` 缓存，减少重复的 `OPTIONS` 往返，但数值不宜过大，以便权限调整后能及时生效。

## 在 PHP Demo Blog 中落地中间件

路由层应在分发前统一处理 CORS，而不是在每个控制器里重复写头。一个可执行的思路是：在入口文件注册一个中间件，先读取 `Origin`，命中白名单则写入上述响应头；若请求方法为 `OPTIONS`，直接返回 204 并终止后续流程；否则继续交给路由处理。这样既保证了预检的幂等性，也让业务代码保持干净。对于需要暴露给前端读取的响应头，例如分页总数，使用 `Access-Control-Expose-Headers` 显式声明。调试阶段可先放宽策略定位问题，但上线前务必收紧，并注意错误响应同样要带 CORS 头，否则前端拿不到真实的错误信息。

## 安全边界与常见陷阱

CORS 不是访问控制，它只约束浏览器行为，服务端仍需做身份认证与权限校验。白名单匹配要精确到协议、域名与端口，避免用后缀匹配导致子域被冒用。开发中常见的坑包括：在 `header()` 之后仍有输出导致头未生效、重定向响应丢失 CORS 头、以及把 `Allow-Credentials` 与通配符混用。建议在测试中用浏览器开发者工具的 Network 面板逐条核对预检与真实请求的响应头，并用 curl 模拟 `Origin` 验证服务端行为。把这些细节做扎实，跨域问题就会从“玄学报错”变成可预期、可复现的工程问题。
