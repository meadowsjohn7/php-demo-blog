## 慢查询日志：定位问题的起点

排查慢查询的第一步不是猜，而是让 MySQL 自己记录。开启 `slow_query_log` 并设置合理的 `long_query_time`（例如 1 秒），同时打开 `log_queries_not_using_indexes`，可以捕获两类问题：执行时间超阈值的语句，以及未走索引的语句。日志中的 `Query_time`、`Lock_time`、`Rows_examined`、`Rows_sent` 四个字段是判断根因的关键：`Rows_examined` 远大于 `Rows_sent` 说明扫描了大量无用行，通常是索引缺失或选择性差；`Lock_time` 偏高则指向锁竞争，而非单纯的查询效率问题。

## 执行计划：理解优化器的选择

`EXPLAIN` 输出中的 `type`、`key`、`rows`、`Extra` 是核心。`type` 从 `const`、`eq_ref`、`ref`、`range` 到 `ALL` 逐级退化，出现 `ALL` 意味着全表扫描。`Extra` 中的 `Using filesort` 和 `Using temporary` 往往对应排序或分组无法利用索引，需要额外内存或磁盘操作。更底层的做法是使用 `EXPLAIN FORMAT=JSON` 或 `optimizer_trace`，观察优化器为何放弃某个索引——常见原因是统计信息过期、索引列参与了函数运算，或隐式类型转换导致索引失效。

## 索引与存储引擎：成本模型的决定因素

InnoDB 的二级索引叶子节点存储的是主键值，因此通过二级索引查询非覆盖列时需要回表，这是 `Rows_examined` 偏高的常见来源。覆盖索引（将查询列全部放入索引）可以消除回表，是性价比最高的优化手段之一。同时要注意最左前缀原则：联合索引 `(a, b, c)` 对 `WHERE b = ?` 无效。索引的选择性同样重要，低基数列（如性别）单独建索引收益有限。此外，`ORDER BY` 与 `GROUP BY` 若能与索引顺序一致，可避免 filesort。

## 锁与并发：被忽视的慢查询成因

很多“慢查询”实际卡在锁等待上。`SHOW ENGINE INNODB STATUS` 的 `TRANSACTIONS` 段落会显示当前等待的锁与持有者。长事务、缺少索引导致的间隙锁扩大、以及 `SELECT ... FOR UPDATE` 的不当使用，都会让查询在 `Lock_time` 上消耗大量时间。排查时应结合 `information_schema.innodb_trx` 查看运行中的事务，优先缩短事务边界，而不是盲目加索引。

## 落地排查顺序

建议按“慢日志筛选 → EXPLAIN 看访问类型 → 检查索引与回表 → 查看锁等待 → 核对统计信息”的顺序推进。每一步都应有数据支撑，避免凭经验直接改 SQL。对于高频慢查询，可借助 `performance_schema` 的语句摘要表做聚合统计，再针对性优化。
